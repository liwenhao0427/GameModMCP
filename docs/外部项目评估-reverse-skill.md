# 外部项目评估：zhaoxuya520/reverse-skill

> 评估时点：2026-10。结论先行：**这个项目对我们最大的价值不是「抄功能」，
> 而是它作为一条独立路径，收敛到了与我们相同的方法论** —— 这是外部验证。
> 我们采纳了它的 3 条做法（见 §3），并明确**不采纳**它的技能路由架构（见 §4）。

评估对象：<https://github.com/zhaoxuya520/reverse-skill>
（逆向/渗透/安全技能路由包，MIT，38.4k★ / 5.3k fork，语言 PowerShell + Markdown）

---

## 1. 它是什么

一个**技能路由包**（不是 MCP 服务器）：AI 客户端命中安全/逆向关键词后，
它把任务路由到对应的方法论技能，并做「按需自举工具链 + 自进化经验库」。

规模（README 自述）：44 条路由规则（R0–R45）、175 个回归 case、
45 个核心技能模块、Windows + Ubuntu 双平台 CI、客户端中立。

架构要点：

| 机制 | 落点 |
|---|---|
| 行为链唯一真值 | `RULES.md` |
| 路由唯一真值 | `skills/config/routing.json`（见 §2.1） |
| 门禁脚本 | `verify-routing-coherence.ps1`、`test-routing.ps1`、`smoke.ps1` |
| 证据链契约 | `skills/ops/evidence-finding-path.md`（见 §3.2） |
| 生成式文档 | `skills/INDEX.md` 由 `extract-summaries.ps1` 生成 + drift check（见 §3.1） |

## 2. 与我们的重合（为什么值得看）

### 2.1 双方都收敛到了「单一真值 + 门禁校验」这套纪律

| 原则 | reverse-skill | GameModMCP |
|---|---|---|
| 单一真值源 | `routing.json` 是路由唯一真值，文档不得手改 | `server.py` 的 `@mcp.tool` 是工具唯一真值 |
| 门禁而非自觉 | `verify-routing-coherence.ps1` 校验结构 + 供应链 pin | `verify_tool_inventory.py` 9 处双向比对 |
| 回归基准 | 175 个 `hint → 期望 PRIMARY` case，不匹配即 CI 失败 | 48 个 `verify_*.py` |
| 防漂移自检 | 每 5 次工具调用暂停自问「有进展吗」 | 门禁脚本 + 非空转反证 |

**一条有趣的旁证**：它 README 写「175 cases」，而测试命令注释写「173」
—— **38.4k★ 的项目同样在漂**。说明文档数字漂移是这类项目的通病，
不是某个项目的能力问题。

### 2.2 差异：我们比它多的一条

通读 `RULES.md` / `AGENTS.md` / `evidence-finding-path.md` 后，
**没有找到**「把实现改回旧写法、看断言是否报红」这种**主动证伪**要求。
它有 self-audit 与「借口反驳表」（防偷懒），但性质不同：
那是「要求 Agent 做完」，不是「证明断言真的能抓到缺陷」。

我们的**非空转反证**在实战里立刻产生了价值 —— CatapultHero 真机验收
暴露的 3 个缺陷（坐标系 / `wait_for` 假阳性 / 按键结构体大小）全都靠它
兜住。**这一条不学它，保持我们自己的。**

### 2.3 定位差异（这也是我们的护城河）

在它 44 条路由里，「游戏逆向」只是 R0 通用兜底分支的一个关键词：

```
R0: "ollvm|anti-debug|unicorn|angr|gdb|deobfuscat|控制流平坦|反调试|
     unity|il2cpp|游戏.?逆向|game.?reverse|anti-cheat|反作弊"
```

也就是说：**38.4k★ 的安全工具包里，Unity/IL2CPP/游戏逆向没有专门的工具链**。
而我们做深的正是这条垂直线（元数据索引 → 运行时 token 对账 → 探针 →
最后一公里验收）。这个定位有独占价值。

## 3. 采纳的 3 条（本次已落地）

### 3.1 「生成 > 校验」—— 已落地为 `devtools/gen_docs.py`

它的 `INDEX.md` 由脚本从 frontmatter **生成**，并有 drift check。

我们的差别很实质：`verify_tool_inventory.py` 是**校验**，只能**发现**漂移；
生成本**不会产生**漂移。实测我们的 README 工具数已手工漂过 **5 次以上**
（AGENTS.md §4 逐条记着）。

落地前先做了「知识上移」核对，避免生成反而丢知识：

| 阶段 | README 独有特征词数 |
|---|---|
| 改造前 | **402** 个（docstring 里没有的手写事实） |
| 上移进 docstring 首段后 | **106** 个（逐条复核后确认全是**同义改写**，无真实知识丢失） |

生成器覆盖两部分：工具表区块（`BEGIN/END GENERATED` 标记）
**加上**正文里 5 处散落的硬编码数字（首段「N 个工具覆盖」、目录树、
验证脚本表头、报告段、脚本总数）。实测那 5 处就是同一类漂移 ——
生成区块建好之后它们仍在错，所以一并纳入生成。

验收：`gen_docs.py --check` 接进 `verify_tool_inventory.py` 第 2b 节；
反证做过 —— 篡改表格一行后 `--check` 报红 exit=1 并指出差异行。

### 3.2 「≥2 条独立证据才判成立」—— 已落地为 `verify_state`

它 `evidence-finding-path.md` 的原文规则：

> `validated` 需要 **>=2 independent** Evidence（最好 1 静态 + 1 动态）；
> 单条证据**不得静默提升**为 validated。

这条在我们自己的实战里立刻得到印证：CatapultHero 验收 Mod 时，
**日志**（`已修改 精核 = 108`）与**屏幕 OCR**（`精核：108`）两个互相独立的
来源都指向同一结论，才敢说「Mod 生效了」。
只看日志是不够的 —— **日志是 Mod 自己打的，Mod 写错了照样打日志**。

落地方式：新增 `verify_state(checks=..., require_independent=2)`。
- 判 `pass` 要求成立条数 ≥ `require_independent`（默认 2）；
- 只有 1 条成立时判 **`fail`** 并说明「**证据不足，不判通过**」——
  这正是「单条不得静默提升」；
- 三态与 `wait_for` 同源（`pass` / `fail` / `unverifiable`）。

**关键是消除重复实现**：把「单次条件求值」抽成 `_eval_condition`，
`wait_for` 与 `verify_state` **共用**它 —— 否则同一个条件在两处
给出不同结论，就成了新的假信息源（违反 AGENTS.md §3）。

验收：`devtools/verify_verify_state.py` 31 项，含反证
（把 `require_independent` 降到 1，同一输入变 `pass` ——
既证明参数真的影响行为，也证明「单条判 fail」不是恒真）。

### 3.3 量化的防死循环规则 —— 已写进 `SKILL.md`

它的规则很具体：「同一工具同参数 ≥2 次必须换方法」「同一方法失败 2–3 次
必须换路径」。这对我们**特别对症** —— 我们有一批「再试也不会变好」的场景：

| 场景 | 停止条件 | 该改做什么 |
|---|---|---|
| `wedged: true` | 一次都不重试 | `taskkill` 后重新注入 |
| `drain_events(kind=)` 空 | 连续 2 次为空就换判据 | 先看不带 `kind` 的调用看实际类型 |
| `wait_for` 超时 | 1 次即先看 `evidence` | 别直接重调同一个 |
| 同工具同参数 | ≥2 次必须换方法 | 换 `kind` / 换引擎路线 |

已作为「### 卡住了怎么办 —— 量化的停止条件（别死磕）」写进 SKILL.md。

## 4. 明确**不采纳**的

| 项 | 为什么不采纳 |
|---|---|
| 44 条 R0–R45 路由 | 它是「技能路由包」（选哪个**方法论**）；我们是「能力型 MCP 工具」（做**一件事**）。MCP 工具自带 description 供 Agent 选择，再加一层路由是重复（违反我们契约第 3 条「不许让 Agent 猜」的反面 —— 这里是「多给一层没必要的选择」） |
| Consent gate / scope 硬门 | 它靠**流程**门禁；我们靠 `destructiveHint` 等**语义标注**，客户端已有 approval 机制。它的门禁是为「未授权渗透」这个法律风险设计的，与我们的 Mod 场景不同 |
| CTF / 渗透 / EDR / 固件等领域技能 | 与游戏 Mod 无关 |
| 「借口反驳表」 | 防偷懒话术表。我们的对应机制是**门禁脚本**（红灯就是红灯，不需要说服 Agent）。用机器强制比用文字说服可靠 |
| Code-words 参数稳定性 | 它给危险参数起代号防模型改写。我们的危险工具已经用 `destructiveHint` + 显式确认处理，再加代号层是复杂度 |

---

## 5. 一句话总结

**它是一份很有价值的「方法论对照物」，不是「功能来源」。**

- 我们与它在**单一真值 + 门禁**上完全同构（互相印证）；
- 我们比它多**非空转反证**（主动证伪，抓真 bug）；
- 它比我们多**生成式文档**（已采纳）、**证据充分性契约**（已采纳）、
  **量化停止条件**（已采纳）；
- 定位上我们是它 R0 分支的一个关键词，而它没有这条垂直工具链 ——
  **护城河在，方向没错。**
