# 重启验证报告（第二轮）：E:\project 全量生效验证与分游戏理解

**问题**：重启本 MCP 后，它对 `E:\project` 下**符合要求**的游戏到底生效了没有？
判断依据是「能建/读索引」+「能注入并调用工具」。另外说清**还有什么异常**，
并对**不同游戏**给出理解总结，用来证明工具确实被正确调用了。

**验证时间**：2026-10-03 15:43 ~ 16:00（Python 3.10.6 / frida 17.19.0 /
ilspycmd 11.1.0 / MCP v1.0.0，**38 个工具**）。

**一句话结论**：

1. **生效** —— 两项判断依据都通过：静态索引 **26 款受支持游戏全通**
   （15 IL2CPP + 10 Mono + 1 UE，45.1 s），运行时链路在 **5 款游戏**
   （3 IL2CPP + 2 Mono）上**逐环节跑通**，含「静态 token == 运行时 token」对账；
   UE 走资源容器路线同样全通。
2. **重启本身也验证了**：杀掉服务器进程后 DSH 的 `mcp-client` **约 2 秒**
   自动拉起新进程（pid 20752 → 14636），新进程 `get_session` 为空 = 拿到的是新实例。
3. 上一轮报告里**已修的 5 个缺陷全部复验通过**（§4），未回归。
4. **本轮新发现 1 个真实缺陷**（§5）：`archive/probes/` 下 5 个侦察脚本的
   仓库根推导写死层数，归档时没跟着改，导致文档里写的复现命令**整体失效**。
   已修（改为自寻仓库根）并提交 `ee6229e`。
5. 上一轮**未定位根因**的那条（探针在游戏早期 attach 可能卡死）**仍然存在**，
   本轮未再触发，但**不许**据此认为已修 —— 见 §6。

| 游戏 | 静态 token | 运行时 token | 命中 |

| Ved | `0x06000C71` | `0x06000c71` | ✅ |

## 5. 【本轮新发现】归档侦察脚本的仓库根推导失效

### 现象

按 `docs/重启验证与运行时理解报告.md` §5 的复现命令跑：

```powershell
python devtools\archive\probes\runtime_matrix.py
```

**每个脚本都在 `tools/list` 崩掉**，且**残留被测游戏进程**：

```
OSError: [Errno 22] Invalid argument
  File "devtools\mcp_stdio.py", line 109, in _send
    self._proc.stdin.write(json.dumps(obj) + "\n")
```

### 根因

脚本从 `devtools/` 挪进 `devtools/archive/probes/` 时，**路径推导没跟着改**：

```python
ROOT = Path(__file__).resolve().parent.parent   # = devtools/archive ← 错
SERVER = ROOT / "src" / "gamemod_mcp" / "server.py"   # 不存在的路径
```

实测 `Test-Path devtools\src\gamemod_mcp\server.py` = **False**，
真正的 server.py 在 `src\gamemod_mcp\server.py`。

**为什么看起来像「MCP 服务器坏了」**：`subprocess.Popen` 对不存在的可执行文件
**不抛异常**（它启动失败是异步的），于是 `initialize` 有时还能返回，
到第二次写 stdin 时才以 `OSError: [Errno 22]` 暴露 —— 而这个错误
指向 `mcp_stdio.py`，很容易被读成「服务器崩了」。

**隔离实验**（`.cache-test/diag_with_game.py`）证明**服务器完全正常**：

| 场景 | initialize | tools/list |
|---|---|---|
| 不带游戏 | ✅ | ✅ 38 个工具 |
| 先启动游戏再起服务器 | ✅ | ✅ 38 个工具 |

差异只在**脚本传给 `Popen` 的路径**。

### 影响

`docs/重启验证与运行时理解报告.md` §5 把 `runtime_matrix.py` 列为
「运行时链路横向扫描的主工具」，`devtools/archive/README.md` 也这么写。
脚本跑不起来 ⇒ **那份报告的复现步骤整体失效**，而报告本身没有任何标记。

这正是 `AGENTS.md` §5.3 警告的同一类问题：**绝对/写死的路径是本项目最容易腐坏的东西**。

### 修复

改为**自寻仓库根**，不再写死层数（这样以后再挪也不会坏）：

```python
def _repo_root() -> Path:
    for p in Path(__file__).resolve().parents:
        if (p / "src" / "gamemod_mcp" / "server.py").is_file():
            return p
    raise SystemExit("找不到仓库根（没有 src/gamemod_mcp/server.py）")
```

涉及 5 个脚本：`runtime_matrix.py` / `blocking_check.py` /
`failed_call_side_effect.py` / `probe_check.py` / `repeat_launch.py`。

**验证**：`probe_check.py static` 修复后正常输出
（`initialize ok=True tools=38`、`open_game` 0.04s、`list_images` 143 个）；
修好的 `runtime_matrix.py` 跑完 **4 款游戏全部全通**（§3 的横向数据就是它跑的）。

顺带把脚本自己写的产物加进 `.gitignore`（`archive/probes/*.log`、`*.jsonl`）。

提交：`ee6229e`。

## 6. 仍未解决的问题（**不许**说成已修）

### 6.1 探针在游戏早期 attach 可能卡死（上一轮 §4.2 的根因）

**现状**：本轮**未再触发**（`launch_game` 路径没测；4 款游戏都走 attach 模式，
且注入的是已经进主界面的进程）。

**已有结论（上一轮留下，仍然有效）**：

- 触发条件与「探针在游戏早期就调 `il2cpp_thread_attach`」有关；
- 它是**间歇性**的 —— 同样顺序实测既有卡住也有正常，**单次观测不能当结论**；
- 卡住时游戏窗口标题是 `Fatal error in GC`；
- 已做的缓解：`READY_SETTLE_DELAY = 3.0`（spawn 路径第一次探测前先静默 3 秒）；
- 真正兜底的是 `CALL_TIMEOUT`（30 秒）：**无论卡不卡，都不会再无限挂住**，
  且会如实报 `wedged`。

**本轮不能说「已修」的三个理由**（与上一轮一致）：
① 根因未知；② 实验覆盖不全（0.5 秒间隔是 0/8，而产品在同一配置下真卡死过）；
③ 缓解 ≠ 修复（`settle` 只是避开窗口，游戏加载更慢时可能又落回窗口内）。

### 6.2 `launch_game` 本轮未验证

本轮运行时验证全部走 **attach 模式**（先手工启动游戏到主界面，再注入）。
`launch_game`（spawn 路径）**没有测** —— 它正是 §6.1 风险集中的那条路径。
要测它请用 `bounded_repeat.py`（有界成功率统计，按进程树硬杀收尾，自身不会挂）。

## 8. 对不同游戏的理解总结

### 8.1 分类总览

| 类别 | 数量 | 工具能做到什么 | 推荐 Mod 方向 |
|---|---|---|---|
| **IL2CPP**（Unity AOT） | 15 | 全量类型系统 + 运行时真实偏移/地址 + Hook | 数值/逻辑修改、存档编辑、UI 扩展 |
| **Mono**（Unity JIT） | 10 | 同上 **+ 直接反编译出 C# 源码** | 同上，且**能先读源码再改**，成本最低 |
| **Unreal** | 1 | 只有资源容器（pak/utoc/清单/脚本对象） | 资源替换、本地化、配置修改 |
| **不支持** | 8 | 如实报 `unknown` + 家族证据 | 无（本 MCP 不做） |

### 8.2 IL2CPP（15 个样本）

**工具做的事**：解析 `global-metadata.dat` → SQLite 索引（类型/方法/字段/token），
注入后把类实体化，拿真实字段偏移与方法地址，用 token 对账。

**实测理解**：

- 规模跨度大但都稳：最小 `PathOfIdle` 14,477 类型 / 92 程序集，
  最大 `Dave.the.Diver` 44,402 类型 / 182 程序集，全部建起索引。
- 字段类型是**启发式**（约 90% 可解），所以 `class_detail` 的字段类型要带
  `type_confidence` 看；**偏移必须运行时取**。
- **版本区间是硬边界**：v24~v31 可解，v39（Unity 6.3）**如实拒绝**。
- 嵌在子目录里的布局（`Everything.is.Crab.v1.0.1\Everything.is.Crab.v1.0.1`、
  `A\Vampire Crawlers`、`Vampire Crawlers Mods\Vampire Crawlers`）能自动识别。

**推荐做的 Mod**（按性价比）：

| 目标 | 为什么适合 | 实测线索（本轮查到） |
|---|---|---|
| **数值修改**（金币/血量/伤害） | 字段有名字有类型，偏移可运行时取，最稳 | `Vampire Crawlers`：`PlayerStatsSaveData.CurrentHealth`(Int32)、`EnemyConfig.BaseHealth`(Int32) |
| **存档编辑** | 存档类通常集中，字段语义清楚 | `Dave.the.Diver`：`DR.Save.SavePlayerData`（18 字段 / 53 方法）、`SaveSystemPlayerDataManager` |
| **属性/掉落表调整** | 枚举 + 配置类可枚举，适合批量改 | `PathOfIdle`：`EAttrType` 里 `JiChuSkillDamageUp`/`bleedDamageUp` 等一串伤害属性 |
| **UI/行为扩展** | `MonoBehaviour` 可全量枚举（`find_derived_classes`） | Ved 有 1,298 个、Dave 有 7,552 个 MonoBehaviour |

**不建议**：直接改代码字节（会崩；要改行为请 Hook 或改数据字段）。

### 8.3 Mono（10 个样本）

**与 IL2CPP 配方完全一致**，但多一个 IL2CPP 没有的能力：**直接反编译出 C#**。

实测 `decompile(type_name="SaveStats")`（Hollow Knight Silksong）拿到
**119 行真正的 C#**，`Geo`（货币）的赋值逻辑一目了然：

```csharp
public SaveStats(PlayerData playerData, SaveGameData saveGameData)
{
    Version = playerData.version;
    MaxHealth = playerData.maxHealthBase;
    MaxSilk   = playerData.CurrentSilkMaxBasic;
    Geo       = playerData.geo;          // ← 货币在这里赋值
    Shards    = playerData.ShellShards;
    ...
}
```

配合静态字段搜索（`search_fields("geo")` → `PlayerData.geo` 是 `System.Int32`，
`type_confidence: exact`），**改金币这件事在 Mono 上是"看源码 → 找字段 → 改值"，
没有猜测环节**。

**必须记住的 5 条差异**（全部实测成立，见 §3.2）：
① 没有 RVA；② `gc_control` 不支持；③ 程序集懒加载（注入后自动等稳定，实测 2.1s）；
④ 短名只认顶层类型；⑤ **静态索引不含 `UnityEngine.*`**。

**推荐做的 Mod**：与 IL2CPP 相同，但**优先级更高** ——
因为能先读源码确认逻辑，是**成本最低、最不容易改错**的一类。
典型：Silksong 的 `PlayerData.geo`（货币）、`SaveStats`（存档摘要）、
Archon Soul 的 `MusicManager`（音乐/氛围）、Sephiria / Hell Maiden 的战斗数值。

### 8.4 Unreal（1 个样本：CatapultHero）

**能力边界完全不同**：UE 没有集中元数据，`search_classes` / `class_detail` /
`open_game` **都不适用**（`open_game` 明确返回 `ok:false` + `next_tools`）。
UE 的强项是**资源容器**，本轮实测 `match_ratio = 1.0`（与打包清单逐条对上）。

**推荐做的 Mod**：

| 目标 | 工具 | 实测证据 |
|---|---|---|
| **本地化/汉化** | `ue_list_entries(pattern=".locres")` | 游戏自带 51 个 `.locres`，含 `Game/zh-Hans`、`zh-Hant` |
| **资源替换**（贴图/模型/音效） | `ue_list_entries` + `ue_profile` | 7,178 个 `.uasset`，含中文路径 `CatapultHero/Content/CatapultHero/精灵片/角色/…` |
| **确认某功能是否被打进包** | `ue_list_entries(pattern=...)` | 如 `AbilitySystem`、`EasyMultiSave`（存档插件） |
| **配置修改** | `ue_profile` 的 `configs` | 读到 `steam_settings/configs.user.ini`（`language=schinese`）、成就表 |

**拿不到的东西（如实声明，不是 bug）**：UE 版本号、FName 池、UObject 属性偏移、
`.usmap`（样本中不存在）。**不要**在 UE 上期待 `search_classes` 能用。

### 8.5 不支持引擎 / 非游戏（8 个）

Godot（`Pathogenic`）/ GameMaker（`IGNOBLE`）/ Electron（`Im.No.Demonlord`、
`苏丹的游戏阅读器`）/ 自研·原生（`DOOM The Dark Ages`、`Astral.Ascent`）/
未能判定（`CLIProxyAPI`、`sub2api`）。

工具**如实报 `unknown` 并给出家族证据**，`engine` 仍然是 `unknown` ——
提示是「解释」，不是「假装支持」。**看到这些直接停下并说明原因**，
不要反复重试 `open_game`。
