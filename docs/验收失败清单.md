# 验收套件失败清单（7 项）

> 快照时间：2026-10-02 ｜ 分支 `master` ｜ 基于 `python devtools\run_all_verify.py --no-cov`
>
> 结果：**通过 33 / 40，断言失败 7，进程崩溃 0，超时 0**。
>
> 本文件写给**下一步接手修复的人/Agent**。每一项都给出：
> **现象 → 根因（已定位到行）→ 修复路径 → 怎么验证修好了**。
>
> 为什么单独成文：这 7 项在 `run_all_verify.py` 里只输出一行名字，
> 看不出「是环境缺样本」还是「代码真坏了」。而这两类必须分开处理 ——
> 前者换台机器就消失，后者必须改代码。**别把它们混成一个「环境问题」糊过去。**

---

## 〇、先分清两类

| 类别 | 数量 | 特征 | 换台装了全部样本的机器会怎样 |
|---|---|---|---|
| **A. 环境缺样本** | 4 | 报「无法验证：样本 X 不在本机」 | 自动消失（**不是 bug**） |
| **B. 脚本自身语法错** | 2 | `SyntaxError`，脚本根本没跑起来 | **不会消失**，换 Python 版本才有解 |
| **C. 真实功能缺陷** | 1 | 断言红，且与样本无关 | **不会消失**，必须改代码 |

**只有 1 项（C）是真正的产品缺陷**，但它藏得最深 —— 见 §3。
另外 B 类 2 项虽然「只是脚本」，却让两个验收脚本**完全没在跑**，
等于相关能力长期失去门禁保护，优先级不低。

### 本机样本盘点（判断 A 类的依据）

```
find_il2cpp        None      ← 缺（README/多处依赖它）
find_il2cpp_dump   None      ← 缺（verify_parser 的真值来源）
find_mono          E:\project\Archon Soul
find_mono_multi    E:\project\Kinny and the Cosmic Cauldron
find_ue_pak_v12    E:\project\CatapultHero
find_ue_pak_v11    None      ← 缺（Dinoblade）
find_container     E:\project
find_unsupported   E:\project\IGNOBLE (gamemaker)
```

`AGENTS.md` §5.3 的约定是「样本缺失记为『无法验证』并跳过，**不许假装通过**」。
A 类 4 项的**退出码**是 `1` 而不是 `0`，所以它们在 `run_all_verify.py` 里
被计成「失败」—— 这是**报告口径**问题，不是产品问题（见 §4 的收尾建议）。

## 一、A 类：环境缺样本（4 项）

### A1. `verify_mcp_discovery`

- **现象**：`⚠️ 无法验证：样本「IL2CPP (Garden of Witches)」不在本机` → `缺少样本 ['il2cpp']，无法验证。` → exit 1
- **位置**：[`verify_mcp_discovery.py:445-458`](../devtools/verify_mcp_discovery.py#L445-L458)
- **根因**：`samples.require(il2cpp, ...)` 返回 False，函数直接 `return 1`。
  它需要 **5 个**样本（container / il2cpp / mono / ue / unsupported），
  本机缺 `il2cpp`（Garden of Witches）。
- **修复路径**：无需改代码。补样本即可 —— 把 Garden of Witches 放到
  `E:\project` 下（或设 `GAMEMOD_SAMPLES` 指向别处）。
- **验证**：`python devtools\verify_mcp_discovery.py` → 应打印各部件断言而非「缺少样本」。

### A2. `verify_session_switch`

- **现象**：`没有 IL2CPP 样本，无法验证。` → exit 1
- **位置**：[`verify_session_switch.py:245-247`](../devtools/verify_session_switch.py#L245-L247)
- **根因**：同上，缺 `il2cpp` 样本。
- **修复路径**：补样本。**注意**：这个脚本测的是「切换游戏时上一个游戏的身份
  不许留下来」，属**状态污染**类缺陷的门禁，长期不跑是有风险的 ——
  建议优先补上这个样本。
- **验证**：`python devtools\verify_session_switch.py` → 三个 part 都执行。

### A3. `verify_mcp_extra`

- **现象**：`通过 8 项 / 失败 1 项`，失败项 `❌ 游戏主程序存在`
- **位置**：[`verify_mcp_extra.py:183`](../devtools/verify_mcp_extra.py#L183)
  ```python
  else:
      check("游戏主程序存在", False, GAME_EXE)
  ```
- **根因**：`GAME_EXE` 为 `None`（缺 IL2CPP 样本）时走进 `else` 分支，
  **主动记了一条失败**。这与文件开头「样本不可用时记为『无法验证』并跳过」
  的约定自相矛盾 —— 别的脚本缺样本时是跳过，这里却记成失败。
- **修复路径**（两条，任选）：
  1. 补样本（最简单）。
  2. 改代码：把这个 `else` 分支改成打印「⚠️ 无法验证」并**不调 `check`**，
     与同文件 `HAVE_GAME` 的语义保持一致。**推荐这条** —— 它同时修掉
     一个真实的口径不一致（缺样本被算成断言失败）。
- **验证**：`python devtools\verify_mcp_extra.py` → 缺样本时应显示「无法验证」
  而不是「失败 1 项」。

### A4. `verify_mcp_ue`

- **现象**：`通过 39 项 / 失败 1 项 / 警告 2 项`，失败项
  `❌ Dinoblade：ue_manifest 返回 ok — 需要提供 path 或 game_dir`
- **位置**：[`verify_mcp_ue.py:330-335`](../devtools/verify_mcp_ue.py#L330-L335)
  ```python
  for sp in SAMPLES:
      if not Path(sp["root"]).is_dir():
          continue
  ```
- **根因**：**这是本清单里最隐蔽的一处**。缺 `ue_pak_v11`（Dinoblade）时，
  `SAMPLES` 里 Dinoblade 的 `root` 被设成**空串 `""`**（见
  [`verify_mcp_ue.py:46`](../devtools/verify_mcp_ue.py#L46)），
  而 `Path("")` 等于 `Path(".")`、`.is_dir()` 返回 **True** ——
  于是「缺样本就跳过」的判断**失效**，脚本拿着当前目录去调 `ue_manifest`，
  自然报「需要提供 path 或 game_dir」。
- **修复路径**：把跳过条件从 `not Path(sp["root"]).is_dir()` 改成
  **先判空串**：
  ```python
  if not sp["root"] or not Path(sp["root"]).is_dir():
      continue
  ```
  （或建 `SAMPLES` 时用 `None` 而不是 `""`，并相应判 `None`。）
  **注意**：这同时解释了为什么它报的是「失败 1 项」而不是「无法验证」——
  脚本以为自己有样本。
- **验证**：`python devtools\verify_mcp_ue.py` → 缺 Dinoblade 时应跳过该样本，
  失败数降到 0。

## 二、B 类：脚本自身语法错（2 项，**必须改代码**）

这两项的共性是：**用了 PEP 701 语法（Python 3.12+ 才允许 f-string 里出现
换行 / 反斜杠），而本机是 3.10 / 3.11**。脚本连编译都过不了，
`SyntaxError` 让整个验收**一行都没跑**。

> **为什么优先级不低**：`verify_agent_js` 是探针接口的门禁
> （「每个 RPC 必须宿主侧有出口，不许有死代码」），`verify_mono_runtime`
> 是 Mono 运行时的门禁。两者长期不跑 = 相关能力长期无保护。
> 本轮改 `agent.js` 新增 `dispose()` 时，**就是靠人工核对**确认它有出口的，
> 本该由 `verify_agent_js` 自动拦住。

### B1. `verify_agent_js`

- **现象**：
  ```
  File "devtools\verify_agent_js.py", line 89
      print(f"  探针加载期消息：{json.dumps(exports[0].get('payload'),
            ^
  SyntaxError: unterminated string literal (detected at line 89)
  ```
- **位置**：[`verify_agent_js.py:88-90`](../devtools/verify_agent_js.py#L88-L90)
  ```python
  print(f"  探针加载期消息：{json.dumps(exports[0].get('payload'),
                                        ensure_ascii=False)}")
  ```
  f-string 的 `{}` 表达式里跨了行 —— 3.12 之前不允许。
- **修复路径**：把表达式提到 f-string 外面（**最小改动，且与 3.10 兼容**）：
  ```python
  _payload = json.dumps(exports[0].get("payload"), ensure_ascii=False)
  print(f"  探针加载期消息：{_payload}")
  ```
- **验证**：`python -m py_compile devtools\verify_agent_js.py` 应通过；
  再 `python devtools\verify_agent_js.py` 应跑到断言而不是 SyntaxError。
  **注意**：该脚本会**注入自己的进程**，Windows 无显示环境下偶发
  访问违例（`0xC0000005`），`run_all_verify.py` 已把它列进
  `SELF_ATTACH` 给额外重试预算 —— 崩了按「环境抖动」重试，别当成产品问题。

### B2. `verify_mono_runtime`

- **现象**：
  ```
  File "devtools\verify_mono_runtime.py", line 247
      print(f"  同一正则在后端实现区的命中次数：{len(re.findall(r'funcs\\.il2cpp_[a-zA-Z0-9_]+', backend_zone))}")
                                                                                                                                 ^
  SyntaxError: f-string expression part cannot include a backslash
  ```
- **位置**：[`verify_mono_runtime.py:247`](../devtools/verify_mono_runtime.py#L247)
  f-string 的 `{}` 里含 `r'...\\.'` —— 反斜杠在 3.12 之前不允许出现在
  f-string 表达式内。
- **修复路径**：同样把正则提到外面：
  ```python
  _hits = len(re.findall(r"funcs\.il2cpp_[a-zA-Z0-9_]+", backend_zone))
  print(f"  同一正则在后端实现区的命中次数：{_hits}")
  ```
- **验证**：`python -m py_compile devtools\verify_mono_runtime.py` 通过；
  再跑该脚本应进入断言。

> **顺带提醒**：`pyproject.toml` 声明 `requires-python = ">=3.10"`。
> 既然声明支持 3.10，`devtools/` 下的脚本就不该用 3.12 才有的语法 ——
> 这两处属于**声明与实现不一致**。修法有两种：
> (a) 改脚本（上面给的，兼容 3.10+，**推荐**）；
> (b) 把 `requires-python` 提到 `>=3.12`，但那会缩小可用范围。
> 建议 (a)。**若选 (a)，可考虑加一条 lint 防止再犯**：
> 在 `verify_encoding_console.py` 里加「所有 `devtools/*.py` 必须能被
> 最低支持版本的 Python 编译」的检查（用 `ast.parse` 或 `py_compile`）。

## 三、C 类：真实功能缺陷（1 项，**必须改代码**）

### C1. `verify_mcp_decompile` —— 嵌套类型的 `decompiled_type` 报错名

- **现象**：`通过 44 项 / 失败 3 项`，三个失败项同源：
  ```
  ❌ 明确退让到了外层类型 — 'BarrierSpellEffect.BarrierReference'
  ❌ 给出了 nested_note 说明退让行为 — （否则 Agent 会以为拿到的是内层源码）
  ❌ `Outer+Inner` 写法行为与 `.` 一致 — ok=True type=BarrierSpellEffect.BarrierReference
  ```
- **位置**：[`engine/decompile.py:266-271`](../src/gamemod_mcp/engine/decompile.py#L266-L271)
  ```python
  if cand != str(type_name).strip().replace("+", "."):
      out["nested_note"] = ( ... )
  ```
- **根因（已复现确认）**：`_candidates("BarrierSpellEffect.BarrierReference")`
  生成的第一个候选**就是原样全名**
  `['BarrierSpellEffect.BarrierReference', 'BarrierSpellEffect']`。
  而 `ilspycmd -t BarrierSpellEffect.BarrierReference` **会返回成功、退出码 0**，
  产物是**外层类型**（内含内层声明）—— 这正是文件开头 docstring「坑 1」
  描述的假成功。于是：
  - 第一轮循环 `cand == "BarrierSpellEffect.BarrierReference"` 就命中，
    `_declared_names(source)` 里既有 `BarrierSpellEffect` 也有 `BarrierReference`
    （外层产物必然含内层声明），**护栏 `wanted in declared` 通过**；
  - 循环在**第一个候选**就 `return`，**永远不会退让到 `BarrierSpellEffect`**；
  - `out["decompiled_type"] = cand` = 内层全名（**谎报**，实际产物是外层）；
  - `cand != 请求名` 为 False → **`nested_note` 不写**（Agent 无从知道）。

  实测证据：
  ```
  decompiled_type = BarrierSpellEffect.BarrierReference   ← 报的是内层
  nested_note     = None                                  ← 没提示
  source 含 'class BarrierSpellEffect' : True             ← 产物其实是外层
  ```
- **为什么危险**：Agent 拿到 `decompiled_type=内层全名` + 无提示，
  会以为这是内层类型的**独立源码**。实际给的是外层整份源码 ——
  这与 `decompile.py` docstring 里「绝不把外层当内层交出去」的设计意图**相反**。
  测试脚本的注释也点明了这一点：
  > 「否则 Agent 会以为拿到的是内层源码」

- **修复路径**（两条，建议 2）：

  1. **让护栏识别「内层名也出现在外层产物里」**：仅当产物**顶层**声明了
     该类型（而不是嵌套声明）才算命中。需要区分
     `class BarrierSpellEffect`（顶层）与 `class BarrierReference`（嵌套），
     `_DECL_RE` 目前是扁平匹配、做不到，改动面较大。

  2. **直接跳过「内层全名」这个候选**（最小且语义正确）：嵌套类型在
     ilspycmd 里**无法单独定位**是已知事实（docstring 坑 1），
     那第一个候选本就不该试。改成：若 `type_name` 归一化后含 `.` 或 `+`，
     **先按「去掉最后一段」退让**，只在退让后的名字上跑 ilspycmd；
     并把 `decompiled_type` 如实设成**实际反编译的那个**（外层名），
     同时写 `nested_note`。
     这样 `decompiled_type == "BarrierSpellEffect"`、
     `nested_note` 非空，三个断言同时变绿。

- **务必保留的现有护栏**：脚本里这条**必须继续通过**（它是「不存在的内层
  不许退回外层冒充」的回归，目前是绿的）：
  ```
  ✅ 请求不存在的内层类型时拒绝（不能退回外层冒充）
  ```
  改候选生成逻辑时，别把「请求 `Outer+根本不存在Xyz` 必须 `ok:false`」
  这条一起改坏 —— 修 C1 的正确姿势是**退让到外层并如实标注**，
  而不是「任何请求都退回外层」。

- **验证**：
  ```powershell
  python devtools\verify_mcp_decompile.py
  ```
  期望：`失败 0 项`，且以下三条为绿：
  - `明确退让到了外层类型`（`decompiled_type == "BarrierSpellEffect"`）
  - `给出了 nested_note 说明退让行为`
  - `` `Outer+Inner` 写法行为与 `.` 一致 ``
  同时 `请求不存在的内层类型时拒绝` **仍然为绿**。

- **需要的样本**：`find_mono()` → `Archon Soul`（本机**已有**）。
  所以 C1 与 A 类不同：**它现在就能修、也能验**。

## 四、建议的修复顺序

1. **B1 + B2（改脚本语法）** —— 5 分钟，让两个门禁**重新开始工作**。
   改完立刻能发现本轮改动是否碰坏了探针契约。
2. **C1（decompile 嵌套类型）** —— 唯一的真实产品缺陷，本机样本齐全，
   可当场改当场验。建议走修复路径 2。
3. **A3 / A4（口径与判空 bug）** —— 各一两行，让「缺样本」不再冒充
   「断言失败」。A4 的 `Path("")` 是个值得记住的坑。
4. **A1 / A2（补样本）** —— 若你能提供 Garden of Witches，
   这两项自动变绿；拿不到就把它们当「已知未验证」，
   别当成产品问题。

### 收尾建议：把「缺样本」与「失败」分开计

`run_all_verify.py` 现在把 A 类的 exit 1 计成「断言失败」，
于是汇总行 `失败 7` 里混了 4 个**环境问题**。建议让这类脚本
在缺样本时返回一个**独立退出码**（例如 `2`），
`run_all_verify.py` 据此归到「跳过」而不是「失败」。
这样汇总行才真正等于「代码坏了几处」。

> 注意 `AGENTS.md` §5.3 的硬要求：**不许假装通过**。
> 所以是「单列一类」，不是「算成通过」—— 跳过要打印出来、要计数。

---

## 五、一句话结论

**7 项失败里只有 1 项是产品缺陷**（`decompile` 的嵌套类型名谎报），
本机样本齐全、可立即修复；
**2 项是验收脚本自己用了 Python 3.12 语法**、在 3.10 上根本没跑起来；
**4 项是缺样本**（其中 2 项还把「缺样本」错误地报成了断言失败）。
