## 三、C 类：真实功能缺陷（1 项，**必须改代码**）—— ✅ 已修

### C1. `verify_mcp_decompile` —— 嵌套类型的 `decompiled_type` 报错名

- **现象**：`通过 44 项 / 失败 3 项`，三个失败项同源：
  ```
  ❌ 明确退让到了外层类型 — 'BarrierSpellEffect.BarrierReference'
  ❌ 给出了 nested_note 说明退让行为 — （否则 Agent 会以为拿到的是内层源码）
  ❌ `Outer+Inner` 写法行为与 `.` 一致 — ok=True type=BarrierSpellEffect.BarrierReference
  ```
- **位置**：[`engine/decompile.py:266-271`](../src/gamemod_mcp/engine/decompile.py#L266-L271)
- **根因（已复现确认）**：`_candidates("BarrierSpellEffect.BarrierReference")`
  生成的第一个候选**就是原样全名**
  `['BarrierSpellEffect.BarrierReference', 'BarrierSpellEffect']`。
  而 `ilspycmd -t BarrierSpellEffect.BarrierReference` **会返回成功、退出码 0**，
  产物是**外层类型**（内含内层声明）—— 这正是文件开头 docstring「坑 1」
  描述的假成功。于是：
  - 第一轮循环 `cand == "BarrierSpellEffect.BarrierReference"` 就命中，
    `_declared_names(source)` 里既有 `BarrierSpellEffect` 也有 `BarrierReference`
    （外层产物必然含内层声明），**护栏 `wanted in declared` 通过**；
  - 循环在**第一个候选**就 `return`，**永远不会退让到 `BarrierSpellEffect`**；
  - `out["decompiled_type"] = cand` = 内层全名（**谎报**，实际产物是外层）；
  - `cand != 请求名` 为 False → **`nested_note` 不写**（Agent 无从知道）。

  实测证据：
  ```
  decompiled_type = BarrierSpellEffect.BarrierReference   ← 报的是内层
  nested_note     = None                                  ← 没提示
  source 含 'class BarrierSpellEffect' : True             ← 产物其实是外层
  ```
- **为什么危险**：Agent 拿到 `decompiled_type=内层全名` + 无提示，
  会以为这是内层类型的**独立源码**。实际给的是外层整份源码 ——
  这与 `decompile.py` docstring 里「绝不把外层当内层交出去」的设计意图**相反**。

- **修复路径（实际采用的，与原建议不同 —— 原建议是错的）**：

  原文档建议的「路径 2」是：**只要 `type_name` 含 `.` 或 `+` 就先砍掉最后一段**，
  只在退让名上跑。**实测这条会打坏命名空间限定的顶层类型**：

  ```
  路径2 对 'FlyingWormConsole3.LiteNetLib.NetManager':
      会去跑 -t 'FlyingWormConsole3.LiteNetLib' → ok=False rc=65   ← 本该直接命中
  路径2 对 'BarrierSpellEffect.BarrierReference':
      会去跑 -t 'BarrierSpellEffect' → ok=True rc=0
  ```

  根因是：**嵌套类型与「命名空间限定的顶层类型」在字面上都是 `A.B`**，
  只看名字里有几个点**根本区分不了**。正确做法是拿程序集的**权威类型清单**：

  · `_list_types()` 调 `ilspycmd -l cisde`，实测与 TypeDef 表行数**完全一致**
    （Archon Soul：1387 = 1387；四个 Mono 样本逐一核对过），
    且清单里嵌套用 `+` 表示（`BarrierSpellEffect+BarrierReference`）。
  · `_match_listing()` / `_real_target()` 据此判定请求名到底是哪一种，
    算出 ilspycmd **实际会产出**的类型名。
  · `decompiled_type` 一律填**实际产出**的那个名字，并写 `nested_note`。
  · 清单取不到时退化为修复前的行为（不会更糟），**不猜**。

  这样 `decompiled_type == "BarrierSpellEffect"`、`nested_note` 非空，
  三个断言同时变绿，而命名空间顶层类型照旧直接命中。

- **务必保留的现有护栏**（继续为绿）：
  ```
  ✅ 请求不存在的内层类型时拒绝（不能退回外层冒充）
  ```
  实测 ilspycmd 对 `Outer+不存在` / `Outer.不存在` 都返回 `exit 65`，
  所以「退让」不会退成「只要外层存在就算成功」。

- **验证**：
  ```powershell
  python devtools\verify_mcp_decompile.py
  ```
  实测：**通过 51 项 / 失败 0 项 / 警告 1 项**（警告来自缺 IL2CPP 样本）。

- **非空转反证**（AGENTS.md §5 要求）：把 `_real_target` 换回旧行为
  （恒返回 `(cand, False)`）后，`decompiled_type` 立刻变回
  `'BarrierSpellEffect.BarrierReference'`、`nested_note` 变回 `False`，
  两条断言**确实报红** —— 说明它们不是恒真。

- **需要的样本**：`find_mono()` → `Archon Soul`（本机**已有**）。

## 五、随机测试新发现的缺陷：IL2CPP 元数据 v39（**本次新增修复**）

### C2. `il2cpp_meta` 对超出支持区间的版本静默硬解

- **现象**：`open_game(Enter the Chronosphere)` 耗时 **573 秒**，最后
  `ok:false` + `构建索引失败：UNIQUE constraint failed: fields.idx`。
- **样本**：`E:\project\Enter.the.Chronosphere.Early.Access`
  （Unity **6000.3.14f1**，metadata **v39**，22.5 MB）。
- **根因（已定位）**：`_typedef_size` 推断不出 stride 时只 `warn` 一句，
  然后**照旧硬解**。v39 的头部布局已变 —— 实测连
  `fields` 表 24,998 字节都**除不尽 12**（余 2），`methods`/`parameters`/
  `images`/`assemblies` 同样除不尽。硬解产出 181,396 个类型、
  Σfield_count = 3,156,391,098（真值只有 2,083 个字段），
  接着花 573 秒建索引，最后撞上 sqlite 唯一约束。
  **把「版本不支持」伪装成了「数据库错误」**，错误信息还会把人往错方向带。
- **修复路径**：在 `_parse_header()` 末尾加 `_validate_layout()`，
  用**两条硬结构不变量**快速判定并抛 `MetadataError`：
  ① 版本号在实测支持区间（v24 ~ v31）；② 固定记录大小的表能被整除
  （fields/12、parameters/12、images/40、assemblies/64）。
  错误信息点明「版本不支持」+ 实际版本号 + 可用替代路径。
- **故意没把「typeDefinitions 能否铺满 fields」当拒绝条件**：那是
  `_typedef_size` 用来**推断** stride 的启发式，当拒绝条件会**误伤合法输入**
  （实测：`verify_typedef_stride` 第 1 节那三个故意做坏的样本全部在建
  `Metadata` 时就抛错，脚本崩在断言之前）。它继续以 warn 形式留在原处。
- **验证**：
  - `python devtools\verify_typedef_stride.py` → **PASS=22 FAIL=0**，
    新增第 5 节专门覆盖本条（含「快速失败 < 2 秒」「错误信息不是 sqlite」
    「放开版本区间后同一文件能被解析」的反证）。
  - 全部 11 个本机 IL2CPP 游戏重跑：**10 个受支持版本照旧正常**
    （types 数一字不差），v39 那个 **0.1 秒**如实拒绝。
- **反证**：把 `SUPPORTED_VERSION_MAX` 放开到 999，同一文件立刻又能被解析
  （types=64）—— 说明拦下它的确实是版本判定，不是文件读不了。

## 五之二、随机测试新发现的另外两个缺陷（**本次新增修复**）

### C3. `inject_process` 失败时**顺带毁掉了正在用的会话**

- **现象**：已经成功注入 Mono 游戏后，调
  `inject_process(pid=<不存在的 pid>)` → 返回 `ok:false`
  （`unable to find process with pid`），**但紧接着所有 `runtime_*` 工具都报
  「当前没有已注入的运行时会话」** —— 想试一个 pid，结果把在用的会话弄没了。
- **根因**：`state.ensure_runtime()` 走的是「**先断开旧的，再去连新的**」：
  ```python
  old_pid = cur_pid
  _state.close_runtime()          # ← 旧会话在这里就没了
  ...
  sess = attach(target_pid, ...)  # ← 这里才失败
  ```
  于是新目标连不上时，旧会话**已经**被 detach 了。典型的「失败还带副作用」。
- **为什么危险**：这不是「少了一个功能」，而是**破坏性**的 —— 调用方只做了一次
  试探性调用，就丢掉了正在用的注入会话，而错误信息里**没有任何提示**。
  Agent 很可能据此判断「探针坏了」并重启整套流程。
- **修复**：改成「**先连新的，连上了才断旧的**」。新目标连不上时原样保留旧会话，
  并在返回值里带上 `kept_pid` 与
  `hint="原有会话未受影响（仍是 pid=N）…"`，让调用方知道还能继续用。
- **验证**：`verify_mono_runtime.py` §3b 新增 3 条断言 ——
  ① 不存在的 pid 如实失败；② 返回值说明「原会话未受影响」；
  ③ **关键回归**：注入前后 `get_session()` 的 pid 必须一致。
- **反证**：修复前同一段代码 `会话 pid(前)=15940` → `会话 pid(后)=None`；
  修复后 前=15940、后=15940，且失败后 `runtime_class_info` 仍然可用。

### C4. `verify_mono_runtime` 只能跑一次（跑完不收拾游戏进程）

- **现象**：第一次跑通过；**紧接着再跑一次，`launch_game` 直接 `ok:False`**，
  后面几十条运行时断言全部连坐报红。
- **根因**：脚本跑完只调 `S.close_session()` —— 它只 detach（卸载 Hook、断开
  连接），**不结束游戏进程**。留下的 `Archon Soul.exe` 让下一轮
  `launch_game` 命中「已有同名进程在运行」的**故意拒绝**分支
  （Unity 单实例锁，新进程不会加载 mono 模块，只会白等到超时）。
  其他运行时脚本（`verify_mcp_tools` / `verify_mcp_extra`）收尾时都会
  `taskkill /PID <自己 spawn 的 pid>`，只有本脚本漏了。
- **为什么重要**：一条**不可重复**的验收，等同于一条不可信的验收 ——
  在 CI / 连续跑的场景下它必然失败，而失败原因（残留进程）看起来却像产品缺陷。
  本次就是因为这个，一度把它误判成「Mono 运行时坏了」。
- **修复**（两处，缺一不可）：
  1. 开场先清掉**上一轮残留的样本游戏进程** —— 按**精确可执行文件路径**核对
     （`Get-CimInstance … .ExecutablePath`），只结束确实是本样本游戏的那一个 pid，
     **不做按进程名的宽泛清理**（那种写法会误伤同名的无关进程）。
  2. 收尾 `taskkill /F /T /PID <本脚本 spawn 的 pid>`，与另外两个脚本对齐。
- **验证**：连续跑两次，两次都是 **101 项 / 0 失败 / 0 警告**，
  且跑完 `Get-CimInstance -Filter "Name='Archon Soul.exe'"` 为空（无残留）。

### 顺带：动态覆盖率门禁从 **21/38** 补到 **38/38**

- **现象**：`run_all_verify.py` 最后一步的
  `report_tool_coverage.py --strict` 一直不通过。**基线就是红的**
  （已用 `git stash` 回退验证：基线 21/38），不是本次改动引入的。
- **根因**：13 个运行时工具**只有 IL2CPP 侧**验过
  （`verify_mcp_tools` / `verify_mcp_extra` 都用 Garden of Witches），
  该样本一不在本机，那两条脚本整段跳过 → 这些工具长期没有动态调用证据。
- **修复**：这些工具**与引擎无关**（读内存 / 扫特征码 / 按绝对地址挂钩 /
  字段读取），Mono 会话完全能跑。于是
  · `verify_mcp_mono.py` 补 `list_images` 的**工具层**断言
    （AGENTS.md §5.1 点名的唯一一个「只有会话对象调用」的工具），
    并验证 `limit` / `offset` / `pattern` 真的生效（不是死参数）；
  · `verify_mono_runtime.py` 新增 §3b，覆盖
    `inject_process` / `find_hook_target` / `hook_address` /
    `read_memory` / `write_memory` / `scan_pattern` / `read_field_value`。
- **结果**：**38/38**，门禁转绿。
- **非空转细节**（这几条都刻意避开了「看起来绿其实没跑」）：
  · `scan_pattern`：先从**目标模块自己的内存**读 4 字节，再拿它当特征码扫
    同一模块 —— 那些字节一定存在，扫不到才是真坏。**不能**拿 `Memory.alloc`
    的缓冲区当特征码：那段内存在 Frida 自己的页里、不在目标模块内，
    扫不到是**正确**行为（一开始就这么写，假红了一次）。
  · `read_field_value`：先按静态索引挑「真有 `System.Int32` 字段」的类，
    再**逐个试到运行时真能解析出来**为止。只按静态字段数取第一名会空转
    （实测第一名 `DiceBody` 运行时拿不到）。
  · 字段必须挑**基础类型**：一开始挑到引用类型字段
    `m_CancellationTokenSource`，它按 8 字节读是**正确**行为，
    拿它断言 4 字节是测试自己写错。

## 六、一句话结论

原始的 **7 项失败**里只有 **1 项是产品缺陷**（`decompile` 的嵌套类型名谎报），
本机样本齐全、已修复并验证；
**2 项是验收脚本自己用了 Python 3.12 语法**、在 3.10 上根本没跑起来，已修；
**4 项是缺样本**（其中 2 项已改成「与具体游戏无关」从而能真正跑起来，
2 项已改成正确的「无法验证」口径）。
**另加 3 项**随机测试新发现的缺陷：
IL2CPP v39 静默硬解（空转 573 秒）、`inject_process` 失败毁掉在用会话、
`verify_mono_runtime` 不可重复；全部已修并留了回归断言。
动态覆盖率门禁也从基线的 **21/38** 补到 **38/38**。

最终：**通过 40 / 40，断言失败 0，进程崩溃 0，超时 0，覆盖率门禁通过。**
