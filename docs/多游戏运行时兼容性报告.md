## 6. 本轮修复（及各自的验收）

这张矩阵不是一次跑完就完事的快照：**第一轮跑出来的失败**（6 个 IL2CPP 游戏「启动/注入被拒绝」、4 个 `runtime_class_info` 失败、`read_memory` 假成功）逐条定位到根因并修掉之后，才得到上面这份 0 失败的结果。每条修复都有可复现的验收脚本，并做了**非空转反证**（把代码改回旧写法，断言必须报红）。

| 缺陷（第一轮的现象） | 根因 | 修复 | 验收 |
|---|---|---|---|
| 6/9 个 IL2CPP 游戏注入后**游戏当场崩掉**（`0x80000003` in `GameAssembly.dll`），后续工具全部报「没有已注入的运行时会话」 | `GameAssembly.dll` 已加载 ≠ IL2CPP 运行时已初始化：`il2cpp_domain_get()` 此时返回野指针（实测 `0x135`），拿它去 `il2cpp_thread_attach` 触发访问违例，旧代码把它当「可降级的 fallback」吞掉，于是在**未附着的线程**上继续调 il2cpp 接口 | 加 `domainPointer()` 试读指针确认域真的建好了；域没好或附着失败一律**拒绝继续**并返回可重试失败，由 `wait_ready` 每 0.5s 重试 | `verify_thread_attach.py`（源码契约 + 桩对象重试契约 + 真实游戏密集轮询 + `ptr(0x135).readPointer()` 抛异常的反证） |
| `runtime_class_info(name="Transform")` 在 4 个游戏上「未找到类」；在 RIP_nz 上**静默返回了不相干的嵌套枚举**`UnityEngine.RuleTile.TilingRuleOutput.Transform` | 运行时类解析把「嵌套类型」当成「namespace 为空」来判断，而带命名空间的顶层类型（`UnityEngine.Transform`）也满足该条件 | 用 `il2cpp_class_get_declaring_type` 真正判断嵌套；匹配规则改为「完整名 / 显式 namespace + 短名 / 无 namespace 时只匹配顶层」，歧义就拒绝并给 candidates，找不到时给出 hint | `verify_class_resolve.py`（短名/显式 namespace/完整名三方一致 + `State` 歧义 + 不存在的类给 hint + 用 7056 个嵌套类型做反证） |
| `read_memory(address="0x0", size=4)` 返回 `{ok:true, hex:""}` —— **假成功** | Frida 的 `readByteArray` 对不可读地址返回 `null`（不是抛异常），`new Uint8Array(null)` 得到长度 0 的数组 | 显式判断 `null` 与实际字节数，读不到就 `ok:false` | `verify_mcp_tools.py` §12（`0x0` 必须失败且不给 `hex`；`0x1` 走抛异常那条路） |
| `launch_game` 启动游戏后 MCP 服务器**stdout 被游戏日志污染**（实测 30 行，其中一行是合法 JSON 字符串），客户端把它当 JSON-RPC消息用 → `AttributeError: 'str' object has no attribute 'get'` | spawn 用了默认的 `stdio="inherit"`，子进程与服务器共享 stdout，而 stdout 是 JSON-RPC 通道 | 改为 `stdio="pipe"` 并由 Frida 把子进程输出转发到 **stderr** | `verify_spawn_stdio.py`（产品路径用 `pipe`、`inherit` 会泄漏标记、4 MB 洪水不卡死） |
| Mono 游戏 `launch_game` 每次都要**白等满 60 秒**（实测 4 个样本各 62 秒）才如实返回「没有 IL2CPP 运行时」 | 等就绪的预算写死 60 秒，而当时 Mono **没有探针路径**（`agent.js` 只认 IL2CPP），等下去永远不会就绪 | 预算按引擎给（`state.ready_timeout_for`）：有托管运行时探针的引擎（IL2CPP / Mono）60 秒，其余（UE/原生）2 秒。探针补上 Mono 后端之后，Mono 的 60 秒是**真的会就绪**，不再空转 | `verify_runtime_target.py` §8（纯函数 + 端到端确认传下去的 timeout 真的是 2.0/60.0） |

> 反面教材（这一轮踩到的）：第一版修复曾让探针在「未找到 IL2CPP 运行时模块」时表态 `retryable: false`，结果 **8 个 IL2CPP 游戏全部误判**——刚 spawn 完第一次探测几乎必然是这个错误（`GameAssembly.dll` 还没加载完），实测 GoW 的第二次探测才成功。这条误判正是被**这张矩阵**抓出来的（33 → 17 个可用工具），所以「等多久」只能由**引擎**决定，不能由探针在那一刻的观测决定。
