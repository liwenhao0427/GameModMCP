## 一、项目定位

**一句话**：一个 stdio 型 MCP 服务器，把「用游戏自带元数据定位 Hook 落点」这件事
做成 41 个可被任意通用 Agent 调用的工具，支持 IL2CPP / Mono(.NET) / Unreal 三类引擎。

**核心方法论（两段式）**：

```
① 离线：解析元数据 → 类型/字段/方法/token 清单 → 落 SQLite 缓存
② 在线：注入 Frida 探针 → 问运行时「真实字段偏移 / 方法真实地址」
③ 对账：静态 token == 运行时 token  → 证明挂的就是想挂的那个重载
```

这个「token 对账」是整个项目最有价值的设计，也是它与内存修改器的本质区别
（`index.py:772` 的 `runtime_token`、`agent.js:551-553` 的 `il2cpp_method_get_token`、
`README.md:264-268` 的验证结论）。

### 分层架构

```
                    ┌─────────────────────────────────────────┐
                    │ server.py  FastMCP 41 tools（唯一入口）  │
                    └───────────────┬─────────────────────────┘
                                    │  必定返回 {ok, error?} 契约
                    ┌───────────────▼─────────────────────────┐
                    │ state.py  进程级单例会话（隐式上下文）    │
                    │  game_dir / engine / exe / index / runtime│
                    └──────┬───────────────────────┬──────────┘
                           │                       │
              ┌────────────▼─────────┐   ┌─────────▼──────────────┐
              │ engine/  静态分析层   │   │ runtime/  动态分析层   │
              │  discovery 进程/Steam  │   │  session  Frida 生命周期│
              │  pe        纯标准库PE  │   │  agent.js 进程内探针    │
              │  il2cpp_meta  .dat解析 │   │   (59 个 il2cpp 导出)  │
              │  mono_meta   ECMA-335  │   └────────────────────────┘
              │  ue        pak/utoc    │
              │  adapt   ★引擎适配层   │
              │  index   SQLite+句柄   │
              └────────────────────────┘
```

`adapt.py` 是关键抽象：把「IL2CPP 索引轨道式类型引用」与「Mono `#Blob` 签名式类型引用」
的差异收在一处，让 `index.py` 用同一套代码吃两种引擎（`adapt.py:1-22`、
`verify_adapt.py` 就是为证明这一点而存在）。

## 四、冗余与缺陷清单（按严重度）

### P0 —— 会直接误导 Agent 的问题

#### 4.1 `ensure_runtime` 早退忽略 `pid` 与 `spawn`

```python

    if _state.has_runtime():
        return {"ok": True, "reused": True, **_state.summary()}
```

这个早退在函数**最前面**，且在 `pid` / `auto_find` / `spawn` / `launcher_exe` 参数
处理之前。后果：

- `inject_process(pid=B)`：会话已存在（pid=A）时**不会注入 B**，却返回 `ok: true`，
  且返回的 `pid` 是 A。Agent 会以为成功挂上了 B。
- `launch_game(exe=...)`：会话已存在时**根本不会启动游戏**，直接返回 ok。
  `server.py:710-729` 已经把 `target/argv` 拼好并写进返回值，看起来就像启动过。

**建议**：早退条件加上目标一致性判断；`spawn=True` 时永不早退；不一致时
返回明确错误（或先 close 再注入），并让 `inject_process` 回显「实际注入的 pid ≠ 请求 pid」。

#### 4.2 `hook_method` 无法选择重载

`session.py:339-347` 取 `usable[0]`（`il2cpp_class_get_methods` 的枚举顺序），
`hook_method` 的参数里**没有任何**选择重载的手段——`args_type` 只用于解析参数值，

而 `SKILL.md:272-275`（配方 5）明确要求「按 `param_count` 选候选」，
`server.py:592-596` 的 `get_method_source`（现已合并进 `class_detail`）

候选选择改为「param_count 命中优先 → in_module → 第一个」，并在返回里回显

#### 4.7 索引与内存解析器「双份数据」

`class_detail` / `class_hierarchy` / `find_monobehaviours`（已合并进
`find_derived_classes`）**几乎不用 SQL**——
它们只拿一个 `row["idx"]`，然后全部回落到 `self.meta.types[...]` / `m.fields_of()` /
`m.base_chain()` / `m.find_derived()`。真正吃 SQL 的只有
`search_classes` / `search_fields` / `search_methods` / `list_images` / 句柄层。

也就是说：**`types` / `fields` / `methods` 三张表的一部分是为「搜」建的，
而「看」的路径完全绕开了它们**，同时 `Index.open` 在缓存命中时**仍然加载整个解析器**
（`index.py:224` `_load_meta` 在 230 行 digest 校验之前）——这就是
「缓存复用 1.3s」里那 1.3s 的来源（README 自己写了 2.6s vs 1.3s）。

**建议**：把解析结果**全部**落库（含 parent_name、字段类型名、方法返回类型名、
`is_subclass_of` 需要的基类闭包），命中缓存时**不加载解析器**；
这能把缓存命中从 ~1.3s 压到 ~10ms 量级，也让 `class_detail` 不必依赖 `meta`。

#### 4.8 `search_classes(subtype_of=...)` 是 Python 侧全表过滤 ✅ **已修（P1-4，见 §4.8.1）**

`index.py:573-578`：先取全部类型，再对每个类调 `meta.is_subclass_of`（走基类链）。

> ⚠️ **本节被订正过两次，第一次订正本身也是错的，请看完**
>
> **原文**（第一次）称「20,072 类型规模下每次调用都是**秒级**」——**不成立**。
>
> **第一次订正**（2026-10-01）改成「继承过滤根本不是瓶颈，IL2CPP 上甚至为负
> （−7.5 ms），属测量噪声」——**这个结论也不成立**。
> 它来自 `bench_index.py` 的「5 次取最小值」，而**最小值的符号不稳定**：
> 两次跑分别得到 −4.9 ms 与 +14.7 ms。**最小值会挑中噪声里最有利的那一次**，
> 在两条耗时接近的代码路径之间做差，本就不可靠。
>
> **第二次订正：改量分布，不量最小值**（`devtools/bench_index.py` 的
> `[P1-4]` 段，每条路径各跑 12 轮，打印最小/中位/最大）：
>
> | | 最小 | 中位 | 最大 |
> |---|---|---|---|
> | IL2CPP 普通查询 `pattern=''` | 44.0 ms | 47.8 ms | 51.2 ms |
> | IL2CPP `+ subtype_of` | 68.4 ms | 70.8 ms | 80.0 ms |
> | IL2CPP **净增** | **+19.5** | **+23.8** | **+33.1** |
> | Mono 普通查询 | 2.4 ms | 2.6 ms | 4.6 ms |
> | Mono `+ subtype_of` | 4.0 ms | 4.3 ms | 4.7 ms |
> | Mono **净增** | −0.7 | +1.6 | +2.2 |
>
> 结论：**IL2CPP 上继承过滤是一笔真实开销（12 轮符号全为正，+20~33 ms），
> 但远不是「秒级」** —— 相对 48 ms 的基线约 **+50%**。
> Mono 规模小（1,387 类型），落在噪声里。
>
> **根因**（比「Python 侧全表过滤」更具体）：过滤对**每一行**调一次
> `meta.is_subclass_of`（`index.py:711-714`），而它每次都走一遍基类链
> —— 即 **O(行数 × 链长)**。同一个形状也拖慢了
> `find_derived_classes`（实测 **20.5 ms**，`find_derived` 内部同样是
> 对全表逐个 `is_subclass_of`，见 `il2cpp_meta.py:997-1007`）。
> 所以这是**同一个根因的两个出口**，不是两件事。
>
> **订正后的建议**：不必建 `type_ancestors` SQL 闭包表（那要改 schema），
> 更合算的是在 meta 对象上**惰性缓存一张 parent→children 邻接表**，
> 之后 `subtype_of` = 从基类 BFS 出候选下标集合再与行取交集，
> 一次 O(N) 建表 + O(后代数) 每次查询。它同时修好
> `subtype_of` 与 `find_derived` / `find_derived_classes` 两处，
> 且**不需要迁移索引缓存**。
>
> 另有两处引用错误（与性能无关，但同一段里）：原文称「`SKILL.md:254`
> 推荐的正是 `search_classes(subtype_of=..., limit=2000)`」—— 实测
> `SKILL.md` 里 `subtype_of` **只出现在第 111 行**，且**不带 `limit=2000`**。

**建议（订正后）**：收益是「宽查询里省掉一次 O(N×链长) 的 Python 侧过滤」，
量级是**几十毫秒**（IL2CPP），不是「秒级变毫秒级」。
按这个量级决定要不要做 —— 它值 5 行左右的代码，不值一次 schema 迁移。

#### 4.8.1 ✅ **已修（P1-4）**：`subtype_of` 反过来查

**做法**（比原来设想的「SQL 闭包表」更省）：在 meta 上**惰性**建一张

| 其中「算后代集合」首次（含建邻接表） | — | 5.87 ms（此后 2.03 ms） | — |

#### 4.10 危险工具缺 MCP 语义标注 & 参数类型问题

**标注部分 ✅ 已修（P2-5）**。原来的问题是：38 个工具全部只用了
`title` / `readOnlyHint`，而 MCP 这几个语义位的**默认值不是「都关」**：

| 位 | MCP 默认 | 后果 |
|---|---|---|
| `readOnlyHint` | False | — |
| `destructiveHint` | **True** | 不写 = 客户端按「它会破坏东西」处理 |
| `idempotentHint` | False | — |
| `openWorldHint` | **True** | 不写 = 客户端按「它与外部世界交互」处理 |

默认值本身是**保守**的，但用在本项目上全是错的：`search_classes` 只读本地
SQLite，却会被描述成「破坏性 + 开放世界」。

修法是 `server.py` 的 `_ann(title, read_only=..., open_world=..., destroy=...,
idempotent=...)`：**每个**工具都显式表态，且只读工具的「不破坏 / 无副作用」
由 `read_only` 推出来，**写矛盾组合会在导入期直接抛错**
（`read_only=True` + `destroy=True`）。

同时修掉两个**写错的**标注：

| 工具 | 原标注 | 为什么错 |
|---|---|---|
| `drain_events` | `readOnlyHint: True` | 它是「**取走即消费**」—— 事件消费掉就没了，标只读会让客户端以为重试无害 |
| `decompile` / `ue_profile` | `readOnlyHint: True` | 给了 `output_dir` / `output_path` 就会**落盘**（只写自己的产物、可覆盖，所以不算破坏，但不是只读） |

现在的分组（`devtools/verify_tool_annotations.py` 逐项核对，双向一致）：

| 分组 | 个数 | `readOnlyHint` | `destructiveHint` | `openWorldHint` |
|---|---|---|---|---|
| 只读、只读本地文件/SQLite | 17 | True | False | False |
| 只读、但要活着的游戏进程 | 8 | True | False | True |
| 非只读 | 13 | False | 其中 **4** 个为 True | 其中 9 个为 True |

破坏性的 4 个：`write_memory`（写错地址立刻崩）、`eval_script`（任意代码执行）、
`unhook`（不带 id 会全卸）、`drain_events`（消费数据）。

### P2 —— MCP 协议层的机会（这才是「作为 MCP」的优化空间）

实测环境 `mcp 1.26.0`，以下能力**都可用但一个都没用**：

#### 4.11 零 `outputSchema`（结构化输出）—— ❌ **本轮实测后决定：不做**

原判断是「为每层定义 `TypedDict` 并标注返回类型，这是**投入产出比最高**的一项」。
本轮把 `mcp 1.26.0` 的行为逐条量了一遍，**这个判断是错的**，而且照做会**破坏产品**。
下面是量出来的东西（探针脚本已删，结论都进了
`devtools/verify_response_size.py` 与本节）。

**先说会炸的那条**：FastMCP **会拿 outputSchema 校验返回值**
（`func_metadata.py:119-131`：`output_model.model_validate(result)`）。
本项目每个工具都有**两条形状不同的返回路径** —— 成功时字段齐全，
失败时只有 `{ok: false, error, ...}`。于是：

| 注解写法 | 生成的 schema | 实测后果 |
|---|---|---|
| `-> dict`（现状） | `null` | **只返回 text**，不校验、无额外开销 |
| `-> TypedDict`（字段必填） | 属性名 + `required` 齐全 | 少一个字段就 **`ToolError`** → **所有错误返回变成协议错误** |
| `-> TypedDict` + `NotRequired[...]` | 同上（`NotRequired` **被忽略**，仍进 `required`） | 同样全炸。`NotRequired` 在本版本**不可用** |
| `-> TypedDict, total=False` | 属性名齐全、无 `required` | 不炸，但三条新问题（见下） |
| `-> dict[str, Any]` | `{type: object, additionalProperties: true}` | **一个属性名都没有**，等于没说 |

`total=False` 的三条新问题，都是实测出来的：

1. **显式 `None` 直接被拒**：声明成 `int` 的字段，返回 `None` 时
   `ToolError: Input should be a valid integer`。而本项目**真的会**在数值字段上
   返回 `None`（`is_64: None` 表示「没测出来」、`offset: None`）。要绕开就得把
   每个数值字段都写成 `int | None` —— 38 个工具全套改一遍，且以后每加一个字段
   都要记得加，**漏一个就是线上 ToolError**。
2. **静默强转**：声明 `int` 的字段收到 `"3"` 会被 pydantic **转成 3** 并照常返回。
   本项目的契约是「不许编造」，数据被悄悄改型正属于此类。
3. **补 null**：缺失的键会在 `structuredContent` 里被补成 `null`。

**再说代价**：spec 建议（**SHOULD**，非 MUST）「返回结构化内容时同时把 JSON
放进 TextContent」以兼容旧客户端（2025-06-18 Tools §Output Schema），
FastMCP 也确实两份都给，所以 **每个响应会翻倍**。用真实载荷实测：

| 调用（`verify_response_size.py` 可复现） | 现状 text | 加 schema 后线上 | 倍数 |
|---|---|---|---|
| `search_classes('', limit=2000)` | 856,186 B | 1,548,350 B | **1.81×** |
| `search_classes('Player', limit=2000)` | 368,430 B | 679,684 B | **1.84×** |

（「加 schema 后线上」= 该调用的 text 字节数 + 同一 payload 的 compact JSON 字节数，
两个数都是 `verify_response_size.py` 里实测打印出来的：后者就是 FastMCP 会放进
`structuredContent` 的那份。）

也就是说：为了拿到**属性名**这点信息，要把最大的响应从 **836 KB 推到 1.5 MB**，
并且给 38 个工具引入一类新的线上崩溃面（注解与实际返回不一致就是 `ToolError`）。

> **P2-4 落地后的补充**：那个 1.5 MB 现在会被 256 KB 的上限挡住 ——
> 但这不是「P2-1 变可行了」，而是**代价换了个形式**：双份载荷会让同一批查询
> 被截得更狠（实回条数更少、翻页更多），而 `ToolError` 那个崩溃面一点没变。
> 所以 P2-1 的结论不变：**不做**。这也说明「有上限」不等于「可以随便浪费字节」。

**还有一个不能走的路**：手写 `outputSchema` 挂上去、但不返回 `structuredContent`。
spec 原文是 **MUST**：

> Servers MUST provide structured results that conform to this schema.
> Clients SHOULD validate structured results against this schema.

所以这条路不合规（[Tools 规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)；
引文逐字来自[第三方指南](https://mcp.zovo.one/guides/mcp-structured-tool-output)，
规范页本机抓取时中段被截断。另有把这条当校验项的实现：
[mcp-go](https://pkg.go.dev/github.com/mark3labs/mcp-go@v0.55.0/server)、
[IBM/mcp-context-forge#4208](https://github.com/IBM/mcp-context-forge/issues/4208)）。

**根因要说准，别记反**：「失败路径会炸」**不是** MCP 的固有缺陷 ——
规范允许「schema 只描述成功、失败不附结构化内容」。炸的是 FastMCP
**无条件校验 + 无条件附带**。而本项目还有一层自己的问题：失败**不是**
`isError: true`，而是「协议层成功、信封里 `ok: false`」（AGENTS §3.1 的契约），
框架分不出成功与失败，**而 schema 只能有一个**。这才是本项做不了的根因。

**结论**：`outputSchema` **不做**。返回结构继续由 docstring 承载
（它本来就是给人/给模型读的散文，不受 schema 校验约束）。
将来若 `mcp` 支持「只给 schema、不校验、不重复内容」，可以重新评估。

> 这一条是本文件里**唯一一处「原建议被实测否决」**，也是唯一一处
> 「照建议做会破坏产品」的地方 —— 保留在此，是为了让下一个人不要再去试。

#### 4.12 零 `resources` / 零 `prompts` —— 一半已修（P2-2），一半实测否决

`server.py` 里没有任何 `@mcp.resource` 或 `@mcp.prompt`。当前的工作流知识
（`SKILL.md` 511 行：引擎差异、6 个配方、排查表）必须**手动拷进 Agent 的 skill 目录**
（`README.md` 的「让 Agent 加载 skill」一节）。而 MCP 的 `prompts` 能力正是为
「服务器侧提供可复用提示/工作流」设计的，
`resources` 则可以承载索引概况、`UE_CAPABILITIES`、缓存清单等只读信息。

**原建议**（照抄上面的判断）：
- `prompts/get`：把 `SKILL.md` 作为 MCP prompt 暴露（`gamemod-mod-workflow`），
  配参数 `engine` 返回对应路线的裁剪版；这样客户端无需手动拷贝。
- `resources`：`gamemod://session`、`gamemod://capabilities`、`gamemod://cache`。
  同时把「静态层 vs 运行时层」的能力边界做成可订阅资源，
  比塞在 `get_diagnostics` 的一次性返回里更可靠。

##### ✅ 落地情况（P2-2）：只做了 1 个资源，prompts 不做

**先量客户端，再动手** —— 结论与建议书出入很大，两处都记下来：

| 原建议 | 实测 | 结果 |
|---|---|---|
| `prompts` 暴露 SKILL.md | 客户端的 MCP 客户端里 `prompts/*` **零命中**（`dsh-mcp-client` 的请求分发 `switch` 只有 `resources/*` 三个分支），289 个 `@deepseek-ai/dsh-*` 包里**没有** prompts 相关的包 | ❌ **不做** —— 加了也传不到模型面前 |

| `gamemod://cache` | 缓存清单已在 `get_diagnostics` 里 | ❌ 不做（同上） |

所以这一条的结论是：**建议书里点名的那三个资源都是重复出口，真正该做的是
建议书没提的那一个**。原判断「把能力边界做成可订阅资源比塞在
`get_diagnostics` 里更可靠」不成立 —— 那份矩阵本来就不是一次性返回，

它是一个 115 MB 的归档文件，**直接文本搜索没有意义**（整个文件在文本工具眼里
就是一行）。要先解析头部（`struct.unpack("<4I", ...)` 拿 `header_size`/`json_size`，
内容起点 `8 + header_size`），再按需读其中的 JS 文件。

**验收**：`devtools/verify_mcp_resources.py`（23 项）。
其中第 1 条「资源清单**恰好**只有 `gamemod://guide`」是**防重复的门禁** ——

#### 4.13 长任务没有进度与取消 —— ❌ **实测后决定不做（P2-3）**

`open_game`（2.6s）、`launch_game`（spawn 后最长等 60s）、`ue_profile`（多容器 + 清单交叉校验）
都是秒级到分钟级操作，但：

- 没有 `ctx.report_progress()`（FastMCP 支持 `Context`）；
- 工具里没有 `Context` 参数，因此也**无法响应 `notifications/cancelled`**——
  用户取消后，服务器仍会把 `ue_profile` 跑完，并把结果丢进一个没人读的响应里。

**原建议**：给这三个工具加 `ctx: Context`，分阶段 `report_progress`
（找元数据 → 建表 → 写索引 → 完成），并在循环里 `await ctx.check_cancelled()`。

##### ❌ 落地情况（P2-3）：两半都不做，因为够不着

先量客户端、再量 SDK，四条都是「协议里有、这条链路上没有」：

| 协议面 | 实测 | 结论 |
|---|---|---|
| `notifications/progress` | 客户端调工具时只传 `{signal, timeout, toolDefinition}`，**从不传 `onprogress`** → 请求里没有 `progressToken`；而 `report_progress` 无 token 时**直接 return**（实测发 0 条，有 token 时发 1 条作反证）。它还是 `async def`，38 个同步工具**根本调不了** | ❌ |
| `notifications/cancelled` | 客户端**确实**会传 `AbortSignal`，协议面通；但服务器够不着 —— `RequestContext` **没有任何取消字段**、`Context` 没有 `cancelled`；更根本的是 FastMCP 对同步工具是**内联调用**（`func_metadata.py:95` 的 `return fn(**arguments_parsed_dict)`，不开线程、不 `await`），工具体在事件循环上跑到底，**取消通知根本读不到** | ❌ |
| `notifications/message` | 只有通用 SDK 里有，没有任何 `dsh-*` 包消费 | ❌ |
| tasks 扩展 | 客户端桥**直接抛错**：`requires task-based execution, which this bridge does not support` | ❌ |

**原建议里有一个不存在的东西**：`ctx.check_cancelled()` 在这个 SDK 里**没有**
（`Context` 的公开成员里既没有 `cancelled` 也没有 `is_cancelled`）。
所以原建议不是「实现起来麻烦」，是**按它写会直接 `AttributeError`**。

**代价如实记录**：60 秒的 `launch_game` 期间服务器什么都干不了（连 ping 都答不了）。
这是**已知且接受**的行为。触发重新评估的条件很明确：
**客户端开始传 `onprogress`，或开始消费 tasks**。

**验收**：`devtools/verify_mcp_context.py`（20 项）—— 它是**决策门禁**，
不是行为测试（功能没做，没有行为可测）：把上述四条依据钉住，

#### 4.14 没有分页/截断的返回 —— ✅ **已修（P2-4）**

只有 `search_classes` / `search_fields` / `search_methods` 走句柄分页。
以下工具**可以把任意大的数组直接砸进 Agent 上下文**：

- `class_detail(full_name, include_inherited=True)`：大类的 methods/fields 无上限；
- `runtime_class_info`：`methods` 无上限（`UnityEngine.Time` 之类会很长）；
- `runtime_info`：返回全部 94 个映像；
- `find_derived_classes` / `class_hierarchy` / `ue_manifest`：有 limit 但也无句柄；
- `ue_profile`：见 4.5。

**先量清楚「到底多大」**（`devtools/verify_response_size.py`，可复现）。

##### 落地情况（P2-4，2026-06 本轮）

#### 4.15 会话是不可重入的进程级单例

`state.py:125` `_state = SessionState()` 是模块级单例，所有工具共享一个「当前游戏」。
MCP 本身是无状态协议，同一个服务器进程理论上可以被多个会话/多个客户端复用
（DSH GUI、多个 Claude Code 实例、子 Agent）。当前设计下：

- 两个 Agent 同时用 → 互相把对方的「当前游戏」切掉，且没有任何提示；
- 没有 `session_id` 参数，也没有「单会话」的显式声明。

**建议**：至少在做 `select_game` 切换时，把「上一个游戏被切换掉」写进返回的
`notes`/`warning`（`state.py:202` 现在只在**复用**时留痕，切换时静默 `notes.clear()`）；
更进一步可以给每个工具加可选 `session_id`，用 `dict[str, SessionState]` 支持多会话。

#### 4.16 结果句柄跨索引重建不隔离（**错数据**）—— ✅ **已修（P2-4a）**

原判断：`handle = f"{kind}-{self._counter}"`，而 `ResultStore` 是 `Index` 的实例属性，
切游戏后新建 `Index` → 计数器从 0 重来。于是旧游戏拿到的 `"classes-3"`，
在新游戏里会**命中另一份结果集**而不是报错。

**本轮实测确认它是真缺陷，不是隐患**（推理正确，但必须实测才敢下结论）：

```
IL2CPP  search_classes('Player') -> 句柄 'classes-1'，首条 PlayerPrefsController
切 Mono  search_classes('a')     -> 句柄 'classes-1'，首条 __StaticArrayInitTypeSize=26136
再读 IL2CPP 那个句柄              -> ok=True，读出来的是 Mono 的那一条
```

`ok=True` 而数据属于另一个游戏 —— 属「假成功」，是本项目的红线。

**修法**：句柄改为 `{引擎}-g{代次}-{kind}-{n}`
（`ResultStore._EPOCH` 是进程内单调计数，每新建一个句柄表 +1）。
唯一性由**代次**保证；引擎段只为可读性 —— 只带引擎名是不够的，
同一个引擎的两个游戏会撞名。失效时返回 `available_handles` + `hint` 说明原因。

原建议里的 `{engine}-{sha16[:6]}-classes-3` 用的是「游戏指纹」，
那样**同一个游戏重建索引后仍会撞名**；改成「实例代次」才真正隔离。

验收：`devtools/verify_handle_scope.py`（20 项），含**非空转反证** ——
把新句柄的引擎段与代次段剥掉后两者都还原成 `classes-1`，
证明旧格式确实会撞名（否则「两个句柄不相等」这条断言可能只是格式变了而已）。

### P3-2 —— 索引缓存会一直长大 ✅ **已修（先量后改）**

原清单只有一行「缓存目录 LRU/TTL；长期运行的整洁性」，没有实测支撑。
开跑之前先量本机，确认这是个真问题：

```
C:\Users\Administrator\.gamemod\cache
  il2cpp-b6304a75b752e1ac.sqlite   26,356 KB
  mono-27b7ee933801e9b2.sqlite      1,384 KB        总计 27.1 MB / 2 个文件
```

再看键的取法（`index.py`）：缓存名 = `<引擎>-<元数据 sha256 前 16 位>.sqlite`。
**这个键本身是对的**（换游戏、换版本必定重建，不会串数据），但它的副作用是：

> 「玩过多少游戏」**加上**「游戏更新过多少次」，都会**永久**堆在缓存目录里。
> 每次游戏更新换一个新文件，旧文件再也不可能被命中 ——
> 一个 26 MB 起步的纯泄漏，而且**没有任何工具返回报过它占了多少**
> （`get_diagnostics` 以前只报一个路径字符串 `cache_dir`）。

**做了什么**：

| # | 内容 | 为什么这么做 |
|---|---|---|
| 1 | `_CACHE_NAME_RE` 只认 `<引擎>-<16 位十六进制>.sqlite` | 安全第一：缓存目录里可能有用户自己的东西，删文件不可逆 → 宁可漏删不可错删 |
| 2 | `prune_cache()`：上限 **2 GiB**、最近 **4** 个不删、**7 天**内用过的不删；只删最久没用的 | 刻意留宽。误删的代价是重解析 0.5~12 秒，多留的代价只有 26 MB；5 个游戏的 ~130 MB 永不被碰 |
| 3 | 命中缓存时 `_touch` 刷新 mtime | sqlite 的**读**不改 mtime —— 不 touch 的话，天天在用的缓存会被 LRU 当成「最久没用」先删掉。这是 LRU 正确性的**前提** |
| 4 | `diagnostics` 的 `cache_dir` → `cache{dir,files,total_bytes}`；`index_info` 加 `cache` 与**真删了才出现**的 `cache_evicted` | 看得见。没删就不给字段，不制造恒定噪声（§契约） |

**验收**：新增 `devtools/verify_cache.py`（**54 项 / 0 失败**，只需 Mono 样本）。
「安全」放在第 1 节；所有删除类断言都在临时目录里做，真实缓存目录**只读**
（统计 + 默认护栏跑一次 prune + 复查文件数与总量未变）。
三处脚本内反证：放宽正则会误删（证明安全断言非空转）、`min_age` 调到极大则一个都删不掉
（证明「会删」非恒真）、`min_keep=0` 必须真的删光（专钉 `files[-0:]` 是**整个列表**、
会让护栏把全部文件都「保护」起来的反向 bug）。

**顺手抓到自己的一个「报告说谎」**：`cache_evicted.reason` 一开始写死模块默认上限，
而调用方可以传别的上限 —— 用 1 字节上限触发清理时，报告却写「超过 2147483648 字节」。
现在 `prune_cache` 返回**本次实际生效**的边界，报告只用真值，并加断言钉住。

**为什么不加「清缓存」工具**：清理是纯派生数据的维护动作，`open_game` 每次都做，
Agent 没有独立消费场景；想立刻腾空间直接删目录即可（代价只是重解析）。

### 4.17 冗余代码模式（结构性）

`server.py` 里下面这段出现了 **10 次**：

```python
res = st.runtime.xxx(...)
return res if res.get("ok") else _err(res.get("error", "..."), **{
    k: v for k, v in res.items() if k not in ("ok", "error")})
```

`_ok` / `_err` 的 `try/except → _err` 也重复了 41 次。

**建议**：一个装饰器收口：

```python
def tool_result(fn):
    @functools.wraps(fn)
    def wrapper(*a, **kw):
        try:
            res = fn(*a, **kw)
        except Exception as exc:
            return _err(f"{fn.__name__} 失败：{exc}")
        if isinstance(res, dict) and "ok" in res and not res["ok"]:
            return _err(res.get("error") or "未知错误",
                        **{k: v for k, v in res.items() if k not in ("ok", "error")})
        return _ok(**(res or {})) if not (isinstance(res, dict) and "ok" in res) else res
    return wrapper
```

省下约 300 行样板，也顺手统一了 §4.11 需要的返回类型声明位置。

### 4.19 P1-3b：先量前提 → **否决**（不改 schema）；并修掉「载入失败被降级」

那就先把前提量出来（本机 IL2CPP，20,072 类型 / 17 MB 元数据）：

| 事实 | 实测值 |
|---|---|

1. **半量修复等于零。** `search_classes` 需要解析器只因 `parent` 一个字段；
   但「只存 `parent_name`」省不下任何东西 —— 紧接着的 `class_detail`
   仍要解析。解析是**全有或全无**，所以「`parent_name`/`field_type` 入库」
   这种**按列拆的清单本身就误导**：这两列不能分别计价。
2. **完整修复要动分层。** 要让那 7 个查询都不解析，`class_detail`
   （遍历 `fields_of`/`methods_of`）、`class_hierarchy`（`base_chain`）、
   `analyze_dependency`、`_direct_children` 等 **10 个**函数都得改成完全由
   SQLite 驱动 —— 等于在索引层**再实现一遍继承语义**，而 AGENTS.md §3
   要求引擎差异只出现在 `adapt.py`。两份继承语义互相漂移，正是本项目
   反复吃亏的那类错误（错数据 + 无提示）。
3. **省下的是「每次 `open_game` 一次」的 440 ms**，不是每题；而缓存命中
   本身已经是 5~20 ms。

**验收**：新增 `devtools/verify_lazy_meta.py`（**16 项断言 / 0 失败**），
它同时是回归门禁（命中不解析不许退化、解析每次 open 只发生一次）与
决策门禁（那张表空了就提醒回来订正结论）；含三处非空转反证，
其中一处是**把旧写法原样搬回来必须报红**。

**顺手捞到的真缺陷（已修）**：写计数替身时把 `_load_meta`
（`staticmethod`）的签名搞错了，于是每次调用都抛 `TypeError` ——
结果 `search_classes` **一声不响**地返回 `ok: true` + 200 行 `parent: null`。
根因是 `_resolve_parent` / `_resolve_param` 把 `self.meta`（惰性载入，
**真的会失败**的那一步）放进了 `try/except Exception` **里面**，
于是「元数据载入失败」被降级成「这些类没有基类」。这撞在 AGENTS.md §2.3
（不许假成功）上，而 `server.py` 每个工具本来就包了
`try/except → ok: false`，异常抛出去就是诚实的错误。
修法只有一行：把 `m = self.meta` **提到 try 之外**。
教训值得单独记一笔 —— **这条缺陷是「写错的测试替身」捞出来的**：
替身坏掉之后，产品代码没有报错，而是安静地给了一份看起来正常的答案。

### 追加发现：`hook_method` 的重载盲选（已修，附验证状态）

`session.py` 原本 `chosen = usable[0]` —— 在多个同名重载里**盲取第一个**。
危险之处在于它不是「失败」，而是「成功但挂错」：Hook 装得上，
直到很久以后数据对不上才暴露，极难排查。

修法（`_select_overload`）——**拿不准就拒绝，不猜**：

| 传入 | 行为 |
|---|---|
| `token="0x06000484"` | 按 token 精确匹配（**首选**；大小写/`0x` 前缀已归一化） |
| `param_count=1` | 按参数个数匹配；仍有多个 → 报歧义并提示改用 token |
| 都没给、候选唯一 | 直接挂（简单场景不受影响） |
| 都没给、候选多个 | **拒绝挂载**，返回候选清单 + `hint` |
| token/param_count 无匹配 | 拒绝，并列出可用的 token / 参数个数 |

**验证状态（如实记录）**：

- ✅ **单测**：`_select_overload` 7 种分支逐一验证通过（唯一候选 / token 命中 /
  `param_count` 命中 / 多候选拒绝 / token 不存在 / 参数个数无匹配 / 归一化）。
- ✅ **静态**：签名确认 `token`（默认 `''`）与 `param_count`（默认 `-1`）已暴露。
- ✅ **e2e 通过**（`verify_mcp_tools.py` §11b，8 条断言全绿）：
  靶子选 **`System.String.Concat`** —— 实测运行时已加载、**6 个重载全部可挂**，
  且天然含两种情形（`param=4` 唯一可区分；`param=3` 与 `param=1` 各有 2 个）：

  | 断言 | 实测结果 |
  |---|---|
  | 多候选且未指定 → 拒绝而非盲挂 | ✅ `ok=False`，提示必须给 token 或 param_count |
  | 按 token 指定 → 挂上的就是它 | ✅ 故意选**最后一个** `0x0600026f`，命中即非「取首个」 |
  | `chosen.token` 在静态元数据中存在 | ✅ `0x0600026f` ∈ 6 个静态 token |
  | `param_count=2`（唯一）→ 参数个数相符 | ✅ chosen=`0x0600026c` param=2 |
  | `param_count=3`（有 2 个）→ 报歧义 | ✅ 拒绝并提示「改用 token 指定」 |
  | 不存在的 token → 拒绝 | ✅ 列出可用的 6 个 token |
  | 无重载方法仍可直接挂 | ✅ `Time.get_frameCount` 走简单路径 |

  该脚本由 65 项升至 **78 项通过 / 0 失败 / 0 警告**。

- 📌 **选靶子的教训**：最初选的是 `BodyPart.Visualize`（静态元数据里确实有 2 个重载），
  但它在运行时**从未被加载** → `find_hook_target` 返回「未找到类 BodyPart」。
  那测的是「游戏当前场景加载了什么」，**不是产品行为**。
  选 e2e 靶子必须挑「运行时确实存在」的类（核心库类型如 `System.String` 最稳）。

### 追加发现：`total` 谎报（本轮新发现并已修）

用动态覆盖率垫片（`devtools/_cov/sitecustomize.py` + `report_tool_coverage.py`）
统计各工具真实返回体大小时，发现 `find_derived_classes` 有**契约违规**：

```
find_derived_classes(base_full_name="UnityEngine.MonoBehaviour", limit=5)
  → total = 5          ← 谎报
  → 无 returned / 无 has_more
真实派生类总数 = 644
```

`total` 被写成「截断后的条数」，且**根本没有** `has_more`。
后果与 §3.1 第 5 条要防的正好相反：Agent 会以为
「这个游戏只有 5 个 MonoBehaviour 脚本」，从而漏掉 99% 的目标。

已修为：`total` = 匹配总数，新增 `returned` 与 `has_more`，
截断时附 `note` 说明。**全量扫描实测只要 17 ms（IL2CPP 20,072 类型）/
2 ms（Mono 1,387 类型）**，所以不存在「为了性能牺牲正确性」的理由。

顺带纠正一个读数：`find_derived_classes` 的返回体此前测得 242 KB，
那是**测试自己传了 `limit=5000`**；默认 `limit=200` 时只有 24.4 KB。
所以它不是「返回超大结果」的反例 —— 这也是为什么看覆盖报告时
必须同时看调用参数，不能只看字节数。

**同类缺陷还有第二处**：`class_detail` 的 `derived_count` 写死了
`find_derived(..., limit=200)`，于是

```
class_detail("UnityEngine.MonoBehaviour")   # Garden of Witches (IL2CPP)
  → derived_count = 200        ← 谎报
  → derived 列表 50 条，且无任何截断标志
真实派生类总数 = 1548
```

两个字段都在撒同一个谎，根因也一样：**拿「取回来的条数」当「总数」**。
已一并修为全量统计 + `derived_returned` / `derived_has_more`，
并在 `verify_mcp_tools.py` 里对 1548 这个真值加了断言（防止回退成 200）。

> 注：Mono 样本 Archon Soul 的 `SpellEffect` 只有 124 个派生类，
> 没触发 200 的上限，所以**只看 Mono 样本会漏掉这个 bug**。
> 这类「截断类」缺陷必须拿 IL2CPP 样本（20,072 类型）才暴露得出来。

### 追加发现：静态覆盖率检查会「高估」

`verify_tool_coverage.py` 只看工具名有没有出现在脚本里，因此把
`sess.hook_method(...)`（**会话对象**调用，不是 MCP 工具层）也算成覆盖。
于是它报「38/38 全部覆盖」，而带垫片实测只有 **30/38**。
首轮报 0 的这 8 个工具，原因其实是两类：

```
hook_method / hook_status / launch_game / read_memory /
runtime_info / scan_pattern / write_memory      ← 7 个：垫片的锅
list_images                                     ← 1 个：真的没测到
```

**7 个是「记录工具自身有 bug」造成的假缺口**：垫片只挂了
`import gamemod_mcp.server`，漏了 `from gamemod_mcp import server as S`
这种写法（`verify_mcp_tools.py` 正是这么导入的），
所以那批调用一条都没记下来。修掉垫片后立刻回升到 **37/38**。

**剩下 1 个（`list_images`）是真缺口**：只有一个会话对象调用，
工具层从没跑过。补上工具层断言（含「pattern 无命中时如实返回 0」的反例）后到 **38/38**。

> 教训：**「测量工具」本身也要被验证**。否则垫片静默漏记，
> 会把「没有数据」误读成「已经覆盖」，也可能反过来冤枉 7 个工具。
> 两种情况都无法用静态检查发现 —— 只有把数字跑出来、逐个核对原因才分得清。

现在分工明确：

| 检查 | 手段 | 能回答 |
|---|---|---|
| `verify_tool_coverage.py` | 静态扫源码 | 哪个工具**没人写测试** |
| `report_tool_coverage.py --strict` | 运行时垫片 | 哪个工具**真的没被跑过** |

> 只有后者能当门禁。前者是「补测试」的导航图。

### 追加发现：`verify_index.py` 会清空**共享**的测试缓存目录（本轮新发现并已修）

`devtools/verify_index.py` 为了「强制走完整构建路径」，原本执行的是：

```python
CACHE = str(samples.CACHE_TEST)      # ← 所有脚本共用的 .cache-test
shutil.rmtree(CACHE, ignore_errors=True)
```

它清掉的是**全脚本共用**的 `.cache-test/`，后果有二：

1. **会删掉别的脚本放在那里的文件** —— 本轮实测就删掉了一个待用的脚本
   （`Move-Item` 到 `.cache-test/` 暂存，跑完 `verify_index` 后文件消失）。
2. **会清空动态覆盖率的日志** `.cache-test/tool_calls.jsonl`（同一个目录）。
   当前恰好没有「只被更早脚本覆盖」的工具，所以当时 39/39 仍能通过，
   **把问题掩盖了**；但只要存在那样一个工具，就会表现为
   「明明跑过却报未覆盖」的**假红**，而且是间歇性的、极难排查。

已改为使用**本脚本专属**的子目录（同样达到「强制完整构建」的目的）：

```python
CACHE = str(samples.CACHE_TEST / "verify_index")
```

验证方式：在 `.cache-test/` 放哨兵文件与假覆盖日志，跑完 `verify_index`
后两者都还在（实测通过）。教训：**多个脚本共用目录时，
谁都不许 `rmtree` 整个目录** —— 「我只想清自己的缓存」必须用子目录表达。

### 一句话总结

**优点**：方法论扎实（元数据 + token 对账）、契约严格（永不假成功）、
`adapt.py` 抽象干净、验收脚本对着**第三方地面真值**跑——这三条在同类项目里很少见，
应作为不可退让的设计底线。

**主要问题**：不在解析算法，而在**工具层与文档层的"最后一百米"**：
`ensure_runtime` 的静默早退、`instructions` 里关于偏移/RVA 的错误描述、
`hook_method` 无法选重载——这三处会直接让 Agent 拿到错误结论却以为成功
（均已修）；以及作为 MCP 服务器，**四个协议面查完了**：
`resources` 做了（只做那一个不重复的，§4.12），
`outputSchema`（§4.11）、`prompts`（§4.12）、`Context`/tasks（§4.13）
三个都经实测否决。

**最新的一条教训**（P2-1、P2-2、P2-3 与 P2-4 一起给出的）：
**「协议能力没用到」不等于「应该去用」，也不等于「照建议书说的那几样去做」**。
本节原来把 `outputSchema` 称作「投入产出比最高」，实测后发现它会引入新的
线上崩溃面、还把响应翻倍到 1.5 MB —— 而同一轮量出来的真问题（836 KB 的响应）
本来是记录错的 242.9 KB；
P2-2 更直接：建议书点名的三个资源**全是既有工具的第二出口**，
真正该做的（`gamemod://guide`）它一个字没提，而它力推的 `prompts`
在这个客户端里根本传不到模型面前；
P2-3 最彻底：建议书让写的 `await ctx.check_cancelled()` 在 SDK 里**不存在**，
而「取消」看着只是加个参数，实际是**结构上不可达**（同步工具占满事件循环，
连取消通知都读不到）。
**先量，再排优先级** —— 量到 SDK 和客户端那一层，而不是量自己的代码。
这一点在本项目已经反复应验。

**后续（P3）把这条教训又用了一次**：P3-1 那份死代码清单**自己腐坏了**
（6 条判定是错的，包括「说死代码其实在用」和「说在用其实早没了」），
所以是**当轮重新数引用数**才动手；P3-2 的「缓存 LRU/TTL」原来只有一句
没有实测的断言，先量出「27.1 MB / 2 个文件 + 键 = 元数据 sha256 ⇒
每次游戏更新漏一个 26 MB 的文件、且任何返回里都看不见」才确认值得改。
**清单和文档和死代码一样会腐坏**，唯一可靠的做法是当轮重新量。

**最后一项 P1-3b 给出了这条教训的第三种结局**：前两种是「量完确认该做」
（P3-2）与「量完确认清单错了」（P3-1），这次是 **「量完发现不该做」**。
前提真的成立（缓存命中后的第一题确实会逼出解析器、每次 open 一次、
IL2CPP ~440 ms），所以它不是「收益不存在」，而是**代价与风险不成比例**：
解析是全有或全无（半量入库省不下任何东西），完整修复要在索引层再实现
一遍继承语义（违反 AGENTS.md §3），而省下的只是每次 `open_game` 一次。
**「否决」也是结论，而且必须把依据钉在脚本里**（`verify_lazy_meta.py`），
否则下一个人会把同一份清单再推一遍。修 P1-3b 前提时顺手捞到的
「载入失败被 `except Exception` 降级成『这些类没有基类』」还补了一个
更实用的观察：**写错的测试替身能捞出真缺陷** —— 替身坏掉之后，
产品代码没有报错，而是安静地给了一份看起来正常的答案。

**而这一轮最值得单独记的一条，来自「文档实时更新」这件事的尽头**：
把仓库里的文档全部改对、门禁全绿之后，**Agent 真正读的那份文档却不在仓库里**。
`~/.dsh/skills/gamemod-mod/SKILL.md` 这份副本落后仓库 **139 行 / 8,897 字节**，
开头第一句还在教「动手前第一步永远是 `detect_games()`」—— 一个 P0 就删掉的工具。
于是出现了本项目最典型的失效形态：**「修好的那份」不是「被读的那份」**。
它现在由 `verify_tool_inventory.py` 第 9 节卡着（副本存在就必须与仓库逐字节相同，
不存在则记为「无法验证」并跳过），并且这条断言**先失败过再转绿** ——
红→绿是当场取证的自然实验，不需要另外构造反证。
