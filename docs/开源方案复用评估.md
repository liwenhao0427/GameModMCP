# 开源方案复用评估：反编译与注入

> 结论先行：**注入已经站在开源之上（继续用 Frida，不要换）；
> 反编译是一个真实的缺口，建议薄封装 `ilspycmd`；
> IL2CPP 元数据解析建议继续自研，不引入 Cpp2IL / Il2CppDumper。**

本文回答三个问题：
1. 这两件事**现在是怎么实现的**？
2. 有没有成熟开源方案可以**直接复用**？
3. 哪种方案**更合理**？给出取舍依据，而不是拍结论。

评估时点：2026-04（文中"实测"数字均为本次在本机跑出来的，非引用他人结论）。

---

## 1. 现状：我们现在到底怎么做的

### 1.1 注入 —— 直接调 Frida，没有自研注入器

注入这件事我们**没有自己造轮子**，用的是 [Frida](https://frida.re)。

`src/gamemod_mcp/runtime/session.py`：

| 位置 | 调用 | 作用 |
|---|---|---|
| `session.py:507,512` | `frida.get_local_device()` → `device.attach(pid)` | 附着到已在运行的进程 |
| `session.py:575,581` | `device.spawn(argv, cwd=...)` | 以挂起态启动，抢在初始化前 |
| `session.py:526,589` | `session.create_script(agent_source())` | 注入我们的探针 JS |
| `session.py:613` | `device.resume(pid)` | 探针就位后再放行 |

也就是说：**进程附着、spawn、脚本注入、符号解析、内存读写这些"脏活"全部外包给 Frida**，
我们只写业务逻辑（探针 `agent.js`）。

`agent.js`（1195 行 / 48.4 KB）用的**不是**逆向出来的结构体偏移，而是
**IL2CPP 官方导出的 C API**：

- 用到 **60 个不同的 `il2cpp_*` 导出函数**，例如
  `il2cpp_field_get_offset`、`il2cpp_method_get_token`、
  `il2cpp_class_get_methods`、`il2cpp_domain_get`、`il2cpp_thread_attach`。
- 通过 `mod.findExportByName(nm)`（`agent.js:265`）动态解析符号。

这一点很关键：**依赖官方导出 API 意味着不随 Unity 内部结构变化而失效**。
代码里确实有少量"回退布局"（`agent.js:117-122`，如
`FIELDINFO_OFFSET_FALLBACK = 0x18`、`METHODINFO_POINTER_OFFSET = 0x00`），
但注释明确写了是「未经验证，仅在官方导出缺失时启用」，
并且会把启用的回退记录进 `fallbacks` 上报。

**评价：这块架构是对的，没有重复造轮子，也没有脆弱的猜测。**

### 1.2 反编译 —— **根本没有实现**

这是本次评估最重要的发现。全仓库搜索 `ILSpy|ilspy|decompil|反编译|dnSpy`，
在 `src/` 下只有 **3 处命中，且全部是 docstring 里的一句建议**：

| 位置 | 内容 |
|---|---|
| `engine/adapt.py:249` | `"可直接用 ILSpy/dnSpy 反编译拿到接近源码的 C#"` |
| `engine/discovery.py:581` | 注释：`# Agent 拿到它就能直接读/反编译，不用在 160 个 dll 里猜` |
| `engine/state.py:132` | `"mono": "Mono (Unity JIT / .NET) — 逻辑在托管 dll 里，可直接反编译成 C#"` |

**没有工具、没有函数、没有任何代码去调用反编译器。**
我们做的是「告诉 Agent：你自己去装个 dnSpy 看吧」。

这对 Mono 游戏尤其可惜 —— `inspect_game` 已经把 `Assembly-CSharp.dll` 找出来交给 Agent 了，
只差最后一步。

## 2. 候选开源方案

### 2.1 反编译方向

| 方案 | 许可 | 形态 | 关键实测/事实 |
|---|---|---|---|
| **ILSpy / `ilspycmd`** | MIT | .NET 全局工具，CLI | 本机已装 9.0.0.7889，**可直接用** |
| dnSpy / dnSpyEx | MIT | GUI | 已停止维护（原版）；Ex 仍在更新。**无 CLI**，难以自动化 |
| JetBrains dotPeek | 专有免费 | GUI | 无 CLI，不适合 MCP 调用 |
| ICSharpCode.Decompiler (NuGet) | MIT | 库 | ILSpy 的引擎，但要从 C# 调 |

**`ilspycmd` 实测（本机，Archon Soul 的 `Assembly-CSharp.dll`）**：

```
输入: Assembly-CSharp.dll (1115 KB)
命令: ilspycmd -o <out> -p <dll>
耗时: 4.7 秒
产出: 855 个文件, 合计 2.14 MB C# 源码
样例: ActionCondition.cs / AddCharacterNameToTextKey.cs / ...
```

4.7 秒、产出真实可读的 C#，一个进程调用解决。**这个缺口补起来成本极低。**

### 2.2 注入方向

| 方案 | 许可 | 是否适合我们 |
|---|---|---|
| **Frida**（现用） | wxWindows/LGPL 类 | ✅ 已在用，成熟，跨平台 |
| **[frida-il2cpp-bridge](https://github.com/bfloat16/frida-il2cpp-bridge)** | MIT | ⚠️ 见下 |
| BepInEx / MelonLoader | LGPL / Apache | ❌ 是**给玩家装 Mod 的框架**，不是给 Agent 做分析的工具链。要在游戏侧预置 loader，与"不修改游戏、纯外部分析"的定位冲突 |

`frida-il2cpp-bridge` 值得单独讨论，因为它是"Frida + IL2CPP"这个组合的最流行封装。
它的官方 README 写明：

> **Platforms**: Android, Linux, Windows, iOS, macOS are supported.
> **However, only Android and Linux are "tested": expect breakage if you are using another platform.**

它的**测试基础设施只跑 Linux x86_64**（依赖 `clang`/`make`/Docker，
`make assemblies` 自动下载 Unity 编辑器构建 IL2CPP 测试程序集）。

对我们意味着什么：**我们 100% 在 Windows 上工作，而它明确说 Windows「expect breakage」、
且自己的 CI 完全不覆盖 Windows。** 它提供的能力（枚举类、hook 方法）
我们现在用官方 `il2cpp_*` 导出已经实现了，并且有
`verify_il2cpp_runtime.py`（静态 token ↔ 运行时 token 交叉验证）为正确性背书 —— 那套验证是**对着真实游戏**跑的，
换成 bridge 就要重做一遍验证，收益却是负的（引入一个在目标平台上未经验证的依赖）。

### 2.3 IL2CPP 元数据解析方向

| 方案 | 许可 | 支持版本 | 是否能替代我们 |
|---|---|---|---|
| **Cpp2IL / LibCpp2IL** | MIT | 元数据 **v24–v27**（= Unity 2018 起） | ❌ 版本覆盖不足 |
| Il2CppDumper | MIT | Unity 5.3 – **2022.2** | ❌ 同上，且是独立 exe |
| 本项目 `il2cpp_meta.py` | — | **v24 – v31**（已实测 v31） | ✅ |

**这是本次评估第二个关键发现。**

Cpp2IL 的 `README_CORE.md` 原文：

> These are used to determine which il2cpp metadata version to use
> (**24.0 through 24.5, and 27.0 through 27.1 are currently supported, i.e. Unity 2018 and up**)

Il2CppDumper 的 README：

> Supports Unity **5.3 - 2022.2**

而我们的主力样本 Garden of Witches 是 **metadata v31**：

```
$ python -c "...Metadata(...global-metadata.dat)..."
[gamemod] INFO 解析类型 20,072 个
[gamemod] INFO 解析方法 139,501 个
version = 31
types = 20072
```

`il2cpp_meta.py` 的 docstring 明确写了 v31 的 `Il2CppTypeDefinition` 是 88 字节
（v24–v29 是 92）、`methods` 记录是 36 字节（更早是 32），
并记录了按错误偏移解包会「方法数/字段数互换」这个隐蔽坑。

**结论：这两个工具在我们要处理的版本上都够不着。**
换过去等于把已实测 100% 正确的解析器，换成一个对新版本无能为力的。
况且 Cpp2IL 明确说明「生成的方法**没有函数体**（只有 stub）」，
Il2CppDumper 也只能恢复 DLL「except code」——
它们给不出我们真正想要的「方法里的逻辑」，
而这恰好是我们用 dump + 运行时对账来补的。

## 3. 建议

| # | 事项 | 建议 | 理由 |
|---|---|---|---|
| 1 | 注入 | **继续用 Frida，不换** | 已站在成熟开源之上；`frida-il2cpp-bridge` 在 Windows 上自认不可靠且 CI 不覆盖 |
| 2 | IL2CPP 元数据解析 | **继续自研，不引入 Cpp2IL / Il2CppDumper** | 我们支持到 v31，它们只到 v27 / 2022.2 |
| 3 | **反编译** | **新增薄封装 `ilspycmd`**（见下） | 当前完全缺失，而成本仅 4.7 秒/次，MIT 许可，本机已可用 |
| 4 | Mono DummyDll | **暂不做** | 只有 IL2CPP 才需要"先造 DLL 再反编译"；Mono 游戏直接有真 DLL |

### 3.1 如果做 #3：设计约定

补这个能力时应遵守本项目既有契约（`AGENTS.md` §3.1）：

- **只加一个工具**，不要 `decompile_assembly` + `decompile_class` + `decompile_method` 三个（§3.3 单一职责/不许让 Agent 猜）。
  建议一个 `decompile`，用 `full_name` / `type_name` / `output_dir` 参数区分粒度。
- **外部依赖要显式报告缺失**，不能假成功。`ilspycmd` 不是运行期依赖
  （`requirements.txt` 只该有 `mcp` + `frida`），所以要：
  `get_diagnostics` 报 `decompiler.available`，工具在缺失时返回
  `ok: false` + `error` + 安装指引，而不是抛异常。
- **输出体积要设上限**。实测一个 1.1 MB 的 dll 出 2.14 MB 源码、855 个文件；
  大游戏会爆。必须有 `output_dir` 落盘 + 返回文件清单与总数，
  **不要**把源码塞进工具返回值。
- **要补验收断言**（§5），并且真值可以用「反编译产物里能找到已知类名/方法名」这种可核查的东西。

---

## 4. 一句话总结

- **注入**：已经复用了最好的开源方案（Frida），并且只用官方 `il2cpp_*` 导出，架构无需改。
- **反编译**：**没有实现**，是一个真实缺口；`ilspycmd` 是最合理的补法（MIT、4.7 秒、本机可用）。
- **元数据解析**：自研是**必要**的而非重复劳动 —— 成熟开源方案都停在 metadata v27 / Unity 2022.2，
  而我们的样本是 v31。
