# 「最后一公里」：AI 自动操作游戏 + Mod 自动验收 —— 调研与思路

> **结论先行**：本项目的「最后一公里」缺口**不是缺截图，而是缺「主动读写游戏状态」的能力**。
> 现有工具能让 Agent **看懂**游戏（定位类/字段/方法、Hook、观察调用），
> 但**不能主动让游戏做一件事、也不能把「改完了」变成一句可证伪的结论**。
> 补法应顺着本项目既有的「元数据优先」哲学，做成**对象层 → 动作层 → 验收层**三级，
> 而不是去追像素与图像识别 —— 后者既是我方最弱的地方，也是同类项目公认
> **不能当判据**的东西（`podium-mcp` 源码原话：*Screenshots are NEVER an oracle.*）。
>
> 本文是**调研 + 思路**，并随执行进度更新。**V0（真机验证 liveness）与
> V1（`set_field_value`）已完成并全绿**，见 §5；V2 起为待做。
> 落地涉及 `AGENTS.md` §4「五处同步」，需先确认范围（见 §7）。

调研时点：2026-10。文中「本机实测」均为本次在本机跑出来的，不是引用他人结论。

## 2. 本项目现状：能看懂，但不能动手

把现有 38 个工具按「Agent 想做的四件事」摆开，缺口一目了然：

| Agent 想做的 | 现有工具 | 评价 |
|---|---|---|
| **知道**游戏里有什么 | `search_*` / `class_detail` / `runtime_class_info` | ✅ 强项，全项目最扎实的部分 |
| **观察**游戏在做什么 | `hook_method` / `drain_events` / `read_field_value` | ✅ 可用，但**被动**：只能等游戏自己调用 |
| **让**游戏做一件事 | ❌ **没有** | ❌ **缺口 1**：`invoke` 只能靠 `eval_script` 手写 |
| **判定**「改对了没有」 | ❌ **没有** | ❌ **缺口 2**：结论留在 Agent 脑子里，不是可证伪的证据 |

还有两个具体痛点：

- **拿不到对象的指针。** `read_field_value` / `write_memory` 都要 `instance=`，
  而拿 `instance` 的**唯一**现成办法是「Hook 一个恰好会收到该对象的函数，从 `args[0]` 捡」。
  想读一个单例的字段，得先赌对「哪个方法会被调用」—— 这是**碰运气**，与本项目哲学相悖。
- **`read_field_value` 没有对称的写入口。** 只能 `write_memory(address=实例+偏移, hex)`，
  得自己算偏移、自己按宽度编码。读有「按字段名自动算偏移」的便利，写却没有。

### 2.1 探针里已经有「绑好但从未调用」的动作原语

这是本次调研最实用的一个发现。`agent.js` 已经把下列函数**解析并包装成 `NativeFunction`**，
但**全文搜不到任何一处真正调用它们**（本机实测：调用次数均为 0）：

| 探针已绑定的函数 | 用途 | 探针内实际调用次数 |
|---|---|---|
| `il2cpp_runtime_invoke` | **主动调用任意托管方法** | **0** |
| `il2cpp_object_new` | 创建对象 | **0** |
| `il2cpp_type_get_object` | 类 → `System.Type` | **0** |
| `il2cpp_field_static_get_value` | 读静态字段 | **0** |
| `il2cpp_class_get_method_from_name` | 按名字取方法 | **0** |

也就是说：**动作层的地基已经铺好了，只是没有出口。**
按 `AGENTS.md` §3「`agent.js` 里的能力必须有对应的 MCP 出口；没有出口的函数是死代码」，
这 5 个恰好是「该补出口」而不是「该删」—— 它们正是缺口 1 所需。

## 3. 关键技术可行性（本次本机实测，不是推测）

### 3.1 找活对象实例：**可行**（这是解锁一切的前提）

先排除一个常见误解：**不存在** `il2cpp_class_get_instances` 这种「按类直接列实例」的导出。
本机对 5 个真实 IL2CPP 游戏逐个核对了 PE 导出表：

| 游戏 | 导出总数 | `il2cpp_unity_liveness_*` | `gc_heap_foreach` | `capture_memory_snapshot` |
|---|---|---|---|---|
| Dave the Diver | 371 | **4/4** | ❌ 无 | ✅ 有 |
| Pass The Fear | 386 | **4/4** | ❌ 无 | ✅ 有 |
| PathOfIdle | 386 | **4/4** | ❌ 无 | ✅ 有 |
| Echoes of Mystralia | 386 | **4/4** | ❌ 无 | ✅ 有 |
| Everything is Crab | 371 | **4/4** | ❌ 无 | ✅ 有 |

正确路径是 **Unity 自家内存分析器用的 GC liveness 导出族**：
`il2cpp_unity_liveness_allocate_struct` / `_calculation_from_root` / `_finalize` / `_free_struct`。

这不是我猜的路线：`frida-il2cpp-bridge` 的 `gc.choose(klass)` 就是这么实现的，
其源码注释写着 *"This variant reads GC descriptors"*，
而它的 `Il2Cpp.memorySnapshot` 走的是 `il2cpp_capture_memory_snapshot`。
`il2cpp-frida-mcp` 的 `il2cpp_gc_choose` 工具即薄封装 `gc.choose`。
**三方（本机导出表 + bridge 实现 + 同类项目工具）互相印证。**

两个必须记住的边界：

- **只对引用类型有效**（`gc.choose` 对值类型直接报错）—— 这是合理的，值类型没有堆实例。
- `frida-il2cpp-bridge` 的 v0.8.0 release notes 明说 `gc.choose` **曾在 Unity 2021.1+ 上崩进程**，
  修复描述是 *"should be fixed, or it shouldn't happen frequently at least"* ——
  即**维护者自己都不敢打包票**。所以这条能力必须**先在真机上验证再依赖**（见 §6）。

> ⚠️ **未验证的部分（不许当成已成立）**：我核实的是**导出存在**与**别家实现可行**，
> **尚未**在本机真机上跑通「注入 → liveness 计算 → 拿到非空实例列表」。
> 落地第一步必须是这个验证，而不是直接写工具。理由见本仓库的历史教训：
> 「三方一致」不等于「我们的样本上成立」。

### 3.2 主动调用方法：**可行**

`il2cpp_runtime_invoke` 与 `il2cpp_class_get_method_from_name` / `il2cpp_type_get_object`
在 5 个样本上 **3/3 全部存在**。调用配方是纯元数据路径：

```
class_detail 拿 token  →  runtime_class_info 拿 method pointer
→ il2cpp_class_get_method_from_name 拿 MethodInfo
→ il2cpp_runtime_invoke(method, instance, params, exception)
```

Mono 侧同样齐备（Archon Soul 的 `mono-2.0-bdwgc.dll`，1237 个导出实测）：
`mono_runtime_invoke` ✅、`mono_type_get_object` ✅、`mono_class_get_method_from_name` ✅。

### 3.3 截图：**Frida 不支持，必须外挂**

我直接查了 [Frida 官方 JavaScript API 文档](https://frida.re/docs/javascript-api/)全文：
**没有 `Screen` 章节，也没有任何截图 API**（全文 `screenshot` 仅出现在示例文件名 `/plugins/screenshot.js` 里）。
这否掉了一条想当然的路。

外挂方案的现实约束（本机实测已装/未装）：

| 库 | 本机 | 说明 |
|---|---|---|
| `mss` | ✅ 已装 | 纯 ctypes，无 GPU 加速 |
| `PIL` / `numpy` / `cv2` / `pytesseract` | ✅ 已装 | 可做缩放、裁剪、比对 |
| `dxcam` | ❌ 未装 | Desktop Duplication，对全屏独占 D3D 最稳（第三方基准 239 FPS@1080p） |
| `windows_capture` | ❌ 未装 | Windows Graphics Capture |

**但 `AGENTS.md` §2.4 规定运行期只依赖 `mcp` + `frida`，新增第三方依赖必须先说明理由并获得确认。**
所以截图要不要做、用哪个库，是**需要你拍板**的事（§7）。

### 3.4 判断「游戏加载完了」：有多条不靠截图的路径

- `Application.isLoadingLevel` **已废弃**，禁止使用。
- `SceneManager.sceneLoaded` 是官方推荐入口，但文档明确它触发于 `OnEnable` 之后、
  **`Start` 之前** —— 单独拿它当「可验收」判据会**过早**。
- `Scene.isLoaded` 文档原文：*"set to true after loading has completed and objects have been enabled."*
- 业界范式（Playwright）：元素 *"considered stable when it has maintained the same bounding box
  for at least two consecutive animation frames"* —— 这就是「画面稳定」的通用定义，
  而它**不需要截图**：Unity 侧用 `Time.frameCount` 连续 N 帧不变 + 目标对象存在即可近似。

## 4. 设计思路：三级能力，一条闭环

核心主张：**验收 = 动作 + 断言 + 证据，三者缺一不可。**
只有动作没有断言 → 「全绿但游戏没变化」的假成功；
只有断言没有证据 → Agent 自欺欺人。

```
        ┌─────────────── 观察面（已有，被动）───────────────┐
        │  search_* / class_detail / runtime_class_info     │  ← 静态+运行时元数据
        │  hook_method / drain_events / read_field_value    │
        └───────────────────────────────────────────────────┘
                              ▲ 补「主动」
        ┌─────────────── 动作面（新增）────────────────────┐
        │  find_instances   ← 拿到活对象（解锁一切）        │
        │  invoke_method    ← 让游戏做一件事                │
        │  set_field_value  ← 对称写入口                    │
        └───────────────────────────────────────────────────┘
                              ▼ 补「结论」
        ┌─────────────── 验收面（新增）────────────────────┐
        │  wait_for         ← 等到「可以判了」              │
        │  verify_state     ← 出一份**可证伪的证据包**      │
        └───────────────────────────────────────────────────┘
```

### 4.1 动作面

- **`find_instances(name, ...)`** —— 本方案里**最重要的一个**。
  走 §3.1 的 liveness 路径，返回某类的活实例指针（含 `field_count` 之类的过滤辅助）。
  **这一步直接消灭「靠 Hook 捡指针碰运气」**，让 `read_field_value` / 未来的
  `set_field_value` / `invoke_method` 全都有的放矢。
  必须遵守既有契约：`total` 是真实总数、`limit`/`has_more` 如实、超过 256 KB 自动进句柄。

- **`invoke_method(name, method, instance=..., args=...)`** —— 主动调用。
  参数类型沿用现有 `args_type` 那套规格（`int/uint/float/ptr/string/...`），
  返回值沿用现有自动推断（`float` 走 XMM 那条路已经修对了，直接复用）。
  **重载必须按 `token` 指定**，沿用 `hook_method` 已有的「多候选就拒绝，不猜」规则。

- **`set_field_value(instance, name, field, value)`** —— `read_field_value` 的对称入口。
  按字段类型决定写入宽度（与既有的 `_field_read_width` 同一张表），
  **不重复 `write_memory`**：后者要地址+裸字节，前者要「哪个对象的哪个字段」。
  这符合 §3.1「一个能力一个工具」——两者是「原始字节」与「语义字段」的关系，不是特例关系。

> **UI 点击要不要单独做一个工具？建议：先不做。**
> 语义化点击的可行路径（`ExecuteEvents.Execute` 派发 PointerClick，或 `Button.onClick.Invoke()`）
> **本质就是 `invoke_method` 的一个用法**，只是参数更讲究（泛型方法需先 inflate）。
> 按 §3.1 第 3 条「一个是另一个的特例就合并」，正确做法是
> **在 `SKILL.md` 里写成配方**，而不是再开一个工具让 Agent 猜该用哪个。
> 只有在实测发现「配方太脆、每次都要 Agent 手写一堆前置」时，才考虑升级为工具。

### 4.2 验收面（这才是「最后一公里」的正题）

- **`wait_for(condition, timeout_ms, ...)`** —— 等到「可以判了」再判。
  条件不该是像素，而应是**引擎自己的信号**：字段值到达某值 / 对象出现 / 场景已加载 /
  帧计数连续 N 帧稳定（§3.4）。超时**必须如实报错**，不许静默当成通过。
  参考 `funplay` 的教训：返回一个 `revision` + 建议的下次轮询间隔，
  让 Agent 遵守退避，而不是每秒自发轮询。

- **`verify_state(assertions, ...)`** —— 输出**证据包**，而不是一个布尔值。
  这是把 `podium-mcp` 那套设计搬进本项目，并按本项目的 token 对账改造：

  | 设计点 | 具体做法 | 来源 |
  |---|---|---|
  | **三态而非二态** | `verdict: "pass" \| "fail" \| "unverifiable"` | podium 的 `visible: true/false/null` |
  | **无法验证 ≠ 不存在** | 读不到就 `unverifiable`，**绝不**降级成 `fail` 或 `pass` | podium 的 fail-closed |
  | **每条结论必须点名依据** | 断言里带 `observed`（实际读到的值）、`static_token` / `runtime_token`、采样时刻 | podium 的 `via` / fivem 的「引用确切日志行」 |
  | **证据成组落盘** | 失败时把「期望/实际/差异」写文件并返回路径，**不塞进返回值** | gua 的 `actual/expected/diff/comparison.json` |
  | **区分「已提交」与「已完成」** | 动作已下发 ≠ 已生效，必须有独立确认态 | gua 的 `completion_unconfirmed` |

  这一条与美国项目管理协会无关，但与本仓库 `AGENTS.md` 的核心信条
  **「假成功是最危险的」**完全同源 —— 可以说它就是那条规矩在验收面的延伸。

### 4.3 视觉的定位：**证据，不是判据**

如果最终要做截图，严格按两条约束：

1. **`podium` 的铁律**：*"Screenshots are NEVER an oracle."*
   截图只作为**给人看的附件**，**不许**参与 `verdict` 的计算。
2. **返回文件路径，不是 base64**（podium 做法）。
   本项目已有 256 KB 硬上限，base64 图片会**瞬间把它吃满**，
   而 `windows-computer-use-mcp` 实测单张截图约 **5 万 token** —— 对 Agent 上下文是灾难。

### 5.1 V0 结果（真机实测，2026-10）

在 PathOfIdle（IL2CPP，Windows x64）上分四阶段验证，**四阶段全部通过**，
收尾 `close_session` 返回 `ok:true / restored:true`，游戏进程正常结束。

| 阶段 | 内容 | 结果 |
|---|---|---|
| A | 正确枚举程序集/映像 | 92 个映像，`Assembly-CSharp.dll` / `mscorlib.dll` / `UnityEngine.CoreModule.dll` 均在 |
| B | liveness 与 gc-world 导出存在性 | 6/6 全在（含 `il2cpp_stop_gc_world` / `il2cpp_start_gc_world`） |
| C | 单独调 stop/start GC world | 均 0ms 返回，**未死锁** |
| D | **对多个类枚举活实例** | **GameObject 100+（溢出上限）、Transform 49、System.String 100+，每类约 10–13ms** |

**结论：`find_instances`（V2）有确定的技术基础**，且性能足够（毫秒级）。

#### 三个必须记住的坑（都是本次踩出来的）

1. **`il2cpp_domain_get_assemblies` 是 out-param，不是迭代器。**
   第一版把它当迭代器循环（`while (asm = f(dom, iter))`），返回值永不判空 →
   死循环 → 探针 30s 超时卡死。**这曾被误读成「liveness 不行」**。
   正确签名是「返回数组首地址 + 把个数写进第二个出参」，
   本仓库探针的 `allImages()` 一直是对的，照抄即可。
2. **导出名是 `il2cpp_stop_gc_world` / `il2cpp_start_gc_world`**，
   不是 `il2cpp_gc_stop_world`（本机实测前者 5/5 存在、后者 0/5）。
3. **不要在游戏早期初始化阶段附着**。首次用 `spawn_and_attach(init=False)`
   直接卡死（窗口标题 `Fatal error in GC`）—— 这是《重启验证与运行时理解报告》
   §4.2 的已知问题。规避方式：**先裸启动 → 等约 25 秒 → 再 `attach`**，
   本次这样跑就正常了。

另有一条待观察项：D 阶段日志里出现过一次
`realloc_error: access violation accessing 0xffff...`（回调里对 `NULL`/`-1`
句柄调了 `il2cpp_free`），但**不影响结果**（三个类都拿到了实例）。
V2 落地时要把这个分支收严（只在句柄有效且 size==0 时 free）。

### 5.3 V2 结果：`find_instances`

「拿 instance 指针」的正路。在此之前**唯一**的办法是「Hook 一个恰好会
收到该对象的函数、从 `args[0]` 捡」—— 碰运气，与本项目哲学相悖。

**真机实测（PathOfIdle，IL2CPP）12/12 通过**：

```
find_instances(name="Transform", namespace="UnityEngine", max_count=5)
→ ok=true, count=5, overflow=true
  pointers: ["0x2ceca934320", ...]
  instances: [{pointer, class_name: "RectTransform"}, ...]
  class_name_counts: {"RectTransform": 5}
  exact_class_count: 0, derived_count: 5
```

**最关键的证据链**：独立读实例对象头（`read_memory`）拿到 klass 指针，
再用 `il2cpp_class_get_name` 解出类名 = `RectTransform`，
与工具报的 `instances[0].class_name` **完全一致** —— 证明拿到的确实是
该类的活实例，不是野指针。

#### 实测踩到并修掉的四个问题

1. **`il2cpp_class_is_valuetype` 的返回值不能直接当布尔用。**
   本探针把所有导出统一按 `'pointer'` 返回类型包装，于是 C 的 `false`
   变成一个**非空但内容为 0** 的 NativePointer 对象，而 JS 里任何对象都
   truthy —— `if (fn(k))` 会把**每个类**都判成值类型。
   实测：`UnityEngine.Transform`（明确的引用类型）被拒绝枚举。
   修法：`.toInt32() !== 0`（与文件里既有写法一致）。

2. **liveness 返回的是「该类**及其派生类**」的实例 —— 这是个陷阱。**
   实测 `find_instances(Transform)` 拿回的**全是 `RectTransform`**
   （Unity 里 UI 节点都是 RectTransform）。语义如此、不是缺陷，
   但若调用方拿基类的字段偏移去读派生类实例，**偏移可能不对**。
   修法：返回 `instances[].class_name` + `class_name_counts` +
   `exact_class_count`/`derived_count`，并在 `derived_count>0` 时给 `note`。
   这条**不是**「多给点信息」，而是把一个静默的错值风险变成可见的。

3. **`fail(msg, extra)` 的 extra 在 `detail` 里，会被调用方漏看。**
   探针统一把附加信息放 `detail`，而 `unsupported` 是调用方**直接读**的
   语义位 —— 验收脚本读顶层读到 `None`，把「引擎限制」误判成
   「工具没按契约标注」。修法：工具层把 `detail` 摊平到顶层。

4. **`mono_gc_walk_heap` 的返回类型必须登记为 `pointer`。**
   Mono 侧我一开始按 C 头文件写了 `'int'`，被项目的既有断言拦下 ——
   这条断言是有来历的（非 pointer 的数值返回类型造成过一次真实崩溃）。
   修法：登记 `pointer` + 调用处 `.toInt32()`，顺从项目不变量。

#### Mono 侧：如实声明限制，不用零冒充

Mono **没有** IL2CPP 那套 liveness 导出。唯一相关的 `mono_gc_walk_heap`
在官方头文件（`mono/metadata/mono-gc.h`）里写着：

> heap walking is only valid in the pre-stop-world event callback

所以从 Frida 线程直接调它**不保证有效**。实测 Archon Soul 上返回
`rc=1, scanned=0`。工具的处理是：

- 返回 `ok:false` + `unsupported:true` + `rc` + `scanned`，
- 错误信息**明确写**「本次记为『本时机不可用』，**不能**据此断定该实例不存在」，
- **不返回 `count`** —— 给个 `count:0` 会被读成「这个类没有实例」。

`verify_mono_runtime.py` 里对这条的断言是**契约式**的（两种结果都合法，
但不合法的是假成功），没有把引擎限制写成产品缺陷。

#### 验收

- `devtools/verify_find_instances.py`：**24 项**纯契约断言（不需要游戏），
  含三条非空转反证。其中一条反证本身踩到了**空真陷阱**：
  `all("class_name" in x for x in (instances or []))` 在空列表上返回 `True`，
  会把「没有 instances」误判成「有 class_name」→ 反证空转。
  已改为先要求列表非空，并加了一条反向确认断言。
- `verify_mcp_tools.py` / `verify_mono_runtime.py` 补了真机断言
  （含上面那条「对象头解出的类名 == 工具报的 class_name」的证据链）。
- 全套 **47/47 通过**，动态覆盖率门禁通过。

### 5.4 V4 结果：`wait_for`（验收闭环的关键一步）

游戏是**异步**的：点完按钮要等界面出来。不等待直接断言会得到大量
**假失败**。`wait_for` 把这个模式做成了一句可依赖的工具，支持五种条件：
`field` / `instances` / `log` / `ocr` / `window`。

**设计上最重要的一点：`verdict` 是三态，不是布尔。**

| 值 | 含义 | Agent 该怎么做 |
|---|---|---|
| `pass` | 条件成立 | 继续 |
| `fail` | **判了**，没成立（含超时） | 看 `evidence` 里的实测值 |
| `unverifiable` | **没法判**（引擎侧不支持等） | 换判据，**别去修不存在的缺陷** |

把「没法判」说成「没通过」，会让 Agent 去修一个**根本不存在的缺陷** ——
这与本项目「假成功最危险」是同一枚硬币的两面。返回里另带
`polls` / `elapsed_ms` / `evidence`（每次轮询实测值，限 30 条）/
`last` / `hint`，超时**如实报 fail**。

验收 41 项，含四条反证。其中最有价值的一条是**非空转前提**：
要验「evidence 有上限」，就得先确认轮询次数**真的超过**上限 ——
第一版用 `interval_ms=100` 只轮了 29 次（没到 30 的上限），
断言就变成了空转。改成 `interval_ms=50` 后轮 49 次，才真正验到截断。

### 5.5 V5 + V6 结果：截图 / OCR / 日志 + 按键配方

**新增 3 个工具**（`capture_screen` / `ocr` / `probe_log`），
设计纪律全部来自 Bot 项目调研：

- **截图是证据、不是判据**（`podium-mcp`：*Screenshots are NEVER an oracle*）；
- **坐标一律屏幕绝对坐标**（裁剪图不回传基准会点偏）；
- **只 OCR 局部**（实测整屏 2560x1440 = **4.1 秒**，ROI = 几十毫秒）；
- **截图只落盘、不回 base64**（256 KB 上限 vs 单图约 5 万 token）；
- **`matched_count == 0` 是「本次没找到」，不是「不存在」**。

**`probe_log` 是本项目的差异化能力**：调研的 7 个 Bot 项目**没有一个**
用游戏日志判断结果（它们靠视觉/注册表/CDP），而用户明确要
「通过日志确认结果」。它**只读不消费**，所以天然适合轮询。

#### V6：按键链路 —— **实测跑通**，且记下了四个坑

用户场景里「按热键唤起 Mod 面板」这一步，本机在真实游戏上验证通过。
四个坑缺一个都发不出键：

| 坑 | 实测现象 | 解法 |
|---|---|---|
| **前台锁** | `SetForegroundWindow` 返回 **0**，键发到了浏览器 | 先 `AttachThreadInput` 附加到前台线程 |
| Frida 17 API 变更 | `Module.getExportByName` 报 **"not a function"** | 用 `Process.getModuleByName('user32.dll').findExportByName` |
| `eval_script` 的表达式语义 | JS 里的 `//` 注释报 `unexpected token`（它先按表达式求值、包一层 `return (...)`） | 只用 `/* */` |
| `SendInput` 只看前台窗口 | 「投递成功」返回 1，但游戏**没收到**（前台是别的程序） | 发键前后都核对 `fg_is_game` |

**实测数据（PathOfIdle）**：

```
SetForegroundWindow 单独用          → returned=0, fg_is_game=false  ← 失败
SetForegroundWindow + AttachThreadInput → returned=1, fg_is_game=true ← 成功
游戏在前台时 SendInput               → sent=1
```

配方写进 `SKILL.md` 配方 8（按用户决策**不新增工具**）。
同时明确标注：`SendInput` 是系统级合成输入，**带反作弊的网游会检测**，
只适用于单机/离线场景。

### 5.6 V3（`invoke_method`）为什么**没做**

原计划要加一个「主动调用方法」的工具。V2/V4 做完后重新判断：
**它没有不可替代的价值**，理由有三条：

1. **现有 `eval_script` 已能覆盖**：`il2cpp_runtime_invoke` 等 5 个导出
   本就绑定在探针里（V0 阶段实测确认），配方 6/8 已给出可直接抄的写法。
2. **做成工具会把「选哪个重载」的难题塞进参数里**，而 `hook_method`
   已经有一套「多候选就拒绝、按 token 指定」的成熟规则；
   再开一个工具要么重复这套规则，要么留一个更弱的版本，
   违反 AGENTS.md §3.1「不许让 Agent 猜该用哪个工具」。
3. **调错方法的后果是崩游戏**，而配方形式天然要求调用方**自己写出
   方法名与参数**，比一个通用工具更难误用。

**结论：不做。** 留着配方；若将来发现「同一套 invoke 前置步骤被反复
手写」成为真实痛点，再按当时的证据重新判断。

### 5.7 真机验收：CatapultHero（UE 5.7 + UE4SS Lua Mod）

在 `E:\project\CatapultHero` 上用本工具集对**已完成的 Mod**
（`CatapultHeroDebugPanel` v0.1.0）做了一次完整验收 ——
这是「最后一公里」能力的第一次实战，**发现并修掉了 3 个真实缺陷**。

**环境特殊性**：这是 **UE 游戏**，没有类型元数据，所以
`find_instances` / `field` / `instances` 这些条件**用不了** ——
判据全部来自 **UE4SS.log 的 `[调试面板]` 日志** + **屏幕 OCR**。
这恰好说明为什么 `probe_log` 与 `ocr` 是必需的两条腿。

#### 验收结果（全部通过）

| 项 | 判据 | 结果 |
|---|---|---|
| Mod 加载 | `probe_log` 找 `[调试面板]` | ✅ `热键注册完成：成功 17，失败 0` |
| 进局内 | 点击「序幕」→「明白了」 | ✅ 到达地图界面（`序幕 / 通过第7层`） |
| **F1 呼出面板** | 日志新增 4 条 + 屏幕 OCR | ✅ `面板已创建并显示`；OCR 读出全部 8 项 |
| **F2 精核 +100** | 日志 + 屏幕**双重**独立证据 | ✅ `已修改 精核 = 108`，OCR 同步显示 `精核：108` |
| double 类型 | 按 8 两次 | ✅ `敌人强度 = 0.5 → 1.0` |
| 缩放热键 | 按 `+` | ✅ `缩放调整为 1.1x`（文字一并放大） |
| 闭环复跑 | 连续 5 次 F2 | ✅ 精核 108→208→308→408→**508**，每步双证据 |

#### 实战修掉的 3 个真实缺陷

**① `find_window_rect` 用错坐标系（会截错区域，且返回 `ok=true`）**

本机是 150% 缩放（物理 2560x1440 / 虚拟 1707x960）。进程不是 DPI 感知时
`GetWindowRect` 返回**虚拟化**坐标：

```
GetWindowRect  → [451, 0, 1319, 517]    （虚拟坐标系）
DWM 真实边界   → [685, 0, 1969, 767]    （物理像素，与截图同一坐标系）
```

而 `dxcam`/`mss` 用**物理像素**。两者混用 → **截到了旁边的终端窗口**，
而 `capture_screen` 照样返回 `ok:true` —— 典型假成功。
修法：进程级 DPI 感知（`SetProcessDpiAwarenessContext(-4)`）+ 优先用
`DWMWA_EXTENDED_FRAME_BOUNDS`；返回里新增 `rect_source` /
`dpi_awareness` 便于核查。

**② `wait_for(kind="log")` 是「等存在」而非「等新增」→ 假阳性**

原实现判「日志里有没有匹配行」。于是日志里**早就有**匹配行时，
它在 **1ms** 内返回 `pass`，而本次操作根本没发生：

```
UE4SS.log 里已有 5 条「已修改 精核」
wait_for(kind='log', pattern='已修改 精核') → pass, polls=1, elapsed=1ms
```

修法：首次轮询记**基线**，之后要求**超过**基线才算成立；
证据里带 `baseline` / `delta`。修后同一调用如实返回
`fail, polls=5, 1.6s, delta=0`；真的新增一行时正确 `pass, delta=1`。
验收里加了 9 项断言（含「等满超时才放弃」与旧写法反证）。

**③ 按键投递失败：`ctypes` 的 `INPUT` 结构体大小算错**

宿主侧用 `ctypes` 构造 `INPUT` 时，我用 `padding = c_byte*24` 凑大小，
`sizeof(INPUT)` 只有 **32** 字节，`SendInput` 直接返回 **0**（一个事件都没
送出去），游戏毫无反应。正确 union（含 `MOUSEINPUT` 32 字节）得 **40** ——
x64 的真值。对照：同一套键在**游戏进程内**用 Frida 手工
`Memory.alloc(64)` 是成功的，所以这不是权限或前台问题。

> 这条与配方 8 里记的另外三个坑（前台锁 / Frida 17 API / `//` 注释）
> 合起来是**五个**；全部写进 `SKILL.md` 配方 8。

#### 一条方法论收获

`wait_for` 的 `unverifiable` 与 `fail` 之分，在实战里立刻用上了：
第一次验收闭环时我等的字符串是 `面板已显示`，但本次运行打的是
「面板已**创建**并显示」（`面板已显示` 只在隐藏后重开时才出现）。
`wait_for` 如实报 `fail` + 每次轮询 `matched_count=0` ——
**它判了、没成立**，而不是含糊过去。错的**是我的判据**，工具行为正确。
这正是三态设计想要的效果：让「判据写错了」与「功能坏了」能区分开。

## 6. 落地必须遵守的项目规矩（容易被忽略）

1. **五处同步**（`AGENTS.md` §4）：`server.py`（实现 + docstring + instructions）、

5. **新依赖要问**（§2.4）：截图这条路绕不开新增依赖，需要你确认。
6. 工具的**返回字段不许恒为空**、收下的参数**必须真的影响行为**（§4 的「不干活」批注）。

### 7.1 截图 + OCR 的实现路线（依据 Bot 项目调研）

调研了 7 个游戏自动化 Bot 项目（MAA / MaaFramework / BetterGI /
March7thAssistant / ALAS / ok-script / MaaMCP），归档见
`agent_logs/20261009-091500-研究员-游戏自动化Bot调研.md`。
结论直接决定 V5 怎么设计：

| 设计点 | 采纳的做法 | 依据 |
|---|---|---|
| **OCR 引擎** | 本机已有 **Tesseract 5.5（含 `chi_sim` + `eng`）**，先用它；不引入 PaddleOCR 等重模型 | 零新增大体积依赖；MAA 用 PaddleOCR 是因为要跑在用户机器上且追求速度，我们的场景是本地验收 |
| **只 OCR 局部 ROI** | 必须。`ocr(roi=...)` 只送 ROI 进模型 | MaaFramework `OCRer::analyze()` 第一步就是 `make_roi` |
| **分辨率基准** | 用**相对坐标**（0~1 比例），不写死像素 | March7th 的相对比例 crop；MAA 的 `control_scale` 是另一流派，但我们是外部工具、拿不到游戏内缩放系数 |
| **返回坐标** | 必须回传 `box` + `click_point` + **基准尺寸**，否则 Agent 会点错位置 | MaaMCP README 专门写进坑：裁剪图坐标不回传基准就会点偏 |
| **断言用文本** | OCR 文本参与断言，**截图不参与判据** | podium：*Screenshots are NEVER an oracle* |
| **失败留证据** | 失败时把截图**落盘**并在返回里给路径，**不返回 base64** | MaaFramework `save_on_error`；256 KB 上限 + 单图 ~5 万 token 的教训 |
| **点击方式** | 后台 `PostMessage` 优先，失败降级到前台并**如实标注** `background:false` | MaaFramework 的 input method 枚举标了 Background Support |
| **日志确认** | 单独一个 `probe_log(path, pattern)` 工具 —— **这是 7 个 Bot 项目全都没有的能力**，而用户明确要「通过日志确认结果」 | 调研结论：Bot 们靠视觉/注册表/CDP，没人读游戏日志 |
