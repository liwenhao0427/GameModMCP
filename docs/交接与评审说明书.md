## §1 项目定位：它解决什么问题

GameMod MCP 是一个 **stdio MCP 服务器**，把「游戏 Mod 开发」能力暴露成标准 MCP 工具，
供任意通用 Agent（Claude Code / Codex / Cursor / 自研 Agent）调用。

### 1.1 传统做法的问题

做游戏 Mod（改数值、Hook 函数、改内存）的传统路径是**内存修改器式**的：
反复搜值 → 改值 → 再筛。这条路对 AI Agent 很不友好：

- **没有「有哪些类/字段/方法」的概念**。Agent 只能看到一串地址和字节。
- **每次都要靠猜**。改错了不知道是哪个环节错，只能重来。
- **上下文消耗巨大**。内存值搜索的中间结果（成千上万个候选地址）会塞满上下文。

### 1.2 本项目的做法：元数据优先

用**游戏自带的元数据**（而不是内存搜索）来回答问题：

| 问题 | 传统做法 | 本项目做法 |
|---|---|---|
| 游戏里有哪些类？ | 搜内存字符串 | 解析 `global-metadata.dat`（IL2CPP）或托管 DLL（Mono） |
| 这个字段在哪？ | 反复搜值筛地址 | 静态查字段 → 运行时取**真实偏移** |
| 怎么改这个数值？ | 写内存（易崩） | Hook 方法 → 读事件 → 精确写字段 |
| 这个类能不能改？ | 不知道，试了才知道 | `analyze_dependency` 看牵连范围 |

**关键收益**：Agent 拿到的是**有名字、有类型的结构化信息**，而不是裸地址。
这让「让 AI 做 Mod」从「碰运气」变成「有据可依」。

## §2 技术架构设计

### 2.1 分层结构

```
┌─────────────────────────────────────────────────────────────┐
│  MCP 客户端（Claude Code / Codex / Cursor / 自研 Agent）      │
└───────────────────────────┬─────────────────────────────────┘
                            │ stdio (JSON-RPC)
┌───────────────────────────▼─────────────────────────────────┐
│  server.py —— MCP 工具层（45 个 @mcp.tool）                   │
│  职责：参数校验 → 调下层 → 组装返回。**不写解析逻辑**           │
│  外层统一包 @_cap_response（256 KB 响应上限兜底）              │
└───────────┬──────────────────────────────┬──────────────────┘
            │                              │
┌───────────▼──────────────┐   ┌───────────▼──────────────────┐
│  engine/ —— 静态分析层    │   │  runtime/ —— 动态分析层        │
│  · pe.py        PE 解析    │   │  · agent.js  注入进程内的探针   │
│  · il2cpp_meta.py          │   │  · session.py Frida 会话封装   │
│  · mono_meta.py  ECMA-335  │   │                              │
│  · ue.py        UE 容器    │   │  IL2CPP 59 个 API              │
│  · adapt.py    ★引擎适配   │   │  Mono   56 个 API              │
│  · index.py     SQLite     │   └──────────────────────────────┘
│  · state.py     会话状态   │
└────────────────────────────┘
```

### 2.2 为什么要 `adapt.py` 这一层（关键设计）

IL2CPP 与 Mono 是**两个根本不同的元数据体系**：

- **IL2CPP**：类型/字段/方法各自的索引轨道**相互独立**，字段的 `typeIndex`
  甚至不在自己的索引空间里 —— 得靠「比它小的最大 byval 键」启发式推算（~90% 可解）。
- **Mono**：标准 ECMA-335，字段/方法的类型都编码在 `#Blob` 签名里，
  能**精确**解出完整类型名（数组、泛型、指针都对）。

两者在「类型/字段/方法/参数的归属关系」上是**同构的**，差异集中在
**如何表示与解析类型引用**。把这点差异收进 `adapt.py`，索引层就能共用一套代码。

**设计原则**（三条）：
- **不猜**：解不出来就返回 `None`，由调用方决定怎么呈现
- **不藏**：把 `confidence` 透出来（IL2CPP 是启发式，Mono 是精确）
- **不侵入**：本层只做「读」的适配，不改动 `il2cpp_meta` / `mono_meta`

> **架构铁律**：引擎差异**只允许**出现在 `adapt.py`，不许散落到 `server.py` 或工具文档里。

### 2.3 数据流：一次完整的 Mod 开发

```
[静态阶段 —— 不需要游戏在运行]
  open_game(game_dir)          识别引擎 → 解析元数据 → 建 SQLite 索引
    ↓
  search_classes("Player")     拿到候选；嵌套类型用 nested_name
    ↓
  class_detail("Player")       看字段/方法/token → **记下 token**
    ↓
[运行时阶段 —— 需要注入]
  inject_process() / launch_game()     Frida 注入，探针上线
    ↓
  runtime_class_info("Player")         取字段**真实偏移**、方法**真实地址**
    ↓
  find_hook_target("Player","TakeDamage")   定位可 Hook 的地址
    ↓
  hook_method(..., token=0x06000A3D)   装 Hook（token 对账在此发生）
    ↓
  drain_events()                       读捕获到的调用（参数 / 返回值 / 调用来源）
    ↓
  read_field_value / set_field_value   精确读写字段
    ↓
  close_session()                      卸载 Hook、断开注入，恢复原状
```

### 2.4 关键机制：SQLite 索引 + 结果句柄

- **索引**：解析元数据后落 SQLite，可缓存复用（实测 IL2CPP 建索引 2.6s、复用 1.3s）。
  缓存有边界、可查看、在用的不会被误删。
- **结果句柄**：查询可能命中上万条，不能一次返回。工具返回 `handle`，
  调用方用 `read_query_result(handle, offset, limit, pattern)` 翻页。
  句柄**惰性物化**（翻页只解析那一页），且**跨索引隔离**
  （旧句柄必须被拒绝，不许读到另一个游戏的数据）。

### 2.5 响应体积上限（256 KB 统一兜底）

所有工具被 `@_cap_response` 包一层。为什么不在每个返回里各写各的：
45 个工具里只有一部分走统一的 `_ok()`，而超限最严重的几个恰恰不走它。
超限时**截断最大的那个顶层列表**、完整列表进句柄，并**如实改写**
`has_more` / `returned` —— 「明明还有却说没有」比超限更糟。

## §3 两阶段方法论（项目的核心断言）

这是**全项目最重要、也最容易说反**的一条。评审时请以此为准：

| 信息 | 静态元数据 | 运行时探针 |
|---|---|---|
| 类 / 字段 / 方法的**存在与签名** | ✅ 有 | ✅ 有 |
| 方法的 **token** | ✅ 有 | ✅ 有 |
| 字段的**字节偏移** | ❌ **没有** | ✅ 有（`runtime_class_info`） |
| 方法的 **RVA / 绝对地址** | ❌ **没有** | ✅ 有（`find_hook_target`） |

> **历史教训**：早期文档曾写「元数据给出字段偏移与方法 RVA」，
> 这与代码里的 `method_address_in_metadata: False` 直接矛盾，
> 会误导 Agent 在没注入时就去算地址。**任何文档都不许再出现这种说法。**

### 3.1 token 对账：判断「Hook 落点正确」的唯一证据

```
静态 class_detail(...)  →  token = 0x06000A3D
运行时 find_hook_target(...)  →  token = 0x06000A3D
                              ↑ 两者相等 ⇒ 落点正确
```

`token` 是连接静态与运行时的**唯一钥匙**。挂 Hook 时优先靠 `token` 指定重载 ——
同名方法可能有多个重载，盲挂到错误的重载上 Hook 照样会成功，
错误要到很久以后才以「数据不对」的形式暴露。

### 3.2 嵌套类型必须用 `nested_name`

IL2CPP 的 namespace **只属于最外层类型**，嵌套类型（状态机 `State`、
协程体 `<Xxx>d__0`、私有内部类）的 `full_name` 只是**短名**。

实测：某样本 20,072 个类型里 **7,056 个（35%）是嵌套类型**；
名为 `State` 的类型有 **131 个，只有 1 个是顶层**。

所以下游工具要用 `nested_name`（如 `Outer.Inner`），不是 `full_name`。

## §4 工具全清单（45 个）

> **本清单由运行中的 MCP 注册表导出**（`FastMCP.list_tools()` 的真实返回 +
> `server.py` 的层节注释推断归属），**不是手抄的**。
>
> 「语义」列的四个位是 MCP 的 `destructiveHint` / `readOnlyHint` 等标注。
> **只读** = 不改变任何状态；**改动** = 会改变状态；**破坏性** = 可能弄坏东西；
> **外部世界** = 与进程外的世界交互。

**语义统计（实测）**：只读 27 个 / 非只读 18 个 / 破坏性 5 个 / 无参数 3 个。

## §5 引擎支持矩阵与跨引擎差异

### 5.1 支持程度

| | IL2CPP | Mono (.NET) | Unreal |
|---|---|---|---|
| 静态查询类型 | ✅ 完整 | ✅ 完整 | ❌ 无类型系统可查 |
| 字段类型精度 | ⚠️ 启发式（~90%） | ✅ 精确（ECMA-335 签名） | — |
| 字段偏移 | ✅ 运行时取 | ✅ 运行时取 | ❌ 需运行时，未实现 |
| 方法地址 | ✅ 运行时取（含 RVA） | ✅ 运行时取（JIT 机器码，**无 RVA**） | — |
| 运行时 Hook | ✅ | ✅（按地址挂） | — |
| GC 暂停 | ✅ | ❌ 本版 Mono 无该导出 | — |
| 资源容器清单 | — | — | ✅ pak/utoc 100% 准确 |
| 可反编译出源码 | ❌（已转 C++） | ✅（ILSpy/dnSpy 接近源码） | ❌ |

### 5.2 Mono 上的四条差异（都是**如实声明**，不是「未实现」）

1. **没有 RVA**：地址来自 `mono_compile_method` 触发的 JIT，代码不在
   `mono-2.0-*.dll` 内，所以 `in_module: false` 且不给 `rva`。
   元数据里的 RVA 指向 **IL 字节码**，不能拿来 Hook。
2. **`gc_control` 不支持**：没有 `mono_gc_disable` / `mono_gc_enable` 导出
   （四个 Mono 样本一致核实），调用会明确返回 `ok:false` —— 不要当失败重试。
3. **程序集懒加载**：刚注入时只枚举到十来个程序集，`UnityEngine.*`
   要过几秒才出现（实测 13 → 164）。**注入成功后探针会等它加载稳定再返回**。
   > **为什么必须等**（不是保险起见）：矩阵实测某游戏在只有 13 个程序集时
   > 被 Hook 并强制调用方法，**进程随后消失** ——
   > 「注入成功」与「可以 Hook 托管方法」在 Mono 上**不是同一件事**。
4. **静态索引的范围**：Mono 的静态索引默认只收游戏自己的程序集
   （`Assembly-CSharp.dll`），`UnityEngine.*` 这类框架类型**静态查不到**，
   要用 `runtime_class_info` 在运行时查。

### 5.3 实测数据（真实游戏，非构造样本）

- **IL2CPP**（17 MB 元数据）：20,072 类型 / 139,501 方法 / 81,872 字段 / 94 映像。
  字段类型解析率 90.10%，**与地面真值 dump 比对 27,264 条 0 错（100% 精度）**。
  建索引 2.6s，缓存复用 1.3s。
- **Mono**：1,387 类型 / 6,611 方法 / 6,343 字段。
  与微软官方 `System.Reflection.Metadata` 交叉验证 **45 张表 0 差异**，
  签名解析 100%。运行时 `mono_*` 导出绑定 56 个、零缺失。
- **Unreal**（两个样本）：`.pak` v11/v12 与 `.utoc` v8 完整解析，
  **与打包清单交叉校验 4,556/4,556、7,178/7,178、18,956/18,956 全部 100% 命中**。

## §6 设计取舍：已做的决策与**已实测否决**的项

> **这一节对评审者最重要**：下面这些是**量过之后**才决定的。
> 请不要重复建议已经被实测否决的方向（§6.3 列了清单及否决理由）。

### 6.1 为什么引擎解析器全部手写，不用现成库

`pefile` / `lief` 更省事，但会带来三个问题：**依赖体积、版本漂移、
以及遇到魔改文件时无从下手**。自己写 PE 解析不到 400 行，
IL2CPP 元数据解析 1,000 行 —— 换来的是**零依赖**和完全可控的错误信息。

### 6.2 为什么不做 MCP 的进度、取消与 tasks

这三样都是**协议里有、但这个客户端不消费**的东西：

| 协议面 | 实测 | 结论 |
|---|---|---|
| `notifications/progress` | 客户端调工具时只传 `{signal, timeout}`，**从不传 `onprogress`** → 请求里没有 `progressToken` → `report_progress` 是静默 no-op | 不做 |
| `notifications/cancelled` | 客户端**确实**会传取消信号，但服务器够不着：FastMCP 对同步工具是**内联调用**，事件循环被占满，连取消通知都读不到 | 不做 |
| `notifications/message`（MCP logging） | 只有通用 SDK 里有，没有任何客户端包消费 | 不做 |
| tasks 扩展（`taskSupport`） | 客户端桥**直接抛错** | 不做（声明 `required` 会主动弄坏） |

**代价是诚实的**：一个 60 秒的 `launch_game` 期间，服务器什么都干不了
（同步工具占着事件循环）。要改就得把长任务改成 `async` + 线程池包一层 ——
那是结构性改造，而协议那头的收益恰好是没人消费的。

## §7 可信度：验证体系

这个项目**不靠「看起来能跑」**。`devtools/` 下有 **51 个**可复现的验证脚本，
每个都对着**真实游戏**和**地面真值**跑。

### 7.1 真值来源（为什么数字可信）

拿**游戏或平台自己生成的**东西当真值，不许拿自己写的第二个解析器当真值：

| 引擎 | 真值来源 |
|---|---|
| IL2CPP 结构 | 独立解析 + 内部一致性 + 逐条比对 |
| IL2CPP 字段类型 | 游戏官方 dump（含 `/*0x20*/` 偏移注释） |
| Mono | **微软官方** `System.Reflection.Metadata` |
| UE | 游戏自带 `Manifest_UFSFiles_Win64.txt` 打包清单 |

### 7.2 两类脚本分工

| 类型 | 验证对象 | 能发现什么 |
|---|---|---|
| `verify_<模块>.py` | 模块内部逻辑 | **解析算法错** |
| `verify_mcp_<引擎>.py` | **MCP 工具层** | 能力没接上、返回结构不对、**假成功** |

### 7.3 覆盖率的两种检查（分工不同）

| 检查 | 手段 | 能当门禁吗 |
|---|---|---|
| `verify_tool_coverage.py` | 静态扫源码 | ❌ 会**高估** |
| `report_tool_coverage.py --strict` | 运行时垫片 | ✅ 是门禁 |

**教训**：静态检查只看「工具名有没有出现在脚本里」，会把会话对象调用也算成覆盖 ——
它曾报「38/38 全覆盖」，而带垫片实测只有 30/38。
**「记录工具」自身也要被验证**，否则「没有数据」会被误读成「已覆盖」。

### 7.4 非空转反证（本条对评审建议尤其重要）

改行为类代码时**必须**做非空转反证：**把代码改回旧写法，看断言是否真的报红**。
一条恒真的断言比没有断言更糟 —— 它会让人以为问题已被覆盖。

> 实例：本文档的生成过程中就抓到过两处自写的恒真断言
> （在整份 README 里找 `"MIT"`，而正文别处本来就有 MIT 字样，
> 于是把许可行改成 GPL 后断言照样通过）。修法是**收窄断言范围**。

## §8 已知限制

- **IL2CPP 字段类型约 10% 解不出**。这是元数据格式本身的限制
  （复合类型只给到元素类型），不是 bug。工具会标记 `type_confidence: unknown`，
  需要时用运行时内存读取确认。
- **反调试游戏注入会失败**。带 EAC/BattlEye 的网游基本注入不了，
  这是预期的，不要反复重试。
- **Unreal 支持受限**。UE 没有像 IL2CPP 那样集中的元数据文件，
  结构信息依赖 UE profile / `.usmap`。**FName 池、属性偏移、`.usmap` 未实现**
  （静态样本中不可得，诊断里如实标注）。
- **只支持 Windows**。注入依赖 Frida 在本机的能力。
- **Headless 环境验证不到自然调用**。没有显示/GPU 的机器上游戏不渲染帧，
  每帧方法不会自己触发。
- **Python ≥ 3.10；`mcp` 必须 < 2**。本代码用 1.x 的
  `mcp.server.fastmcp.FastMCP`，2.x 已改名成 `MCPServer`，
  只写 `>=1.0.0` 会让全新环境装到 2.x 然后**服务器起不来**（打包时实测到）。

## §9 硬性规范（评审建议必须满足的约束）

> **请优先检查建议是否违反了这些规则** —— 违反的优化无论多合理都无法合并。

### 9.1 分层与职责

- `server.py` **不许写解析逻辑**；逻辑放 `engine/` / `runtime/`，`server.py` 只编排。
- 引擎差异**只允许**出现在 `adapt.py`，不许散落到 `server.py` 或工具文档里。
- `agent.js` 里的能力**必须有对应的 MCP 出口**；没有出口的函数是死代码，应删除。

### 9.2 MCP 工具契约（5 条）

1. **返回值**：永远是 dict，且**必定**含 `ok`（`True`/`False`）。失败带 `error`。
2. **日志**：一律走 stderr。**stdout 是 JSON-RPC 通道，写任何东西都会破坏协议**。
3. **单一职责**：一个能力只暴露**一个**工具。若两个工具做同一件事
   （或一个是另一个的特例），**合并成一个**用参数区分，而不是留给 Agent 去猜。
4. **找不到就明说**：查询无结果返回 `total: 0` 并附说明，
   不许返回空列表让 Agent 误以为「不存在」。
5. **不返回超大结果**：必须支持 `limit` / `offset` 或 `pattern`，
   并在 `has_more` 里如实标注。**任何返回不超过 256 KB**（由 `cap.py` 统一兜底）。

### 9.3 返回值不许「假成功」

- **收下的参数必须真的影响行为**。没有任何读取方的参数就该删掉。
- **返回字段不许恒为空/恒定值**。拿不到就明确给 `null` 并说明。
- **数值字段的读取宽度必须按类型来**（4 字节字段不许读 8 字节）。
- 改这类行为时**必须同时给纯函数与端到端两层验收** + 非空转反证。

### 9.4 文档同步（改工具时必须**同一次**改完五处）

| # | 位置 | 内容 |
|---|---|---|
| 1 | `server.py` | 工具实现 + 模块 docstring 的「工具分层」列表 + `FastMCP(instructions=...)` |
| 2 | `README.md` | 「工具一览」表格 |
| 3 | `skills/gamemod-mod/SKILL.md` | 工作流、配方、引擎差异 |
| 4 | `devtools/verify_mcp_*.py` | 覆盖该工具的验收断言 |
| 5 | `devtools/verify_tool_annotations.py` | 表态它危不危险 |

> **工具清单以代码为准，文档不许硬编码数量。**
> 不一致时校验脚本返回非零退出码，这是判断「文档是否实时更新」的唯一依据。

### 9.5 ⚠️ README 的工具表是**生成**的，不要手改

`README.md` 里 `<!-- BEGIN GENERATED: tools -->` 与 `<!-- END GENERATED: tools -->`
之间是**由 `devtools/gen_docs.py` 从代码生成**的，且有门禁要求逐字节一致。

**要改工具描述就改该工具的 docstring 首段，再跑 `python devtools/gen_docs.py --write`。**
直接手改 README 表格会让门禁报红。

### 9.6 其它硬性规矩
- **编码**：所有文本文件必须 **UTF-8 无 BOM**，有校验脚本。
- **语言**：与人交互、代码注释、文档正文用**中文**；标识符用英文。
- **不许编造**：不确定就明确说不确定并给出如何验证，绝不猜一个看起来合理的值。

- **绝不入库**：索引缓存（`*.sqlite`）、`__pycache__/`、凭据、构建产物。
- **测试脚本路径**：样本路径集中定义，**不许硬编码绝对路径**。

以下是**当前状态下**我认为最值得外部视角审视的地方（不限于此，欢迎补充）：

1. **`server.py` 3,337 行是否有更好的组织方式？**
   它承载 45 个工具 + 统一的语义标注 + 响应上限装饰器。
   工具层的膨胀是 MCP 服务器的通病，有没有既能保持「一处编排」又不臃肿的结构？

2. **同步工具占住事件循环的代价，有没有低风险的缓解路径？**
   §6.2 的结论是「不改」，依据是「协议那头的收益没人消费」。
   但 60 秒的 `launch_game` 期间服务器完全不可用是真的。
   如果把长任务改成 `async` + 线程池，风险与收益如何重新权衡？

3. **`agent.js` 3,026 行（IL2CPP 59 + Mono 56 个 API 双后端）的复杂度控制。**
   两套后端的差异目前靠命名约定与分支隔离，有没有更清晰的抽象方式，
   同时不引入构建步骤（探针必须能直接注入）？

4. **45 个工具是否仍然过载？**
   工具越多，Agent 的「该用哪个」判断成本越高（实测这些工具的
   描述 + schema 共约 **44 KB / 1.3 万 token**，是每次会话的固定成本）。
   有没有可以合并/隐藏的？注意 §9.2 第 3 条禁止「功能重复的工具各留一个」。

5. **验证体系的边际收益。** 51 个脚本、动态覆盖率门禁 —— 哪里是过度投入，
   哪里还有盲区？（注意：本项目要求「对着真实游戏与第三方真值跑」，
   不接受「断言应该如此」的测试。）

6. **弱视觉层（截图 / OCR）的定位。** 项目方法论强调「截图是证据、不是判据」，
   优先用引擎信号。这一层的 5 个工具是否边界清晰？

## §11 未决疑问清单（**写文档时新发现，附取证**）

> 以下每条都是**在核对本文档数据时**发现的，均已用代码事实取证。
> 它们**没有被修**（不在本文档的职责范围内），如实列出供评审判断。
> 每条都标注了「是不是缺陷」与「为什么我（作者）没有当场改」。

### 11.1 ✅ 已确证的缺陷：`report_runtime_matrix.py` 的工具清单漏了 7 个

| 项 | 事实 |
|---|---|
| 脚本硬编码 `ALL_TOOLS` | **38 个** |
| 服务器实际报出 | **45 个** |
| 脚本漏掉 | `find_instances`、`set_field_value`、`capture_screen`、`ocr`、`probe_log`、`wait_for`、`verify_state` |
| 脚本多写 | 无 |

**后果**：`docs/多游戏运行时兼容性报告.md` 声称「实测 15 个游戏，覆盖 38 个工具；
工具清单与服务器实际报出的 38 个**逐名核对一致**」，而这 7 个工具在该报告中
出现 **0 次** —— 也就是说，**新增的 7 个工具从未进过多游戏矩阵验证**。

**更值得注意的一点**：脚本**确实**会与服务器实际清单对账（`probe.tools()`），
但发现不一致时只 `print("⚠️ 清单不一致…")` —— **不失败、不退出、不影响报告生成**，
不一致的那份报告照样能产出。这与 §9.3「不许假成功」是同一类问题：
**有检查，但检查不拦人**。

**为什么我没有当场改**：这需要真的跑一遍多游戏矩阵（要开游戏、注入、耗时很长），
而当前会话的目标是产出评审文档。补清单本身是一行改动，但**验证它有效**需要
完整跑一次矩阵 —— 按 §9.3，没验证过的改动不该提交。

### 11.2 ⚠️ 语义标注可能过严：`drain_events` 标了 `destructiveHint=True`

| 工具 | 标注 | 实际行为 |
|---|---|---|
| `drain_events` | `destructiveHint=True`、`idempotentHint=False` | **取走即消费**事件队列 |

**这一条不是缺陷**（VERIFY 脚本明确记录了理由：事件被消费掉就没了，
标成只读会让客户端以为重试无害），但值得外部视角判断：
`destructiveHint=True` 在部分客户端会触发**确认弹窗**，
而「读走自己的事件缓冲」与「破坏游戏数据」在用户感知上不是一回事。

同源问题：`eval_script` 标破坏性**完全合理**（任意 JS 注入），
但它与 `drain_events` 现在给出了**相同**的两个语义位 —— 客户端无法区分
「读缓冲」与「任意代码执行」的风险等级。

### 11.3 ⚠️ 5 个「只读」工具会写会话状态（**历史报告中已记录，转述至此**）

| 工具 | 标了 | 实际行为 |
|---|---|---|
| `search_classes` / `search_fields` / `search_methods` / `class_hierarchy` / `find_derived_classes` | `readOnlyHint=True` | `_paged` 每次调用都 `results.put(...)` 写句柄表 |

`ResultStore` 是 **32 条 LRU**（`engine/index.py:376`）—— 也就是说
**一次新搜索能让先前拿到的句柄失效**。

按严格的「改了会话状态就不算只读」标准，这 5 个的标注是**偏乐观**的。
但改成非只读会让 5 个最常用的查询工具在客户端眼里变成「可能破坏东西」
（`_ann` 对非只读默认 `destructiveHint=True`），**代价明显更大**。

**这是一个真实取舍，需要决策**（此条原记录在 `docs/外部项目评估-REA.md` §5.2，
因为 `docs/` 下的历史报告不参与门禁、外部评审者也读不到，故转述至此）。
两个候选方向：① 保持只读但把「会推进句柄代次」写进 docstring；
② 给 `_ann` 增加一档「只读但改内部状态」。

### 11.4 ⚠️ `idempotentHint=True` 用在开关型工具上是否恰当

实测有 **13 个非只读工具**标了 `idempotentHint=True`：
`capture_screen`、`close_session`、`decompile`、`gc_control`、`inject_process`、
`ocr`、`open_game`、`set_field_value`、`ue_profile`、`unhook`、`verify_state`、
`wait_for`、`write_memory`。

其中大多数没问题（同参数再调一次确实无额外影响）。但有两类值得审视：

- **`gc_control(disable: bool)`**：同一份 docstring 写着「观察结束后**务必恢复**，
  否则游戏内存会持续增长」—— 而 `gc_control(True)` 与 `gc_control(False)`
  是两个不同状态。标 `idempotent=True` 语义上指「重复调用同一参数无额外影响」，
  这站得住；但客户端若把它理解成「这个调用可以随便重试」，
  在一个**开了没关**的会话里就会持续压制 GC。
- **`write_memory` / `set_field_value`**：写同一个值两次确实等价，
  但它们**会改变游戏状态**，标 `idempotent=True` 与 `destructiveHint=True` 并存，
  客户端如何解读这个组合，值得确认。

### 11.5 ✅ 已确证的不一致：若干 `devtools/*.py` 里残留旧工具数

这些**不在门禁覆盖范围内** —— 门禁只管 `README.md` / `devtools/README.md` /
`SKILL.md` / `AGENTS.md` 四处活文档的数量声明，以及 README 的工具表。
脚本注释与断言标签里的旧数字没人管：

| 位置 | 写的 | 实际 |
|---|---|---|
| `report_runtime_matrix.py:11,86,810-811` | 38 个工具 | 45（见 §11.1，这条是真的漏了） |
| `verify_tool_annotations.py:1,154` | 「38 个工具都写全了标注」 | 45（**断言本身是按实际数跑的**，只是文案旧了） |
| `verify_cap.py:204,356,363,406,410` | 38 个工具 | 45（同上，注释与标签旧了） |
| `verify_mcp_context.py:15,152,165,166,177` | 38 个工具 | 45（同上，部分检查原本就设计成不写死数值） |

> **`gen_docs.py:30,235-237` 不算残留**：它提到的「44 个工具」是**注释里说明
> 历史上曾硬编码过哪些位置**，而那些位置现在**由 `gen_docs.py` 自动改写数字**
> （`_fix_inline_numbers()`：只替换数字、不动措辞，每次生成再对齐一次）。
> 也就是说那 5 处**已经有护栏**，是正例而非缺陷。

**性质区分**（重要，别一概而论）：
- §11.1 的 `ALL_TOOLS` 是**真漏了**（清单本身错了，报告覆盖不到那 7 个工具）。
- 其余几处多是**注释/标签文案陈旧**，其中 `verify_cap.py` / `verify_mcp_context.py`
  的注释里**已经写明**「本意是『装饰器没把工具弄丢』，不是『恰好 38 个』」——
  那是**有意的**、防止有人把数值写死的设计，不该当缺陷改。

**为什么我没有当场改**：这类「文案里的旧数字」改了不影响任何行为，
但会让 `git diff` 混入大量与本批无关的改动（AGENTS.md §6.1 要求
「一批 = 一个自洽的改动单元」）。**如实列出，交由后续决定。**

### 11.6 疑问：`verify_tool_annotations.py` 的硬编码分组表会随工具增长而腐坏

该脚本靠**三张手工维护的分组表**（只读本地 / 只读但要游戏进程 / 非只读）
与代码双向对账，新增工具不在表里就报红。这个设计是**好的**
（逼着作者当面表态），但它意味着**每加一个工具都要手工同步一张表**。

结合 §11.1 的教训（手工维护的清单必然漂移），值得评估：
这份表有没有办法从 `_ann()` 的调用处**自动导出**，而不是手抄？
注意这里有个张力：自动化之后，「逼作者表态」的强制力可能就没了 ——
可能**故意手抄**才是对的。请评审者判断哪一边更重要。
