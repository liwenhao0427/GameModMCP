### 3.1 P1-2：缓存命中不再全量解析元数据（**优先做这个**）

**问题**：`index.py:239` 在查缓存（`:249`）**之前**就调了 `_load_meta`，
所以即使缓存命中，也要把整份元数据解析一遍，然后**只为了拿一个引擎名**。

**实测（本轮 `bench_index.py`）**：

| 引擎 | `_load_meta` 全量解析 | 缓存命中 `Index.open` | 强制重建 | 纯 SQL 下限 |
|---|---|---|---|---|
| IL2CPP（20,072 类型） | **497 ms** | **528 ms** | 1,391 ms | 3.3 ms |
| Mono（1,387 类型） | **64.5 ms** | **67.1 ms** | 116 ms | 3.5 ms |

→ **缓存命中里约 92~94% 的成本是那次全量解析**，理论下限只要 3~4 ms。

**可行性已实测确认**（这是关键，别凭推断）：

`Index.open` 里那次解析**只用来算两件事**：引擎名 → 拼 `db_path`。
而引擎名可以只读 8 字节得到：

```
_sniff_engine（只读文件头）  IL2CPP 0.244 ms / Mono 0.209 ms
adapt.engine_of（需全量解析） 两者结果**与嗅探完全一致**
```

所以缓存命中路径可以做到**完全不解析**。实测该路径：

| 引擎 | 不解析的缓存命中 | 说明 |
|---|---|---|
| IL2CPP | **27.1 ms** | 其中 27.1 ms 全是 16.5 MB 的 sha256（纯 I/O，省不掉） |
| Mono | **6.5 ms** | 2.2 ms sha256 |

→ 即 **528 ms → ~27 ms（IL2CPP）**、**67 ms → ~7 ms（Mono）**，
而且省下的是 CPU 不是 I/O。

**实现要点（已排查完，直接照着做）**：

1. `_attach`（`index.py:162`）把 `meta` 设成实例字段。全仓库**没有任何
   `index.py` 之外的地方消费 `idx.meta`**（已 grep 核实），所以可以改成
   惰性属性：命中缓存时先不解析，第一次访问 `.meta` 时才 `_load_meta`。
2. 但要注意 `index_info`（`index.py:467`）会调 `adapt.capabilities(self.meta)`，
   而 `capabilities` **不需要解析**——它只回答「这个引擎支不支持某能力」。
   可以改成从引擎名推导，避免「查个信息就把 500 ms 解析拉起来」。
3. `_direct_children`（`index.py:1163`）会遍历 `self.meta.types` 构建直接子类映射。
   这是**唯一**真正需要全量类型的路径（`class_hierarchy(down)` 用）。
   惰性化后它照旧触发解析即可——即「用到才付钱」。
4. `close()`（`index.py:282`）调 `self.meta.close()`，惰性后要处理「从未解析」
   的情况（`meta` 可能是 `None`）。

**验收方式**：`bench_index.py` 前后对比 + `run_all_verify.py` 全绿。
另外**顺带修一个真实的脆弱断言**——见 §五「已发现的缺陷」第 3 条。

### 3.2 P1-3：句柄改惰性（**先看清收益再决定**）

**问题**：`search_*` 会把**全量**结果解析一遍塞进句柄，**与 `limit` 无关**。

**实测**：

| 场景 | 总耗时 | 其中「解析全部进句柄」 | 占比 |
|---|---|---|---|
| IL2CPP 全表 `search_classes('')`（20,072 行） | 94 ms | 40 ms | **43%** |
| IL2CPP `search_classes('Player')`（344 行） | 12.3 ms | 0.6 ms | 5% |
| Mono 全表（1,387 行） | 6.3 ms | 2.8 ms | **44%** |
| Mono `search_classes('Player')`（28 行） | 0.8 ms | 0.1 ms | 6% |

**判断**：收益**只在 `pattern` 很宽时**才显著（宽查询里 43% 是可省的）。
窄查询下解析成本可忽略。所以：

- 值得做，但**优先级低于 P1-2**（P1-2 是每次都付 500 ms，P1-3 只在宽查询付 40 ms）。
- 做的话，正确形状是「句柄只存主键，翻页时再查再解析」，
  而不是「把解析结果缓存起来」——后者没省掉解析。

### 3.3 P1-4：`subtype_of` 下推 SQL —— **文档的说法是错的，先改文档**

**这一项要特别小心**：`docs/项目梳理与优化建议.md` §4.8（第 415-422 行）称
`search_classes(subtype_of=...)`「**20,072 类型规模下每次调用都是秒级**」。
**本轮实测证明这个说法不成立**：

| 查询 | IL2CPP | Mono |
|---|---|---|
| `pattern=''` | 76.6 ms | 4.2 ms |
| `pattern=''` + `subtype_of` | 69.1 ms | 5.0 ms |
| `pattern='Player'` | 13.1 ms | 0.7 ms |
| `pattern='Player'` + `subtype_of` | 13.3 ms | 0.7 ms |
| **继承过滤净增成本** | **−7.5 ms** | **+0.8 ms** |

即继承过滤**根本不是瓶颈**（IL2CPP 上甚至为负，属测量噪声量级）。
真正的瓶颈是 `pattern=''` 时的**全表扫描 + 全量解析进句柄**（即 P1-3）。

该节还有两处引用错误：

- 称「`SKILL.md:254` 推荐的正是 `search_classes(subtype_of=..., limit=2000)`」——
  `SKILL.md` 里 `subtype_of` **只出现在第 111 行**，且**不带 `limit=2000`**。
- 第 417 行称走 `meta.is_subclass_of` —— 实现确实如此（`index.py:595`），
  但既然它不慢，`type_ancestors` 闭包表的收益就要重新评估。

**结论**：**先改文档**（把「秒级」改成实测值），再决定要不要做。
若做，收益是「宽查询里省掉 Python 侧全表过滤」，不是「秒级变毫秒级」。

## 五、已发现的缺陷

### 1. 四个脚本缺 UTF-8 stdout 设置 → 在 GBK 控制台直接崩 ✅ **已修**

**先说结论，再说教训**：真正缺 `sys.stdout.reconfigure(encoding="utf-8")`
的是 **4 个**，不是最初以为的 2 个：

| 脚本 | 症状 |
|---|---|
| `verify_tool_coverage.py` | 直接运行抛 `UnicodeEncodeError: 'gbk' codec can't encode '\u2705'` |
| `report_tool_coverage.py` | **失败路径**崩溃：门禁本该列出「哪个工具没被覆盖」时自己崩掉，把可操作的报错变成看不懂的编码错 |
| `run_all_verify.py` | **最严重**：19 个脚本全跑完、结论却拿不到 —— 汇总打印 `[✅] xxx` 时崩 |
| `samples.py` | 直接运行（`python devtools\samples.py`，排查样本可用性时的第一选择）崩在最后一行 |

**为什么最初只找到 2 个（这是一条真教训）**：
当时用 `re.search(r"reconfigure|TextIOWrapper", ...)` 扫全仓库，
命中的跳过 —— 但 `run_all_verify.py` 与 `samples.py` 里**有**这两个词以外的
UTF-8 相关代码（前者用 `encoding="utf-8"` 读**子进程**输出），
于是被误判成「已经处理过」。**「提到了 utf-8」不等于「设置了 stdout 编码」**。
第二次改用「先找会打印非 GBK 字符（`✅❌⚠️★💥`）的脚本，再查它有没有
reconfigure」才找全。

**另一条被写错的原因，已订正**：本文件曾称「`run_all_verify.py` 会设
`PYTHONIOENCODING`，所以套件里跑不出来」。**这是错的** ——
`run_all_verify.py` 只设 `PYTHONPATH` 与 `GAMEMOD_COV_OUT`，
**从来没设过 `PYTHONIOENCODING`**。所以套件里同样会踩到，
只是当时那条命令恰好带了 `$env:PYTHONIOENCODING="utf-8"`。
（`encoding="utf-8"` 是**读**子进程输出，管不到子进程**写** stdout。）

**修法**（全项目统一模式，照 `verify_mcp_decompile.py:33`）：

```python
try:
    sys.stdout.reconfigure(encoding="utf-8")
except Exception:
    pass
```

**验证方式**（必须清掉 `PYTHONIOENCODING`，否则测不出真问题）：

```powershell
Remove-Item Env:\PYTHONIOENCODING -ErrorAction SilentlyContinue
python devtools\samples.py                          # 现正常列出样本，退出码 0
python devtools\verify_tool_coverage.py             # 现正常列出 ✅，退出码 0
python devtools\report_tool_coverage.py --strict    # 现能打印未覆盖清单
python devtools\run_all_verify.py                   # 现能打出汇总表，退出码 0
```

四条都已实测：修复前用同样的字符可复现 `UnicodeEncodeError`，
修复后全部退出码 0（`run_all_verify.py` 在无 `PYTHONIOENCODING` 的
GBK 控制台下实测 19/19 通过 + 覆盖率门禁通过）。

**已固化为永久验收脚本** `devtools/verify_encoding_console.py`（9 项断言，
2.3 秒，无需游戏）。它做两层：

1. **静态**：`devtools/*.py` 里凡含「GBK 编不出的字符」的文件，都必须设过
   stdout 编码（`reconfigure` 与 `TextIOWrapper` 两种写法都接受）。
2. **运行时**：挑 5 个快且无副作用的脚本，**显式剥掉 `PYTHONIOENCODING`**
   后真跑一遍，断言退出码 0 且 stderr 无 `UnicodeEncodeError`。

第 2 层不可省：第 1 层只能证明「看起来设了」，证明不了真的没崩。
该脚本已实测**非空转** —— 临时移除 `samples.py` 的编码设置后，
静态层与运行时层**各自独立报错**（`❌ samples.py 含 '⚠✅️'` +
`UnicodeEncodeError: 'gbk' codec can't encode '\u2705'`），还原后回到 9/9。

> 这个坑之所以长期存在，是因为**开发时通常带着 `PYTHONIOENCODING`
> 或重定向输出**，两者都会掩盖问题。所以检查里专门有一条断言：
> 「子进程环境里确实没有 `PYTHONIOENCODING`」—— 否则检查本身失效。

同时给 `run_all_verify.py` 加了 `--only <脚本名>`（可重复），
用于单跑某个脚本排查：

```powershell
python devtools\run_all_verify.py --only verify_index
```

`--only` 有两个必须的配套行为（都不是「顺手加的」）：

- **自动跳过覆盖率门禁**。只跑子集不可能覆盖全部工具，
  硬跑门禁只会得到一个恒假的「未覆盖」结论。
- **不清空覆盖率日志**。`verify_encoding_console.py` 会以 `--only` 嵌套调用
  `run_all_verify.py`（就为了覆盖「汇总表打印」那条崩过的路径）；
  若嵌套这次把日志删了，就会抹掉外层跑到一半已积累的证据，
  外层门禁随之报假失败。

> **写这个脚本时踩到的坑，值得记下来**：最初 `verify_encoding_console.py`
> 直接调 `run_all_verify.py` 全套，而后者会 glob 到 `verify_*.py` ——
> 于是**自我递归**，实测把机器 CPU 跑满、600 秒不返回。
> 教训：**任何会被 `run_all_verify.py` 自动收录的脚本，
> 都不许再无条件调用它自己**。

### 6.2 `_probe_parent_sem.py` 的结论**作废**（重要教训）

该探针想核实 `types.parent_il2cpp` / `declaring_il2cpp` 列，得出「0% 匹配」，
看起来像产品 bug。**实际上是探针自己错了**：

这两列由 `adapt.declaring_ref` / `adapt.parent_ref` 写入，
**不是 type 表下标**，不能和 `types.idx` 关联：

- IL2CPP：两者都是 **Il2CppType 索引**；
- Mono：`parent_ref` 是 `extends_ref`，即 **TypeDefOrRef 编码值**
  （低 2 位是 tag：0=TypeDef / 1=TypeRef / 2=TypeSpec，真行号要 `>> 2`），
  `declaring_ref` 是 `parent_index`。

`index.py:381-382` 已写明它们「只用于『有没有外层/有没有基类』的判断，
不参与进一步索引」。**真实基类名只能走 `adapt.parent_name(meta, t)`。**
任何用 type 索引映射去解这两列的探针都是**范畴错误**。
