### 3.1 P1-2：缓存命中不再全量解析元数据 ✅ **已完成**

**问题**：`Index.open` 在查缓存**之前**就调了 `_load_meta`，
所以即使缓存命中，也要把整份元数据解析一遍，然后**只为了拿一个引擎名**。

**修法**：`open()` 改用 `_resolve_engine()`（只读文件头 8 字节）定引擎名，
命中缓存时 `_attach(None, ...)`，元数据由 `meta` 属性**按需解析**。
配套三处：`close()` 要处理「从未解析」；`index_info()` 改用
`adapt.capabilities_of(engine)`（不解析也能答）；`_direct_children`
照旧经 `meta` 属性取，即「用到才付钱」。

**实测（`bench_index.py`，修复前 → 修复后）**：

| 引擎 | `_load_meta` 全量解析 | 修复前缓存命中 | **修复后缓存命中** |
|---|---|---|---|
| IL2CPP（20,072 类型） | 482.1 ms | 528 ms | **19.6 ms** |
| Mono（1,387 类型） | 62.1 ms | 67.1 ms | **5.0 ms** |

省下 96%（IL2CPP）/ 92%（Mono），剩的 ~19.6 ms 里大头是 16.5 MB 文件的
sha256（纯 I/O，省不掉），纯 SQL 下限 3.4 ms。

**确定性证据（不是时间）**：`bench_index.py` 与 `verify_adapt.py` 都断言
「缓存命中后 `idx._meta is None`」—— 直接回答「到底有没有解析」，
不受机器负载影响。两条断言均已实测**非空转**（改回旧行为即报红）。

**附带修掉一个假断言** —— 详见 §五.4。原 `verify_adapt.py:221` 的
「二次打开比首次快」比的是**两个缓存命中**，与 P1-2 无关，
且修完 P1-2 后退化成 `0.00s < 0.00s`。已改为三条确定性断言
（`cache_hit` / `_meta is None` / 嗅探引擎 == 解析引擎）。
`verify_adapt` 现稳定 **52 项 / 0 警告**（连跑 6 次无抖动）。

> **另外，旧文档把「被 P1-2 救活的断言」认错了**。真正因为 P1-2
> 才变稳的是 `verify_mcp_tools.py` 里那两条二次 `open_game` 断言
> （现位于 152-157 行；P3-1 的插入把它从 117 行推后了）：
> 它断言二次 `open_game`
> `< 1.0s`，而修复前 IL2CPP 的缓存命中有 528 ms，**离阈值只剩一倍**
> —— 这才是「机器一忙就可能红」的那条。现在实测约 20 ms，

### 3.2 P1-3：句柄改惰性物化 —— ✅ **已完成**

**问题**：`search_*` 会把**全量**结果解析一遍塞进句柄，**与 `limit` 无关**。

**实现形状**（与当时的建议一致，是「惰性」不是「缓存」）：
新增 `_RowSource(rows, convert)` —— 句柄只登记**原始行 + 解析函数**，
`slice(offset, limit)` 时才解析取到的那一页；`all()`（全量物化）只在
`read_query_result(pattern=...)` 跨结果过滤时调用。
`QueryResult.items` 这个「已物化的列表」字段因此消失，换成 `source` + `total` 属性。

> 注意：**没有**把行再回去查一次 SQL（「句柄只存主键」那种做法）。
> 行本来就已取回内存（`sqlite3.Row` 只是元组，很廉价），
> 昂贵的是把它解析成 dict —— 所以只把**解析**推迟就够了，
> 省掉了「翻页要重放 SQL」带来的排序/一致性问题。

**实测（改前 → 改后）**：

| 场景 | 改前 | 改后 | 省 |
|---|---|---|---|
| IL2CPP `search_classes('')`（20,072 行） | 121.7 ms | **66.9 ms** | 45% |
| Mono `search_classes('')`（1,387 行） | 7.3 ms | **4.4 ms** | 40% |
| IL2CPP `search_classes('Player')`（344 行） | 14.2 ms | 13.6 ms | 4% |
| Mono `search_classes('Player')`（28 行） | 0.9 ms | 0.9 ms | 7% |
| IL2CPP `search_fields('a')`（49,286 行） | ~59 ms | **36.9 ms** | ~37% |
| IL2CPP `search_methods('a')`（79,451 行） | ~89 ms | **65.9 ms** | ~26% |

窄查询的收益依旧可忽略（4%~7%）——**这与当初的判断一致**，
只是宽查询那一档从「40 ms」变成了实打实的省掉。

**证据用计数，不用时间**（`devtools/verify_lazy_handles.py`，46 断言）：

| 断言 | 实测 |
|---|---|
| `search_classes('', limit=20)` 解析条数 | **20**（结果集 16,780） |
| `search_fields('a', limit=20)` 解析条数 | **20**（结果集 49,286） |
| `search_methods('a', limit=20)` 解析条数 | **20**（结果集 79,451） |
| 翻页 `offset=100, limit=5` 解析条数 | **5** |
| 惰性翻页结果 == 全量物化后手动切片 | 逐条相等（**只快没改语义**） |
| `pattern=` 过滤时解析条数 | = 结果集全长（**已知成本**，不是 bug） |

做法是把解析函数包一层计数器（`_row_to_type` 打在实例上、
`adapt.resolve_field`/`resolve_method_return` 打在模块上），
直接回答「到底解析了多少条」。

**反证已做**：把 `_RowSource.slice` 改回「切片前先全量物化」，
12 条断言立刻报红（退出码 1）；还原后与备份逐字节一致。
注意**语义类断言**（逐条比对）在反证时**不会**报红 ——
说明「只快不对」与「快了又对」被分开把守了，这正是想要的。

`read_query_result` 的 docstring 也已补上这条差异：纯翻页只解析一页，
带 `pattern` 要全量解析，所以缩小范围应优先用 `search_*` 的参数。

### 3.3 P1-4：`subtype_of` 的耗时 —— **文档错了两次，第二次是我自己错的**

**第一次错（原文）**：`docs/项目梳理与优化建议.md` §4.8 称
`search_classes(subtype_of=...)`「**20,072 类型规模下每次调用都是秒级**」。
不成立。

**第二次错（本文件早期的订正）**：我当时把它改成
「继承过滤根本不是瓶颈，IL2CPP 上甚至为负（−7.5 ms），属测量噪声」——
**这个结论同样是错的**，而且错得更有教育意义。

错因是**量法**：那个数字来自 `bench_index.py` 的「5 次取最小值」。
两条耗时接近的代码路径做差时，**取最小值等于专挑噪声里最有利的那一次**：
同一个查询两次跑分别得到 **−4.9 ms** 与 **+14.7 ms**，符号都能翻。
**「最小值」适合量单条路径的最优成本，不适合量两条路径之间的微小差值。**

**订正后（改量分布）**：`devtools/bench_index.py` 的 `[P1-4]` 段
（每条路径 12 轮，打印最小/中位/最大；**量具本身也已改掉**，
不再用「取最小值」量差值）：

| | 最小 | 中位 | 最大 |
|---|---|---|---|
| IL2CPP `pattern=''` | 44.0 ms | 47.8 ms | 51.2 ms |
| IL2CPP `+ subtype_of` | 68.4 ms | 70.8 ms | 80.0 ms |
| IL2CPP **净增** | **+19.5** | **+23.8** | **+33.1** |
| Mono **净增** | −0.7 | +1.6 | +2.2 |

**IL2CPP 上 12 轮符号全为正 → 是真开销，约 +20~33 ms**（相对 48 ms 基线
约 +50%），但**远不是「秒级」**；Mono 规模小，落在噪声里。

**根因**（比原文的「Python 侧全表过滤」具体）：对**每一行**调一次
`meta.is_subclass_of`（`index.py:711-714`），每次走一遍基类链
→ **O(行数 × 链长)**。同一个形状也在 `find_derived` 里
（`il2cpp_meta.py:997-1007` 对全表逐个判），所以
`find_derived_classes(MonoBehaviour)` 实测 **20.5 ms** 是**同一个根因**。

**订正后的做法**：不必建 `type_ancestors` SQL 闭包表（要改 schema），
更合算的是在 meta 上**惰性缓存一张 parent→children 邻接表**，
`subtype_of` 改为「从基类 BFS 出候选下标集合，再与行取交集」——
一次 O(N) 建表、每次查询 O(后代数)，**同时修好 `subtype_of` 与
`find_derived_classes` 两处**，且不用迁移索引缓存。

该节另有一处引用错误（与性能无关）：称「`SKILL.md:254` 推荐的正是
`search_classes(subtype_of=..., limit=2000)`」—— 实测 `SKILL.md` 里
`subtype_of` **只出现在第 111 行**，且**不带 `limit=2000`**。

**结论**：文档已按上述订正（含「第二次错」的教训），
**并且代码也做了** —— 做法就是下面 §3.3.1 那个「邻接表 + BFS」，
比原设想的 SQL 闭包表省得多（不用改 schema、不用迁移缓存）。

### 3.3.1 ✅ P1-4 实施：`subtype_of` 反过来查

**做法**：在 meta 上**惰性**建父→子邻接表（`_children_map`），
`derived_set(base)` 从基类 BFS 出后代下标集合，`index.py` 拿行与集合取交集。

| 实测（IL2CPP，20,072 类型；隔离计时 20 轮中位） | 改前 | 改后 | 省 |
|---|---|---|---|
| 纯过滤 16,780 行 | 19.00 ms（逐条 `is_subclass_of`） | 0.72 ms（集合查找）+ 2.03 ms（算集合） | **86%** |
| 其中「算后代集合」首次（含建邻接表） | — | 5.87 ms（此后 2.03 ms） | — |
| `find_derived_classes(MonoBehaviour)` | 20.5 ms | **4.9 ms** | **76%** |
| Mono 纯过滤（1,387 类型 / 916 行） | 1.53 ms | 1.99 ms | **+0.5 ms**（刻意不建表） |

`bench_index.py` 的 `[P1-4]` 段（12 轮分布，且已把**首轮单列** ——
首轮要建表，混在一起看会误以为过滤很贵）：
IL2CPP 净增中位 **+23.8 → +8.2 ms**，最小值 **+19.5 → −8.0 ms** ——
**符号不再稳定，说明已落进噪声**（改前 12 轮全为正）。Mono +1.6 → +2.0 ms。

**Mono 为什么不建表**（这是个刻意的取舍，不是漏了）：只有 1,387 个类型，
逐条判定的净增落在噪声里；而 Mono 的基类是**名字**（可能指向外部程序集、
解析不出下标），按名字反推子类图容易在「同名」「跨 dll」两处出错。
代价 +0.5 ms，换来 `index.py` 里只有**一条**代码路径。
两个引擎 `derived_set` 的接口与语义一致，实现策略不同，各自 docstring 写了原因。

**这次最要紧的不是快，是「一模一样」**：`devtools/verify_subtype.py`（61 项）
拿**旧的逐条 `is_subclass_of` 当真值**（它没删，就留在原处），
对 7 个基类名逐条比对集合相等 —— 含 `System.Object`（18,864 个后代）
与嵌套类型名；再守 `find_derived` 的顺序与 limit 截断。

**反证已做**（两个篡改都抓到了，源码逐字节还原）：
把 BFS 改成「只走一层」→ **12 条断言报红**（退出码 1）；
把邻接表缓存改坏 → 计数断言报红。优化继承语义最怕「快是快了、
结果悄悄少了几个类」，所以这一条是重点，不能只靠「快了多少」。

**残留**：稳态那 2.03 ms 来自每次都要扫全表比对基类名（20,072 次字符串比较）。
再往下要么加「按名字的结果缓存」，要么把名字→下标做成多值表；
两三毫秒不值得再加一份状态，**记下不做**。

**一个观察（不是本次引入的）**：Mono 侧 `subtype_of="UnityEngine.Component"`
返回 **0 个后代**，而 `UnityEngine.MonoBehaviour` 有 644 个 —— 因为

只会写 `extends MonoBehaviour`，不会再往上走一层到 `Component`。
这是 Mono 名字链的**既有**限制，本次改动**没有改变**它（等价断言覆盖了这一点），
也没有修 —— 要修得先有真实需求。

### 3.6 P2-5（标注部分）：38 个工具的语义标注 ✅ **已完成**

### 3.7 P2-5（行为部分）：5 处「参数/字段说了话但不干活」✅ **已完成**

3.6 修的是**标注**（说的是不是实话），这一节修的是**行为**（参数收下了做不做）。
五个问题的共同点：**接口上看得见，实现里是空的** —— 这类东西比死代码坏，
因为调用方会以为自己控制了什么。

| # | 位置 | 原来 | 现在 |
|---|---|---|---|
| a | `server.py` `launch_game` | `argv = args.split()` | `_split_argv()`（见下） |
| b | `server.py` `read_field_value` 函数内 | 死导入 `import ctypes` | 删掉 |
| c | `server.py` `read_field_value` | **固定读 8 字节** | 按字段类型读 1/2/4/8 |
| d | `discovery.process_arch` | 第二返回值恒为 `[]`，还被输出成 `architectures: []` | 删掉该字段；位数只看 `is_64` |
| e | `runtime/session.py` `scan_pattern` | `scope` 参数收了、放进 opts，`agent.js` **从不读它** | 删掉参数 |

**(a) `_split_argv`：文档里的建议本身是错的。**

原来的 bug 是 `args.split()` 会把含空格的路径拆成多个参数。旧文档建议改用
`shlex.split` —— 实测**更糟**：

```
shlex.split(r'--path C:\Games\My Game\a.exe --x')
posix=True （默认）-> ['--path', 'C:GamesMy', 'Gamea.exe', '--x']    ← 反斜杠被当转义符吃掉了
posix=False        -> ['--path', 'C:\\Games\\My', 'Game\\a.exe', '--x']  ← 引号没生效
```

Windows 路径全是反斜杠，默认 posix 模式会把 `C:\Games\Game\a.exe` 变成
`C:GamesGamea.exe` —— 照那条建议改等于**引进**一个新 bug。
所以按 Windows 习惯自己拆：空白分隔、双引号内保留空白、反斜杠不是转义符。
`verify_server_helpers.py` 里有 15 条用例（含引号/反斜杠/tab/未闭合引号），
并且**把「`shlex` 默认模式会破坏 Windows 路径」本身也写成了断言** ——
将来有人换回 `shlex.split`，那条会立刻报红。

**(c) 读取宽度：不只是「多读几个字节」。**

`read_field_value` 原来固定读 8 字节。字段只有 1/4 字节时，多读的字节是
**相邻字段**的内容，后果有两个：给出无意义的 `as_int64`/`as_double`
（两个字段拼出来的数），以及在字段贴近页尾时把一次**本可成功**的读取
变成假失败。现在按 `_field_read_width(字段类型)` 读，返回值里多一个
`read_width`，解释字段也按宽度给（1 字节就不给 `as_int32`）。

**(d) `architectures` 恒为空：一个「永远 `[]`」的字段比没有它更容易误导。**

`process_arch()` 的第二个返回值历来写死 `[]`，而 `find_game_processes`
一直把它输出成 `"architectures": []` —— 客户端会读成「没检测到任何架构标记」。
删掉，位数只看 `is_64`。顺带把 `process_arch` 在**拿不到句柄**时的返回值从
`False` 改成 `None`：`False` 是「32 位」，而那时我们**根本不知道**，
`None` 才是「没测出来」（该字段类型本来就是 `bool | None`）。

**(e) 死参数 `scope`：收了却没人用，比死代码更坏。**

`session.scan_pattern(..., scope="")` 会把 `scope` 放进 opts，
但 `agent.js` 只读 `opts.module` / `opts.max_results` —— 全仓库 grep
`scope` 只命中这 3 行（另有两处是 `mono_meta.py` 里无关的 `ResolutionScope`）。
调用方会以为扫描范围真的被限制了。删掉，限定范围用 `module`。
（MCP 工具签名本来就没有 `scope`，所以这不算工具契约变更。）

**反证已做**（两次篡改都跑真实的 `verify_mcp_extra.py`，约 1 分钟一次；
源码 sha256 逐字节还原一致）：

| 篡改 | 报红 |
|---|---|
| `read_width` 改回固定 8 | 4 项。实测读回 `raw_hex=0100000000000000`（1 字节真值 + 7 字节邻居），解释键从 3 个涨到 9 个 |
| 返回里塞回 `"architectures": []` | 「不再有恒为空的 architectures 字段」 |

三档宽度都**端到端**验过（在真实偏移上写标记值再读回来）：

| 字段 | 运行时类型 | 写入 | `read_width` | 读回 |
|---|---|---|---|---|
| `PresetLoaderV2._isLoading` | `System.Boolean` | 1 字节 `0x01` | **1** | `01` |
| `...InteractionDetector._blockInteractFrameCount` | `System.Int32` | 4 字节 `0x11223344` | **4** | `44332211` |
| `PresetLoaderV2.userDataPresetFile` | `UnityEngine.TextAsset` | 8 字节 | **8** | `78563412bebafeca` |

> 挑 int32 那个字段踩了一个坑：`fieldsOf()` 只枚举类**自己的**字段，
> 不走基类链，所以不能借用 `PresetLoaderV2` **继承**来的
> `OffsetOfInstanceIDInCPlusPlusObject`（它是 `UnityEngine.Object` 的）
> —— 得换一个真有 int 字段的类。这类细节只有实测才会暴露。

> 还有一条**空转陷阱**：那两条「`architectures` 没了 / 带 `is_64`」的断言

> —— 机器上没开游戏时它是 0 条，整段断言被跳过、白跑还显示通过。
> 改成按名字查本机的 `python`（本脚本自己就是 python 进程），

### 3.8 P2-1（`outputSchema`）：❌ **量完之后决定不做** —— 本文件唯一一处「建议被否决」

P2-1 在原计划里排第 4，优化建议文档甚至称它「投入产出比最高」。
本轮花了 3 轮探针把 `mcp 1.26.0` 的行为量清楚，结论是**照做会破坏产品**。

**第一层：它真的会校验返回值。** FastMCP 在
`func_metadata.py:119-131` 里对非空 outputSchema 走
`output_model.model_validate(result)`，然后返回
`(text_content, structuredContent)` **两份**。于是：

| 注解 | schema | 实测 |
|---|---|---|
| `-> dict`（现状） | `null` | 只给 text，不校验、不加体积 |
| `-> TypedDict`（必填） | 属性名 + `required` | 少字段 → **`ToolError`**：本项目「成功字段齐全 / 失败只有 `ok`+`error`」的两条路径会让**所有错误返回变成协议错误** |
| `-> TypedDict` + `NotRequired[...]` | **`NotRequired` 被忽略**，仍进 `required` | 同样全炸（本版本**不可用**） |
| `-> TypedDict, total=False` | 属性名、无 `required` | 不炸，但见下 |
| `-> dict[str, Any]` | `{type: object, additionalProperties: true}` | 不炸，但**一个属性名都没有**，等于没说 |

**这里要说清一件容易记反的事**：「失败路径会炸」**不是** MCP 的固有缺陷。
规范允许失败不带结构化内容（有第三方指南明确建议：若 schema 只描述成功，
就不该给失败结果附结构化内容）。炸的是 **FastMCP 的处理方式** ——
它**无条件**校验、**无条件**附带，调用方无法介入。

而本项目还有一层自己的问题：我们的失败**不是** `isError: true`，
而是「协议层成功、信封里 `ok: false`」（这是 AGENTS §3.1 要求的契约）。
于是框架**根本分不出**这次是成功还是失败，也就没法表达成
「只描述成功」的单一 schema。**两条路径的返回形状不同，而 schema 只能有一个。**
—— 这才是本项在本项目上做不了的根因。

**所以复评时机也很明确**：若将来 FastMCP 支持「按结果决定要不要
structuredContent」，或我们绕过装饰器自己构造 `CallToolResult`，再做不迟。

**第二层：`total=False` 的三条新问题（都是实测）。**

1. 声明成 `int` 的字段返回 `None` 时 **`ToolError: Input should be a valid integer`**。
   而本项目**真的会**这么返回（`is_64: None` = 没测出来、`offset: None`）。
   要绕开得把每个数值字段写成 `int | None` —— 38 个工具全套改一遍，
   而且以后**漏写一个字段就是线上 ToolError**。
2. **静默强转**：`int` 字段收到 `"3"` 会被 pydantic 转成 `3` 照常返回。
   与「不许编造」直接冲突。
3. 缺失的键在 `structuredContent` 里被**补成 `null`**。

**第三层：代价是响应翻倍。** spec 建议（**SHOULD**，非 MUST）「返回结构化内容时
同时把 JSON 放进 TextContent」以兼容旧客户端，FastMCP 照做，所以两份都发。
用真实载荷实测：

| 调用 | 现状 text | 加 schema 后线上 | 倍数 |
|---|---|---|---|
| `search_classes('', limit=2000)` | 856,186 B | 1,548,350 B | **1.81×** |
| `search_classes('Player', limit=2000)` | 368,430 B | 679,684 B | **1.84×** |

**第四层：那条「绕开」的路不合规。** 手写 `outputSchema` 挂上去、但不返回
`structuredContent` —— spec 原文是 **MUST**：

> Servers MUST provide structured results that conform to this schema.
> Clients SHOULD validate structured results against this schema.

（规范页 `specification/2025-06-18/server/tools` 的 Output Schema 一节。
本机抓取那页时中段被工具截断，所以这句是**逐字引自**
[第三方指南的引用](https://mcp.zovo.one/guides/mcp-structured-tool-output)，
并由两个独立实现佐证：[mcp-go 的文档](https://pkg.go.dev/github.com/mark3labs/mcp-go@v0.55.0/server)、
以及一个因「声明了 outputSchema 却不出结构化内容」而修的校验器
[IBM/mcp-context-forge#4208](https://github.com/IBM/mcp-context-forge/issues/4208)。
**这一条我标注为「引文可信但非我亲读规范原文」**，别当成一手证据引用。）

**结论：不做。** 返回结构继续由 docstring 承载。
将来 `mcp` 若支持「只给 schema、不校验、不重复内容」，可以重新评估。

|---|---|---|

### 3.10 P2-4a：结果句柄跨索引不隔离（**错数据**）—— ✅ 已修

原计划里这属于 P2-4 的一个子项（优化建议 §4.16），本轮先把它单独修掉，
因为它是**正确性**问题，且 P2-4 的「自动转句柄」还要往句柄上挂更多东西 ——
底下的句柄本身不隔离，挂得越多错得越多。

**先证实它是真缺陷**（文档里已经有「凭推理下结论、结果记错」的先例，
所以这次先跑现场）：`ResultStore` 是 `Index` 的实例属性，切游戏就换实例、
序号从 0 重来，而句柄是 `f"{kind}-{n}"`：

```
IL2CPP  search_classes('Player') -> 句柄 'classes-1'，首条 PlayerPrefsController
切 Mono  search_classes('a')     -> 句柄 'classes-1'，首条 __StaticArrayInitTypeSize=26136
再读 IL2CPP 那个句柄              -> ok=True，读出来的是 Mono 的那一条
```

**`ok=True` 但数据是另一个游戏的** —— 假成功，红线。

**修法**：句柄 = `{引擎}-g{代次}-{kind}-{n}`，代次来自
`ResultStore._EPOCH`（进程内每新建一个句柄表 +1）。
两点值得记住：

- **唯一性必须由「实例代次」保证，不能靠「游戏指纹」**。优化建议原来提的是
  `{engine}-{sha16[:6]}-classes-3`，那样同一个游戏**重建索引后仍会撞名**。
- 引擎段只为可读性：只带引擎名不够，同引擎的两个游戏会撞名
  （`il2cpp` 与 `il2cpp`）。验证脚本里这两条都钉住了。

失效时的返回也改了：除了 `available_handles`，`hint` 现在直接给出
**当前会话的前缀**（`il2cpp-g3-`），Agent 一眼能看出手上那个是旧会话的。

验收：`devtools/verify_handle_scope.py`（20 项，需 IL2CPP + Mono 两个样本），
含**非空转反证**：把新句柄的引擎段与代次段剥掉，两者都还原成 `classes-1`
—— 证明旧格式确实撞名。没有这条反证，「两个句柄不相等」也可能只是
「格式改了」而已。反向也测了：同会话内 offset/limit/pattern 三种翻页照旧。

### 3.11 P2-4：统一响应体积上限（256 KB）—— ✅ 已修

§3.9 量出来的 836.1 KB 是真的会砸进 Agent 上下文，所以这一批把它收口。

**落在装饰器，不落在 `_ok()`** —— 这是量出来的，不是设计洁癖：
38 个工具里**只有 25 个**走 `_ok()`，而超限最严重的
`find_derived_classes` / `class_hierarchy` / `class_detail` / `runtime_class_info`
**恰恰都不走它**。所以 `@_cap_response` 包在所有工具函数外层，
拿到的是「最终要发出去的那个 dict」。

**两个 payload 形状 ⇒ 两条截断路径**：

| 形状 | 例子 | 做法 |
|---|---|---|
| 有 `handle`（`_paged` 给的，指向**完整**结果集） | `search_*` | **复用**这个句柄，不再另造 |
| 无 `handle` | `find_derived_classes` / `class_hierarchy` / `class_detail` | 完整列表登记进**会话级** cap 句柄表 |

**复用路径里藏着一个会静默丢数据的坑**：`items` 是
`offset .. offset+limit` 这一段，续读必须从 `offset + keep` 开始，
按 `keep` 算会**跳过**前面那些条。`verify_cap.py` 第 4 节专门用
`offset=1000` 钉住它（`offset=943` 与 `offset=1943` 的区别）。

**cap 句柄表挂在 `SessionState` 而不是 `Index`**：纯运行时工具
（没有索引）也会返回大列表，挂 `Index` 上那种句柄就永远登记不了。
`close_index` 会清空它，于是「切游戏 ⇒ 旧句柄全失效」仍是一条统一规则。

**两个刻意的保守选择**：

1. **测量宁可偏大。** `cap.measure()` 用标准库
   `json.dumps(ensure_ascii=True, indent=2, default=str)`，非 ASCII 按
   `\uXXXX` 的 6 字节算 —— 估出来只会比线上大（实测纯 ASCII 大 900 B、
   含中文大得更多）。偏大只是偶尔少回几条，偏小才是真超限。
2. **不递归截断。** 实测超限字节的 **92.8%~93.9%** 集中在**一个**顶层列表上
   （`items` / `down` / `methods`），只截它；递归截断会让「哪里被截了」不明显。
   体积不在列表里时（如 `decompile` 的 `source`）**不截**，只标 `oversize`
   —— 宁可超限，也不悄悄丢字段。

**踩到的坑（都留在代码注释与验收里了）**：

| 坑 | 现象 | 修法 |
|---|---|---|
| 拿「单独序列化列表」当分母 | 把列表在 dict 里多缩进一层的字节算进"其它"，`search_classes` 少回约 20%（514 而不是 612 条） | 改成「把列表清空再量一次」，便宜且恰好是「除它之外的全部字节」 |
| 量探针时还没有 `note` | 截断后补写的 `capped`/`note` 也占字节，实测**超出 160 B** | 留 `RESERVE_BYTES = 2048` |
| 装饰器打断了工具清单解析 | 38 个工具的 `@mcp.tool` 下多了一行 `@_cap_response`，`verify_tool_inventory.py` 解析出 **0 个工具**并报红 | 规则改成「跳过所有装饰器行」——装饰器以后还会加 |
| **脚本「单独跑绿、进套件红」** | 验收脚本用 `S.search_classes.__wrapped__` 拿原函数；而**动态覆盖率垫片**（`_cov/sitecustomize.py`）会在导入完成后把模块属性换成它自己的记录包装器，那个包装器**没有** `__wrapped__` → 单独跑全绿，`run_all_verify.py` 里 `verify_cap` / `verify_response_size` 双双 `AttributeError` | 在 `server.py` 里显式登记 `RAW_TOOLS = {工具名: 原函数}`，脚本一律用它。**教训**：凡「依赖模块属性被谁包过」的写法都不可靠；也说明**改动必须进套件跑一遍才算验过**，单跑不算数 |

> 最后一条还有个小尾巴：`_cap_response` 因为要登记 `RAW_TOOLS` 而带了**副作用**，
> 于是第 8b 节用 `S._cap_response(lambda: ...)` 测兜底时，顺手把 `<lambda>` 也
> 登记了进去，让第 13 节「`RAW_TOOLS` 恰好等于 38 个工具」多出一条
> —— 又是**只有进套件才红**。测试已改成 `finally` 里恢复快照，用完即还原。

**验收**（两个脚本分工，都是纯静态、不需要注入）：

- `devtools/verify_cap.py`（51 项）：机制。纯函数层测「没超限时**原样返回**」
  （`is` 同一对象）、`has_more`/`returned` 是否说实话、复用句柄的续读 offset、
  没有句柄表时**不假装有**、非列表超大体**不丢**、`_cap_response` 兜底
  （循环引用载荷不让工具失败）；端到端层测「截断后的前 N 条 == 未截断的前 N 条」
  与「分页取回的完整列表与未截断时一模一样」；装饰器层测「38 个工具的入参
  schema 与原始签名完全一致」。**三处非空转反证**：
  上限调大后同一载荷不再被截、调到 4 KB 后小载荷也会被截、
  去掉 `functools.wraps` 后签名立刻退化成 `(*args, **kwargs)`。
- `devtools/verify_response_size.py`（26 项）：体积。用
  `S.RAW_TOOLS[...]` 调**未套上限的原函数**量「截断前」，
  再量真实 FastMCP 出参，断言「7 个调用里每一个的真实线上字节 ≤ 上限」。
  （**不要**用 `S.<工具>.__wrapped__`：动态覆盖率垫片会把模块属性换成
  自己的包装器，那个包装器没有 `__wrapped__`，于是「单独跑绿、进套件红」。
  这就是 `RAW_TOOLS` 存在的原因，见下面的坑表。）

**结果**：最大真实线上字节 **836.1 KB → 254.2 KB**，
`class_hierarchy` 那条（248.7 KB）未超限、原样返回。
`search_classes('', limit=2000)` 从 2,000 条变 607 条 + 一个句柄，
分页取回 16,780 条一条不丢。

**合并后用同一套框架再量一次**（不是另跑一套）：全套 27/27 通过、
动态覆盖率 38/38，而覆盖率报告是**另一个序列化器**（紧凑 JSON、
无缩进）独立量出来的，它给出的最大返回体是 220,132 B（`search_classes`）
—— 与 `cap.measure()` 的保守估计结论一致（后者偏大，因为按 `ensure_ascii=True`
和缩进算）。

### 3.13 P2-3：`Context` 进度与取消 —— ❌ **量完之后决定不做**（第二个被否决的）

计划是「给 `open_game` / `launch_game` / `ue_profile` 加进度与取消」。
量完的结论是**两半都不做**，而且原因不是「麻烦」，是**够不着**。

| 协议面 | 客户端（DSH）实测 | 服务器这一侧 | 结论 |
|---|---|---|---|
| `notifications/progress` | `dsh-mcp-client` 调工具时只传 `{signal, timeout, toolDefinition}`，**从不传 `onprogress`** | 没有 `progressToken` 时 `report_progress` **直接 return**（第 2 节实测 0 条通知）；且它是 `async def`，38 个同步工具根本调不了 | ❌ |
| `notifications/cancelled` | **确实会传** `AbortSignal` —— 协议面是通的 | 但 `RequestContext` **没有任何取消字段**，`Context` 也没有 `cancelled`；更根本的是 FastMCP 对同步工具**内联调用**（`return fn(...)`，不开线程），事件循环被占满，**那条取消通知根本读不到** | ❌ |
| `notifications/message` | 只有通用 SDK 里有，**没有任何 `dsh-*` 包消费** | —— | ❌ |
| tasks 扩展 | 客户端桥**直接抛错**：`requires task-based execution, which this bridge does not support` | 38 个工具都没声明 `execution`（没踩这个坑） | ❌ |

**最硬的一条**是取消：FastMCP 的 `call_fn_with_arg_validation` 里，
同步工具走的是 `return fn(**arguments_parsed_dict)`（`func_metadata.py:95`）——
既不开线程、也不 `await`。所以工具体在**事件循环上直接跑到底**，
期间入站消息一条都读不进来。`notifications/cancelled` 只能等工具**跑完之后**
才被处理，那时结果早算出来了。**这不是「没实现」，是结构上不可达。**

要让它可达，得把三个长任务改成 `async def` + `await anyio.to_thread.run_sync(...)`
包一层 —— 那是三个工具的结构性改造，风险实打实（同步逻辑搬进线程、
`cap.py` 与装饰器链要重新过一遍），而协议那头的收益**恰好是客户端不消费的**。

**代价写清楚**：一个 60 秒的 `launch_game` 期间，这个服务器什么也做不了
（连 ping 都答不了）。这是**已知且接受**的行为，不是疏漏。
真要改的触发条件很明确：**客户端开始传 `onprogress` / 开始消费 tasks**。

**验收是「决策门禁」而不是行为测试**：`devtools/verify_mcp_context.py`（20 项）。
没有行为可测（功能没做），它钉住的是**否决所依赖的事实**：

1. **防漂移**：38 个工具没有一个吃 `Context` 参数、`server.py` 里连
   `Context` 这个词都没有、没有一个工具声明 `execution`。
   将来谁想加，第一步就得先把这些断言弄红 —— 逼一次讨论。
2. **行为实验**（不是读源码猜测）：无 token 时发出 **0** 条通知，
   有 token 时发出 **1** 条。后者是**非空转反证** —— 证明「0 条」
   不是因为我实验写坏了。
3. **结构事实**：`RequestContext` 的 8 个字段全是非取消的、
   `Context` 没有 `cancelled`、FastMCP 确实内联调用同步函数。
4. **SDK 版本事实**：`TaskExecutionMode` 的三个取值记录下来，供将来对照。

第 5 节是**脚本内的非空转反证**（学 `verify_cap.py` 的做法，让它每次跑都验一遍）：
塞一个吃 `ctx` 的假工具 → 检测器必须报出来；把 `report_progress` 换成
「无视 token 一律发送」→ 「0 条」那行必须报红；两者复原后必须重新变绿。
实测：翻转各触发**恰好 1 条**报红，且是**对的那一条**。

> **客户端证据为什么不能自动验证**：那四条是在
> `E:\DSH\resources\app.asar` 里检索 JS 得到的，而那是**客户端安装目录**、
> 不是本仓库的东西。所以脚本里只钉 SDK 那一侧，客户端那一侧留在文档里，
> 并明确标注「换客户端要重新量」。

### 3.14 P3-2：索引缓存会一直长大 —— ✅ 已修（P3 至此清空）

**先说这是个「量出来才敢下手」的活。** 优化清单里 P3-2 只有一行
「缓存目录 LRU/TTL；长期运行的整洁性」，没有任何实测支撑。开跑之前先量了本机：

```
C:\Users\Administrator\.gamemod\cache
  il2cpp-b6304a75b752e1ac.sqlite   26,356 KB
  mono-27b7ee933801e9b2.sqlite      1,384 KB
  总计 27.1 MB / 2 个文件
```

再看键的取法（`index.py`）：缓存名 = `<引擎>-<元数据 sha256 前 16 位>.sqlite`。
**这个键选得对**（换游戏、换版本必定重建，不会串数据），但副作用是：

> 「玩过多少游戏」**加上**「游戏更新过多少次」，都会**永久**堆在缓存目录里。
> 每次游戏更新都换一个新文件，旧文件再也不可能被命中 ——
> 一个 26 MB 起步的**纯泄漏**，而且**没有任何工具返回报过它占了多少**
> （`get_diagnostics` 以前只报一个路径字符串 `cache_dir`）。

**修法（三件事，顺序就是重要性）**：

| # | 做了什么 | 为什么 |
|---|---|---|
| 1 | `_CACHE_NAME_RE` 只认 `<引擎>-<16 位十六进制>.sqlite` | **安全第一**：缓存目录里可能有用户自己的东西，删文件不可逆 → 宁可漏删不可错删 |
| 2 | `prune_cache()` 三条护栏：上限 **2 GiB**、最近 **4** 个不删、**7 天**内用过的不删 | 刻意留宽：误删一个还要用的缓存代价是重解析 0.5~12 秒，多留一个的代价只有 26 MB。按这组数，5 个游戏的 ~130 MB 永远不会被碰 |
| 3 | 命中缓存时 `_touch`（刷新 mtime） | sqlite 的**读**不改 mtime，不 touch 的话天天在用的缓存会被 LRU 当成「最久没用」先删掉 —— 这是 LRU 正确性的前提，不是优化 |
| 4 | `get_diagnostics` 的 `cache_dir` → `cache: {dir, files, total_bytes}`；`index_info` 加 `cache` + **真删了才出现**的 `cache_evicted` | 看得见。没删就不给 `cache_evicted`，不制造恒定噪声字段（§4 的规矩） |

**验收**：新增 `devtools/verify_cache.py`，**54 项断言 / 0 失败**（只需 Mono 样本）。
它把「安全」放第 1 节，并且**所有删除类断言都在临时目录里做**；
真实缓存目录只读（统计 + 默认护栏跑一次 prune + 复查文件数与总量未变）。

**反证（脚本内，每次跑都验一遍）**：

- 把 `_CACHE_NAME_RE` 放宽成 `.*` → 第 1 节那条「非缓存文件不会被删」**必须报红**
  （实测放宽后 `我的笔记.txt` 真的被删了，证明那条断言不是空转）；
- `min_age_seconds` 调到极大 → 同一个目录**一个都删不掉**（证明「会删」的结论非恒真）；
- `min_keep=0` **必须真的把候选全删光** —— 这条专门钉一个反向 bug：
  `files[-0:]` 在 Python 里是**整个列表**，写不好会让「护栏」把**所有**文件都保护起来，
  看起来像护栏生效、实际什么都删不掉。

**过程中自己抓到的一个「报告说谎」**：`cache_evicted.reason` 一开始写死了模块默认常量
`CACHE_MAX_TOTAL_BYTES`，而调用方可以传别的上限 —— 于是测试里用 1 字节上限触发清理时，
报告却写「超过 2147483648 字节」。现在 `prune_cache` 把**本次实际生效**的
`max_total_bytes` / `min_keep` / `min_age_seconds` 一并返回，报告只用真值，
并加了断言钉住（`limit_bytes=1` 且 `reason` 里出现「1 字节」）。

**为什么不加一个「清缓存」工具**：清理是**纯派生数据**的维护动作，
`open_game` 已经每次都做，Agent 不需要为此多一个工具；
想立刻腾空间直接删目录即可（代价只是重解析）。按 §3.1 第 3 条，
不为一个没有独立消费场景的能力加第二个出口。

### 3.15 P1-3b：先量前提，然后**否决**（不改 schema）；顺带修掉「载入失败被降级」

**这一节的价值不在改动，而在于「量完之后改主意」。** 路线图里 P1-3b 写的是
「`parent_name`/`field_type` 入库，查询时不再需要解析器」，状态一直是
「仍未做；取决于『不注入就查索引』有多常用」。那就先量。

**实测（本机 IL2CPP，20,072 类型 / 17 MB 元数据）**：

| 事实 | 实测值 |
|---|---|
| 缓存命中后第一次解析元数据 | **~440 ms**（另一次探测 388~420 ms） |
| 逐题量的 8 个查询里会逼出解析器的 | **7 个**（只有 `index_info` 不需要） |
| 更全的 12 项探测 | **11 个**需要解析器 |
| 解析是「每题一次」还是「每次 open 一次」 | **每次 open 一次**（记在 `idx.meta`，脚本用计数替身证实） |
| 一次 5 查询会话里占多少 | **65~78%**（441 / 683 ms） |
| 解析耗时构成 | `_parse_methods` 184 + `_parse_parameters` 103 + `_parse_fields` 72 + `_parse_types` 57 ms |
| 全量重建（未命中）作参照 | 1225 ms（解析 443 + 建表写库 783） |
| 要改写的查询层函数 | **10 个**（AST 数出来的） |

**三条否决理由**：

1. **半量修复等于零。** `search_classes` 需要解析器只因 `parent` 一个字段
   （`_resolve_parent`）。但「只存 `parent_name`」省不下任何东西 —— 紧接着的
   `class_detail` 仍要解析（它要字段/方法类型）。解析是**全有或全无**，
   所以「`parent_name`/`field_type` 入库」这种**按列拆的清单本身就误导**：
   这两列不能分别计价。
2. **完整修复要动分层。** 要让那 7 个查询都不解析，`class_detail`（遍历
   `m.fields_of`/`m.methods_of`）、`class_hierarchy`（`m.base_chain`）、
   `analyze_dependency`、`_direct_children` 等 **10 个**函数都得改成完全由
   SQLite 驱动 —— 等于在索引层**再实现一遍继承语义**，而 AGENTS.md §3 要求
   引擎差异只出现在 `adapt.py`。两份继承语义互相漂移，正是本项目反复吃亏的
   错误类型（错数据 + 无提示）。
3. **省下的是「每次 `open_game` 一次」的 440 ms**，不是每题。Mod 开发一次
   会话会查很多题，这笔钱很快被摊薄；而缓存命中本身已经是 5~20 ms。

**验收**：新增 `devtools/verify_lazy_meta.py`，**16 项断言 / 0 失败**
（只需 IL2CPP 样本）。它同时是**回归门禁**（命中不解析不许退化、解析每次
open 只发生一次）与**决策门禁**（那张「哪些查询需要解析器」的表空了就提醒
回来订正结论）。含三处非空转反证：手动丢弃已解析结果后解析次数必须增加；
同一个 AST 计数在 `cap.py` 上必须为 0；**把旧写法原样搬回来必须报红**。

**顺手捞到的真缺陷（已修）**：写第一节的计数替身时把 `_load_meta` 的签名
搞错了（它是 `staticmethod`），于是每次调用都抛 `TypeError` —— 结果
`search_classes` **一声不响**地返回 `ok: true` + 200 行 `parent: null`。
根因是 `_resolve_parent` 与 `_resolve_param` 把 `self.meta`（惰性载入，
**真的会失败**的那一步）放进了 `try/except Exception` **里面**，于是
「元数据载入失败」被降级成「这些类没有基类 / 这个参数没有类型」。
这撞在 AGENTS.md §2.3（不许假成功）上，而且 `server.py` 每个工具本来就包了
`try/except → ok: false`，异常抛出去就能变成诚实的错误。

修法是把 `m = self.meta` **提到 try 之外**（只留一行），`try` 继续负责
「这一条解不出来」这种预期内降级（与 `adapt.py` 「解不出来就给 None、不猜」
的政策一致）。反证也进了脚本：把旧写法搬回来，同一个查询立刻变回
`ok: true` + `parent` 全为 `null` —— 证明那两条断言确实能失败。

`docs/项目梳理与优化建议.md` 的 P1-3b 行与结尾都据此改成了**否决**。

## 五、已发现的缺陷

### 1. 四个脚本缺 UTF-8 stdout 设置 → 在 GBK 控制台直接崩 ✅ **已修**

**先说结论，再说教训**：真正缺 `sys.stdout.reconfigure(encoding="utf-8")`
的是 **4 个**，不是最初以为的 2 个：

| 脚本 | 症状 |
|---|---|
| `verify_tool_coverage.py` | 直接运行抛 `UnicodeEncodeError: 'gbk' codec can't encode '\u2705'` |
| `report_tool_coverage.py` | **失败路径**崩溃：门禁本该列出「哪个工具没被覆盖」时自己崩掉，把可操作的报错变成看不懂的编码错 |
| `run_all_verify.py` | **最严重**：19 个脚本全跑完、结论却拿不到 —— 汇总打印 `[✅] xxx` 时崩 |
| `samples.py` | 直接运行（`python devtools\samples.py`，排查样本可用性时的第一选择）崩在最后一行 |

**为什么最初只找到 2 个（这是一条真教训）**：
当时用 `re.search(r"reconfigure|TextIOWrapper", ...)` 扫全仓库，
命中的跳过 —— 但 `run_all_verify.py` 与 `samples.py` 里**有**这两个词以外的
UTF-8 相关代码（前者用 `encoding="utf-8"` 读**子进程**输出），
于是被误判成「已经处理过」。**「提到了 utf-8」不等于「设置了 stdout 编码」**。
第二次改用「先找会打印非 GBK 字符（`✅❌⚠️★💥`）的脚本，再查它有没有
reconfigure」才找全。

**另一条被写错的原因，已订正**：本文件曾称「`run_all_verify.py` 会设
`PYTHONIOENCODING`，所以套件里跑不出来」。**这是错的** ——
`run_all_verify.py` 只设 `PYTHONPATH` 与 `GAMEMOD_COV_OUT`，
**从来没设过 `PYTHONIOENCODING`**。所以套件里同样会踩到，

```python
except Exception:

```

### 6.2 `_probe_parent_sem.py` 的结论**作废**（重要教训）

该探针想核实 `types.parent_il2cpp` / `declaring_il2cpp` 列，得出「0% 匹配」，
看起来像产品 bug。**实际上是探针自己错了**：

这两列由 `adapt.declaring_ref` / `adapt.parent_ref` 写入，
**不是 type 表下标**，不能和 `types.idx` 关联：

- IL2CPP：两者都是 **Il2CppType 索引**；
- Mono：`parent_ref` 是 `extends_ref`，即 **TypeDefOrRef 编码值**
  （低 2 位是 tag：0=TypeDef / 1=TypeRef / 2=TypeSpec，真行号要 `>> 2`），
  `declaring_ref` 是 `parent_index`。

`index.py:381-382` 已写明它们「只用于『有没有外层/有没有基类』的判断，
不参与进一步索引」。**真实基类名只能走 `adapt.parent_name(meta, t)`。**
任何用 type 索引映射去解这两列的探针都是**范畴错误**。

### 6.5 「取最小值」不能用来量两条路径的**差值**（本轮踩到）

`bench_index.best()` 取 N 次最小值 —— 量「单条路径的最优成本」是对的
（排掉调度抖动），但量「A 与 B 差多少」时它会**专挑噪声里最有利的那一次**，
于是符号都能翻：同一个 `subtype_of` 对比，两次跑分别得到 **−4.9 ms** 与
**+14.7 ms**。我据此先写成「秒级」、又错改成「甚至为负」，**两版都是错的**。

正确做法：跑多轮、打印**分布**（最小/中位/最大 + 抖动），
符号是否稳定比中位数更能说明问题 —— 12 轮符号全为正才敢说「是真开销」。
`bench_index.py` 的 `[P1-4]` 段已按这个形状改掉。

> 更一般的规矩（AGENTS.md §5 那条的推论）：
> **能数次数、能看布尔值，就不要比时间**；
> 一旦非要比时间，就得报分布，而不是报一个数。
