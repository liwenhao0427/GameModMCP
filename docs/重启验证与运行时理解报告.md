# 重启验证与运行时理解报告

**问题**：重启本 MCP 后，它对 `E:\project` 下**符合要求**的游戏到底生效了没有？
判断依据是「能建/读索引」+「能注入并调用工具」。另外还要说清**还有什么异常**，
并给出对**不同游戏**的理解总结，用来证明工具确实被正确调用了。

**做法**：不猜。先用**独立进程**起的 stdio MCP 服务器复现每一步（不占用 Agent 会话
那个长驻进程），再对**真实游戏**跑静态与运行时全链路，逐条记录实测值。

**验证时间**：2026-10-03（Python 3.10.6 / frida 17.19.0 / ilspycmd 11.1.0 / MCP v1.0.0，38 个工具）。

**一句话结论**：

1. **生效** —— 两项判断依据都通过：索引能建能读（25 款 Unity + 1 款 UE 全通静态链路），
   注入与工具调用在 **4 款游戏**（2 IL2CPP + 2 Mono）上**逐环节跑通**，
   包括「静态 token == 运行时 token」这条落点对账。
2. **重启本身也验证了**：杀掉服务器进程后 DSH 的 `mcp-client` 会在数秒内
   自动拉起新进程（实测 pid 16504 → 25120 → 12316），工具随即恢复可用。
3. 但测出 **5 个真实缺陷**，其中两个是**架构级**的：同步工具会占住整个事件循环；
   探针的 Frida 同步 RPC 没有超时，一次不返回就会让 `launch_game` 永不返回。
   这两个是**同一个现场的两半** —— 我第一次调 `launch_game` 时把自己的 Agent 会话
   卡死了 11 分钟，根因就在这里。

> 本报告里的数字**全部是跑出来的**，脚本归档在 `devtools/archive/probes/`。
> 命令与复现方式见 §5。

## 1. 重启是否生效

### 1.1 重启机制（实测）

DSH 通过 `~/.dsh/profiles/web/cordis.patch.yml` 里的 `dsh-mcp-client` 以 **stdio** 拉起
`gamemod_mcp/server.py`。该插件自带重连监督器
（`packages/mcp/mcp-client/src/connection.ts`，默认 `maxAttempts=10`、`initialDelayMs=500`）。

实测链路：

| 动作 | 服务器 pid | 结果 |
|---|---|---|
| 杀掉 pid 16504 | → 25120（约 5 秒后自动重建） | 工具立刻恢复 |
| 杀掉 pid 25120 | → 12316（约 6 秒后自动重建） | 工具立刻恢复 |

两次都返回了空的 `get_session`（新进程、无会话）—— 说明拿到的是**新进程**，
而不是旧进程的残留状态。**结论：重启生效，无需重启 DSH。**

### 1.2 两项判断依据

| 判断依据 | 结果 | 证据 |
|---|---|---|
| 可以生成读取索引 | ✅ | 单游戏索引 0.02~2.4 s；矩阵里 26 款受支持游戏全部建起索引 |
| 可以注入并调用工具 | ✅ | 4 款游戏注入成功，工具逐环节返回 `ok:true`（§3） |

## 4. 发现的问题（按严重度）

### 4.1 【严重】同步工具占住整个事件循环 —— 一个工具慢，所有工具都不回话

**现场**：我通过 DSH 调 `launch_game`，它 11 分钟没返回；期间连 `get_session`
（**完全不碰 Frida**，只读进程内的会话状态）也一直超时。

**根因**（读 `mcp` 1.26.0 源码，不是推测）：

- `server.py` 里 **38 个工具全部是同步 `def`**（实测 `async def` 计数 = 0），
  实测经 `FastMCP._tool_manager` 逐个确认：**同步 38 / 异步 0**。
- `fastmcp/utilities/func_metadata.py:92-95` 对同步函数是**直接
  `return fn(**arguments)`**，**没有** `to_thread` / `run_in_threadpool`。

所以任何 `def` 工具都在 **asyncio 事件循环线程**里同步跑完；阻塞期间
stdio 循环不再读任何请求 —— 服务器整体停摆，与锁无关。

**实测证据**（`blocking_check.py`，两条判据都成立）：

```
基线 get_session: ok (0.03s)                       ← 无慢调用时秒回
慢调用（全新缓存 → 真建索引）已在飞，并发探测 get_session…
  探测#1: **1.5s 内无响应** (1.5s)                  ← 被挡住
  探测#2: 秒回 (0.75s)                              ← 慢调用结束后恢复
慢调用: 2.57s ok=True 类型=26535                    ← ① 慢调用确实慢（非空转）
结束后 get_session: ok (0.03s)
→ **阻塞成立**：慢调用期间服务器无法响应任何其它请求
```

**危害**：任何一个慢工具（建索引、`launch_game` 的 60 秒就绪等待、
`decompile` 整个程序集、AOB 扫描、大结果分页）都会让**整个 MCP 在客户端侧
表现为挂死**。这与 `toolCallTimeoutMs: 300000`（配置里已放宽到 5 分钟）
叠加后更糟：客户端会等 5 分钟才报超时，而服务器其实早就不响应任何东西了。

### 4.2 【严重】探针的 Frida 同步 RPC 没有超时，一次不返回就让 `launch_game` 永不返回

**现场**（第一次复现，真 Agent 会话里）：`launch_game(exe=ved.exe)` 调用 11 分钟
不返回；被启动的进程窗口标题是 **`Fatal error in GC`**。

**根因**（读源码得出）：

- `RuntimeSession._call` 用 `self._script.exports_sync.init(...)` ——
  **Frida 的同步 RPC 没有超时参数**。
- `RuntimeSession.wait_ready` 的循环里，`deadline` **只在每次 `init` 返回之后**
  才被检查（`session.py:382-393`）。所以只要有一次 `init` 不返回，
  整个 60 秒预算就被架空，`launch_game` 永不返回。

**定向复现**（`wedge_repro.py`，**第 1 轮即命中**，不是偶发）：

```
===== 第 1 轮 pid=24860 =====
  ** init#3 15 秒未返回！（t+15.1s，标题='Fatal error in GC'）
  再等 45 秒后：仍未返回（标题='Fatal error in GC'）
```

命中的进程：`MainWindowTitle = 'Fatal error in GC'`、工作集停在 16 MB、
线程数不再增长 —— 与 Agent 会话里那次**完全一致**。
`ved.gc.log` 里那行 `Collecting from unknown thread` 是同一处现场。

**注意这**不是**「探针把游戏打崩」**：同一台机器上
- 手动双击 `ved.exe` → 约 10 秒进主窗口；
- Frida `spawn` + attach（**不加载探针**，stdio 分别用 inherit / pipe）→ 4 秒进主窗口；
- Frida `spawn` + attach + **加载探针并先 resume 再轮询 init** → 6 轮 6 次正常。

也就是说：**风险集中在「resume 之后立刻高频轮询 init」这条路径**，
而它正是 `launch_game` 走的那条（`ensure_runtime` 先 resume，再 `wait_ready` 每 0.5 s 调一次）。

**这一条与 §4.1 是同一个现场的两半**：探针 RPC 不返回 → 同步工具永不返回 →
事件循环被占死 → 所有工具都不回话。第一次复现时两半同时出现，所以看起来像
「MCP 整个坏了」，实际是两层问题叠加。

### 4.3 【中】失败的 `open_game` 仍然改写会话身份（失败带副作用）

**现场**（`failed_call_side_effect.py` 实测）：

```
① 先选一个真实存在的游戏，建立基线
   ok=True game_dir='E:\project\Ved' engine='il2cpp' exe='E:\project\Ved\ved.exe'

② 调用一个必定失败的 open_game（容器目录）
   ok=False（这一条是正确的：明确拒绝）

③ 关键：失败之后，会话被改成什么了？
   game_dir='E:\project'
   engine  ='unknown'
   exe     ='E:\project\Im.No.Demonlord.Build.24620186\ImNoDemonlord.exe'
```

**危害不是「数字看着怪」**：`launch_game()` 不传 `exe` 时会用会话里的 `exe`，
也就是会去**启动容器目录下的某一款游戏** —— 正是
`docs/多游戏兼容性扫描报告.md` §3.1 警告的最坏情况。
而且原本可用的 Ved 会话（连同索引）被推倒了。

**根因**：`select_game`（`engine/state.py:292-294`）在**判定能否支持之前**就写了
`_state.game_dir` / `_state.engine`，失败分支只 `return`，没有回滚。
同一个文件里 `ensure_runtime` 专门为「失败带副作用」写过一段注释并做了
「先连新的、连上了才断旧的」修复（`state.py:752-805`）——
**同类问题在 `select_game` 这条路上还在。**

### 4.4 【中】`ue_manifest` 自动挑清单挑错，给出误导性的「零命中」

**现场**：

```
ue_manifest(game_dir="E:\project\CatapultHero", pattern=".locres")
→ total=3, matched=0
  note: "清单解析成功（共 3 条），但过滤条件 '.locres' 没有命中任何条目"
```

`CatapultHero` 明明有 51 个 `.locres`。**根因**：`server.py:2255-2259` 用
`ue_mod.find_manifests(root)` 的 `found[0]`，而 `find_manifests` 是
`sorted(root.glob("Manifest_*.txt"))` —— 字母序第一是
`Manifest_DebugFiles_Win64.txt`（3 条），**不是** `Manifest_UFSFiles_Win64.txt`（18,419 条）。

同一个模块里已经有正确的判据 `_is_ufs_manifest`（`engine/ue.py:906-913`），
但只在 `ue_profile` 里用了（`ue.py:1441`），`ue_manifest` **没用**。

**危害**：那个 `note` 让调用方以为「包里没有本地化文本」，而实际是**问错了清单**。
指定 `path=` 就正常：

```
ue_manifest(path="…\Manifest_UFSFiles_Win64.txt", pattern=".locres")
→ total=18419, matched=51   ✅
```

### 4.5 【低】`container_candidates` 截断候选却不标注

```
count = 25          ← 总数（真值）
candidates 条数 = 20 ← 只给了 20 个
'has_more' in c ? False
```

`discovery.py:587` 写的是 `roots[:MAX_CANDIDATES]`（`MAX_CANDIDATES = 20`），
**没有任何字段告诉调用方被截断了**。这违反 AGENTS.md 的
「任何可能上万条的返回都必须 … 在 `has_more` 里如实标注是否被截断」。
本条实际影响很小（25 → 20，少的 5 个仍能通过别的途径看到），
但它是**同一类**问题，且修起来是几行。

```powershell
       --json .cache-matrix\matrix-e-project.json

# 2) 运行时链路（attach 模式；会手工启动并结束被测游戏）
python devtools\archive\probes\runtime_matrix.py          # 4 款样本全跑
python devtools\archive\probes\runtime_matrix.py Ved      # 只跑一款

# 3) 缺陷复现
python devtools\archive\probes\blocking_check.py            # §4.1 事件循环阻塞
python devtools\archive\probes\wedge_repro.py 6             # §4.2 init 不返回（第 1 轮常命中）
python devtools\archive\probes\failed_call_side_effect.py   # §4.3 失败带副作用

# 4) 参考：真实 MCP 路径的 launch_game 成功率（6/6 正常）
python devtools\archive\probes\bounded_repeat.py 6 90
```

这批脚本按 `devtools/archive/README.md` 的约定放进 `archive/probes/`：
它们是**一次性侦察脚本**（文件名不以 `verify_` 开头，不被
`run_all_verify.py` 收集），用来回答「这个格式/这个现场到底长什么样」，
不参与门禁。

> **注意**：§4.2 的复现会**故意把游戏卡死**（`Fatal error in GC`）。
> 脚本已按进程树硬杀（`taskkill /T /F`）做收尾 —— 普通 `communicate()`
> 收尾会跟着一起挂，因为 `script.unload()` / `session.detach()` 同样是
> 没有超时的同步 Frida 调用（这本身就是缺陷的一部分）。

## 6. 结论：对不同游戏的理解总结

### 6.1 IL2CPP（17 个样本）

**工具做的事**：解析 `global-metadata.dat` → SQLite 索引（类型/方法/字段/token），
注入后把类实体化，拿真实字段偏移与方法地址，用 token 对账。

**实测理解**：

- 规模跨度很大但都稳：最小 `PathOfIdle` 14,477 类型 / 92 程序集，
  最大 `Dave.the.Diver` 44,402 类型 / 182 程序集，全部建起索引、类详情可用。
  索引耗时 0.02~1.8 s（命中缓存 0.02 s）。
- 字段类型是**启发式**（约 90% 可解），所以 `class_detail` 的字段类型要带
  `type_confidence` 看；偏移必须运行时取 —— 实测 `Transform.m_CachedPtr`
  偏移 = 16，与运行时一致。
- **版本区间是硬边界**：v24~v31 可解，v39（Unity 6.3）**如实拒绝**。
  这是设计，不是缺陷；遇到 v39 样本不要当工具坏了。
- 嵌在子目录里的布局（`Everything.is.Crab.v1.0.1\Everything.is.Crab.v1.0.1`）
  能自动识别，说明「套一层」的兜底仍然有效。

### 6.2 Mono（10 个样本）

**与 IL2CPP 的配方完全一致**（注入 → 真实偏移/地址 → token 对账 → Hook），
但多一个 IL2CPP 没有的能力：**可以直接反编译出 C# 源码**。
实测 `decompile(type_name="SpellEffect")` 拿到 67 行真正的 C#（1,192 字符），
内容是 `SpellEffect : MonoBehaviour` 的属性与 `Apply(...)` 方法体。

**必须记住的 5 条差异**（全部实测成立，见 §3.3）：
① 没有 RVA（JIT 机器码，`in_module=false`）；② `gc_control` 不支持；
③ 程序集懒加载，注入后会等稳定（实测 2.4 s）；
④ 短名只认顶层类型；⑤ **静态索引不含 `UnityEngine.*`**。

第 ⑤ 条最容易踩：拿 `UnityEngine.Time` 去做静态 token 对账会得到空列表，
**必须换成游戏自己的类**。工具给的报错已经把这条说清楚了。

### 6.3 Unreal（1 个样本：CatapultHero）

**能力边界完全不同**：UE 没有集中元数据，`search_classes` / `class_detail` /
`open_game` **都不适用**（`open_game` 会明确返回 `ok:false` + `next_tools`，
这条修复实测生效）。UE 的强项是**资源容器**：

- `detect_ue`：`is_ue=true`、confidence 51、214 个 `/Script/` 模块、279 个对象路径；
- `ue_profile`：`.pak` 4,556 条 + `.utoc` 7,178 条，与 `Manifest_UFSFiles` 比对
  **`match_ratio = 1.0`**（packaged 真值逐条对上）；
- `ue_manifest`：18,419 条（**必须显式给 `path=`**，见 §4.4）。

**UE 版本号拿不到是正常的**，工具返回空串 + 原因，**不猜**。
`ue_script_objects` 在**启动器** `CatapultHero.exe` 上返回 `ok:false`
（它不是 UE 二进制），要指向 `-Win64-Shipping.exe` —— 这是正确行为。

### 6.4 不支持引擎 / 非游戏（8 个）

Godot / GameMaker / Electron / 自研引擎 / 工具目录，工具**如实报 `unknown`
并给出家族证据**（`.pck`、`data.win`、`chrome_*.pak`）。
`engine` 仍然是 `unknown` —— 提示是「解释」，不是「假装支持」。
用 Agent 时看到这些应当**直接停下并说明原因**，不要反复重试 `open_game`。

### 7.1 复验时发现并修掉的**新**缺陷（本次改动引入）

`close_session` 在探针卡死时**自相矛盾**：`runtime.restored` 是 `false`，
而顶层 `restored` 却是 `true` —— 正是 AGENTS.md 禁止的假成功。
根因是卡死分支返回 `ok:True`（想表达「会话对象已作废」），
而顶层按「任一子步骤 `ok:false` 才算失败」判定，于是照旧报成功。

修法是把两件事拆成两个字段：`ok:false` + `restored:false`（游戏**没有**恢复原状）
与 `session_released:true`（会话已作废、可以重新注入）。见提交 `26890bc`。

### 7.2 §4.2 的根因仍未定位（**不许**说成「游戏自己的问题」）

现有证据（`devtools/archive/probes/frida_matrix.py` 的 A~G 形态）：

| 形态 | 做法 | 结果 |
|---|---|---|
| A | Frida spawn + attach，**不加载探针**，stdio=inherit | ✅ 4 秒进主场景 |
| B | 同上，stdio=pipe | ✅ 4 秒进主场景 |
| C | spawn + 加载探针，**先保持挂起**再轮询 init | ✅ 进主场景 |
| E | spawn + 加载探针，**先 resume 再立刻轮询 init**（= `launch_game` 的真实顺序） | ❌ 曾卡死（`Fatal error in GC`） |
| F | 同 E，但 resume 后**先等 25 秒**再加载探针 | ✅ 进主场景 |
| G | 同 E（verbose 打点） | ✅ 进主场景 |

结论只有一句：**触发条件与「探针在游戏早期就调 `il2cpp_thread_attach`」有关**，
且**间歇**（E 与 G 同路不同命；真实 MCP 路径曾 6/6 正常、也在别的时点连续卡住）。
所以：

- **不能**把 `Fatal error in GC` 读成「游戏自己坏了、与探针无关」——
  证据反而指向探针的调用时机。
- 也**不能**说已经修好了 —— 现在修的是「不再无限挂住」，不是「不再卡死」。
- 下一步要查的是 `agent.js` 的 `ensureReady`：域指针的有效性判据
  （`domainPointer()` 只试读一个指针）在游戏早期是否足够；
  以及 `il2cpp_thread_attach` 是否有更安全的替代路径
  （例如只在 `il2cpp_init` 完成后附着，或改用 `il2cpp_thread_current` 判定）。

### 7.3 对照实验：危险窗口在「游戏启动后的头几秒」

用 `devtools/archive/probes/wedge_ab.py` 做了**多轮对照**（Ved，每格 8 轮，
`init` 超过 12 秒不返回即判卡死；「第一次探测前的静默」与「探测间隔」
两个因素分开测）：

| 第一次探测前的静默 | 探测间隔 | 卡死率 | 说明 |
|---|---|---|---|
| 0 秒 | 0（紧循环） | **8/8** | 最恶劣 |
| 0 秒 | 0.1 秒 | 1/8 | |
| 0 秒 | 0.5 秒（产品原值） | 0/8 | |
| **3 秒** | **0（紧循环）** | **0/8** | 静默生效 |

**读法（重要）**：`interval` 与 `settle` **都能**把卡死率压到 0，
但只有 `settle` 是「不去碰危险窗口」，`interval` 只是「少碰几次」。
产品原值（0.5 秒间隔、0 静默）在这张表里是 0/8，可它在真服务器上**确实卡死过两次**
—— 说明还有本实验没覆盖到的因素（例如真服务器上并发的 `close_session`、
以及紧邻的上一次 `taskkill`）。**这张表不能当「产品已经修好」的证据。**

**据此做的缓解**：`RuntimeSession.READY_SETTLE_DELAY = 3.0` ——
spawn 路径第一次探测前先静默 3 秒；`attach` 路径显式 `settle=0`
（注入的是**已经启动好**的进程，没有那个窗口，白等 3 秒纯属浪费）。
验证：`devtools/archive/probes/verify_settle.py` 在**最恶劣条件**
（探测间隔 0）下走**产品** `wait_ready`，实测 **卡死 0/8、正常就绪 8/8**。

**同时被排除的两个假设**（都跑了 8 轮，都不是原因）：

- 「就绪判据太松」：把 `domainPointer()` 加严（要求
  `il2cpp_domain_get_assemblies` 返回合理数量）后**仍然 8/8 卡死**。
- 「子进程输出转发导致游戏阻塞」：复刻产品的 `_hook_child_output`
  注册 device 级 output 回调后**仍然 0/8**（未复现卡死）。

### 7.4 为什么**不**声称根因已修

三个理由，缺一不可：

1. **根因未知**。现在只知道「危险窗口在启动头几秒」，不知道那几秒里
   `il2cpp_thread_attach` 具体踩到了什么。
2. **实验覆盖不全**。对照表里 0.5 秒间隔是 0/8，而产品在同一配置下真卡死过 ——
   说明有本实验没复刻出来的因素。
3. **缓解 ≠ 修复**。`settle` 是「避开窗口」，一旦游戏加载更慢（低配机、
   大包体），3 秒可能又落回窗口内。

真正兜底的是 `CALL_TIMEOUT`（30 秒）：**无论卡不卡，都不会再无限挂住**，
且会如实报 `wedged`。这才是本次能确定交付的东西。

另建议：把 §4.1 与 §4.3 各补一条 `verify_*.py` 断言（含非空转反证），
这两条都是「静默坏结果」型缺陷，靠人工复测容易漏。
