# 多游戏兼容性扫描报告

**问题**：本 MCP 对「大部分符合规范的游戏」到底能不能生效？生效到哪一步？哪里需要改进？

**做法**：不猜，直接把本机两个游戏目录下的**每个**候选游戏喂给**真 MCP 服务器**
（stdio JSON-RPC，和 Agent 用的完全同一条路），按阶段逐层推进并记录结果。

**扫描时间**：2026-10-01（本机 Python 3.13.1 / frida 17.17.0 / ilspycmd 9.0.0，三类解析器均 ready）。

**一句话结论**：**15/15 款真正受支持的游戏全部生效到「静态分析的最后一层」**
（13 款 Unity + 2 款 UE；IL2CPP 到 `class_detail`、Mono 到 `decompile`、
UE 到 `ue_list_entries`），**没有任何一个阶段失败**；
同时也测出了 **2 个必须修的问题**（一个已修、一个待修），
其中「父目录被当成游戏」会让 MCP **静默分析另一个游戏**却返回 `ok: true`。

---

## 1. 测什么、怎么判

驱动脚本：`devtools/report_multi_game_matrix.py`（本次新增）。

它做三件事：

1. **发现候选**：在两个样本根下按深度受限的目录扫描找引擎标记
   （IL2CPP 的 `global-metadata.dat`、Mono 的 `*_Data/Managed`、UE 的 `Paks/*.pak|utoc`）；
   另外把「有大 exe 但没有引擎标记」的目录也**单独列出来**，
   而不是悄悄丢掉 —— 这一批正是「没生效」的证据来源。
2. **逐阶段驱动真服务器**：每个游戏依次调用

   ```
   inspect_game → inspect_binary → open_game → list_images → search_classes
   → class_detail → search_fields → find_derived_classes → decompile
   （UE 走 detect_ue / ue_profile / ue_list_entries / ue_script_objects / ue_manifest）
   ```

   每个阶段记 `ok / fail / 不适用`，失败的**原始报错**原样保留。
3. **统计 + 落盘**：矩阵、按引擎汇总、各阶段失败数、非支持引擎的家族判定，
   全部写进 `.cache-matrix/matrix.json`（含统计块，避免读者自己再汇总一遍）。

判读口径（本报告里的「生效到哪一步」）：

| 结论标记 | 含义 |
|---|---|
| `✅ IL2CPP/Mono 可用（到类详情[、反编译]）` | 该引擎的静态能力**全部**跑通 |
| `✅ UE 全通（3/3）` | `detect_ue` / `ue_profile` / `ue_list_entries` 都通 |
| `△` | 目录像 Unity，但找不到 IL2CPP/Mono 元数据 |
| `✗ 不支持的引擎（xx；实际上像 yy）` | 引擎不在支持范围内（报告侧会给出家族猜测） |
| `✗ 探测即失败` | 连 `inspect_game` 都没过 |

**边界（必须说清）**：本次扫的是**静态阶段**（元数据 / 容器 / PE）。
运行时阶段（注入、Hook、字段偏移、token 对账）不在本次扫描范围内，
它由既有的 `verify_runtime*.py` / `verify_il2cpp_runtime.py` / `verify_mcp_tools.py` 覆盖。

## 3. 发现的问题（按优先级）

### 3.1 【已修复】切换游戏时，上一个游戏的 `exe` 会串到新会话

**现象**：同一进程内

```
open_game(某个 Mono 游戏)      → exe = "...\Gambonanza_Data\Managed"
open_game(某个 IL2CPP 游戏)    → exe 仍然是上面那个 Mono 目录   ← 串了
```

扫描之外的**手工实测**（长驻进程里先开 Gambonanza，再开 `D:\Projects`）拿到的是
**跨盘符**的串值 —— `game_dir` 在 D 盘，`exe` 却是 C 盘下 Gambonanza 的托管目录，
原文见 §3.2 的那段 JSON。这类值一旦被 `launch_game()` 默认使用，
就是「启动并注入了上一款游戏」。

**根因**（`engine/state.py`）：`_state` 是进程级单例，切换游戏时只关掉了索引/运行时，
**没有清身份字段**；而各引擎分支只写自己那几项 ——
IL2CPP 分支只写 `metadata_path`，**不写 `exe`**，于是旧值被保留下来。

**为什么危害大**：`exe` 正是 `launch_game` / `ue_profile` / `detect_ue` /
`inspect_binary` 在**不传参时**默认使用的目标。最坏情况是
`launch_game()` 启动并注入了**上一款游戏**。

**为什么以前没发现**：新进程里第一次 `open_game` 看不出问题
（那时 `_state.exe` 本来是空的，兜底会填对）。只有「长驻服务器进程里切换游戏」才暴露，
而这**正是 Agent 的用法**。

**已修**：新增 `SessionState.reset_target()`，在切换游戏的路径上显式清空
`game_dir / engine / exe / metadata_path`。
**已加验收**：`devtools/verify_session_switch.py` —— 三层（注入陈旧值 → 真实
Mono→IL2CPP→UE 切换 → 进程级 stdio 端到端），并带**非空转反证**
（把 `reset_target` 换回空操作，断言必须报红）。14 项全过。

### 3.2 【待修，优先级最高】父目录被当成游戏：静默分析另一个游戏，还返回 `ok: true`

**现象**（原始输出，未改一字）：

```json
inspect_game("D:\\Projects")
{"ok": true, "engine": "il2cpp",
 "main_exe": "D:\\Projects\\Pass The Fear(5).exe",          ← 3.3 GB 的自解压安装包
 "main_exe_runtime": "native", "main_exe_is_64": true,
 "il2cpp": {"game_assembly": "",
            "metadata": "D:\\Projects\\Echoes.of.Mystralia.Early.Access\\Echoes_Data\\il2cpp_data\\Metadata\\global-metadata.dat"}}
```

```json
open_game(game_dir="D:\\Projects")            // 实测原文（省略了索引细节）
{"ok": true, "reused": false, "elapsed": 1.598,
 "game_dir": "D:\\Projects",
 "engine": "il2cpp",
 "exe": "C:\\Users\\Administrator\\Projects\\GambonanzaModDev\\Gambonanza\\Gambonanza_Data\\Managed",
 "metadata_path": "D:\\Projects\\Echoes.of.Mystralia.Early.Access\\Echoes_Data\\il2cpp_data\\Metadata\\global-metadata.dat",
 "index_ready": true,
 "index": {"type_count": 21831, "method_count": 169422, "field_count": 111358,
           "image_count": 107, "engine": "il2cpp"}}
```

> 这段是**当前这个长驻 MCP 服务器进程**（在本轮改 `state.py` **之前**启动）给出的输出，
> 所以同时能看到两个缺陷：`game_dir` 在 D 盘、`exe` 却在 C 盘另一个游戏下（§3.1 的泄漏），
> 以及引擎/元数据张冠李戴（§3.2）。
> **改了源码必须重启 MCP 服务器进程才生效** —— 客户端（含 DSH）是在启动时
> 拉起 `gamemod_mcp.server` 的，之后一直用那份旧代码。
> `devtools/verify_session_switch.py` 每次**新起进程**，所以它测的是修好之后的行为。

`D:\Projects` **不是游戏**，是个装着十几款游戏的目录，但 MCP 返回
`ok: true`，并把**下层某个游戏**的元数据当成「这个目录的游戏」索引起来。
扫描里另一个候选 `C:\Users\Administrator\Projects` 也一样
（判定 il2cpp，实际索引到 Echoes）。

**这不是「数字看着怪」而是「换了个游戏」**：`C:\...\Projects` 这一行的计数
与 `Echoes.of.Mystralia` 那一行**逐项完全相同**（21,831 / 169,422 / 111,358 /
107 个程序集 / 1,546 个 MonoBehaviour；`matrix.json` 可直接比对），
而它返回的 `game_dir` 却是 `C:\Users\Administrator\Projects`。
也就是说：**Agent 会以为自己在分析容器目录，实际上全程在读另一个游戏的元数据。**

**根因**（`engine/discovery.py`）：为了支持「游戏外面还套一层目录」的布局
（`<root>/<game>/<game>_Data`，本机 `Everything.is.Crab.v1.0.1\...` 就是这种），
`il2cpp_paths()` 在找不到同级 `*_Data` 时会退到 `glob("*/*_Data")`：

```python
data_dirs = [d for d in game_dir.glob("*_Data") if d.is_dir()]
if not data_dirs:
    data_dirs = [d for d in game_dir.glob("*/*_Data") if d.is_dir()]   # 这里
```

这个兜底**无法区分**「套了一层的单游戏目录」与「装了很多游戏的父目录」——
两者都长成 `<dir>/<X>/<X>_Data`。`mono_paths()` 有同样的兜底，
所以 `D:\Projects` 只差一点就会被判成 Mono。

顺带两个小问题：

- `main_exe` 取了 **3.3 GB 的安装包**（`Pass The Fear(5).exe`）并给出
  `main_exe_runtime: "native"`、`is_64: true` —— 数字是真的，但对用户毫无意义，
  而且掩盖了「这个目录没有游戏主程序」这个事实。
- `il2cpp_paths()` 最后还有一段**无深度限制**的 `rglob("global-metadata.dat")` 兜底。
  实测代价不大（本机最大的非 Unity 目录 0.43 s），但它是「整棵树地毯式搜索」，
  且与上面的问题叠加后会让误判更难解释。

**建议的修法**（很便宜，且不破坏合法布局）：

1. 在子目录里找到候选游戏根时，**数一数有几个**：
   多于一个就**不猜**，返回 `ok: false` + `candidates`（让调用方明确指定 `game_dir`）。
   `D:\Projects` 会因此被正确拒绝，而「只套一层」的合法布局照旧可用。
2. 一致性校验：`<X>_Data` 的可信度取决于同目录是否存在 `<X>.exe`；
   IL2CPP 还应要求同目录有 `GameAssembly.dll`
   （本例 `game_assembly: ""` 已经在提示这个矛盾了）。
3. `main_exe` 的挑选加一条：跳过体积异常（比如 > 1 GB）且与目录名无关的 exe，
   或在返回里标注「可能是安装包，不是游戏主程序」。
4. 把无深度限制的 `rglob` 换成有界搜索，并在返回里带上「元数据是在第几层找到的」。

### 3.3 【待修】UE 的 `open_game` 报错既误导、又没有出口

UE 游戏按设计不走 `open_game`（UE 没有集中元数据），但工具返回的失败信息是
（`matrix.json` 里 CatapultHero / Dinoblade 的原文）：

```
当前会话没有元数据文件。请先用 select_game 选定游戏，
或用 metadata_path 指定 global-metadata.dat。
```

问题在于：**这次调用已经把游戏选好了** —— 同一行返回体里的 `game_dir`
就是那个 UE 目录，随后 `ue_profile` / `ue_list_entries` 也确实取到了数据。
报错却让调用方去做一件刚刚做完的事，而且**完全没提**
「UE 请改用 `detect_ue` / `ue_profile` / `ue_list_entries`」。
Agent 很容易在这里走进死胡同（反复重试 `open_game` 或去翻 `metadata_path`）。

**附带一条因果链（值得记下来）**：修 §3.1 之前，这里报的是**另一句话** ——

```
元数据解析失败：不支持的引擎类型：'ue'（可用：il2cpp / mono / auto）
```

它之所以是「引擎类型参数填错了」的口吻，是因为当时 `_state.metadata_path`
**还留着上一款 IL2CPP 游戏的路径**（正是 §3.1 的泄漏），
代码便拿着一个陈旧的 IL2CPP 元数据 + `engine='ue'` 去开索引。
也就是说：**这条报错本来是泄漏的症状**；泄漏修掉之后，
底下的真问题（UE 该走哪条路、怎么把话说清楚）才露出来。

**另**：`devtools/verify_mcp_ue.py` 从来没有断言过这条路径，
所以「UE 上 `open_game` 报什么」一直没人管。
建议改成显式的「不适用」+ 下一步指引，并把这条断言补进 UE 验收。

### 3.4 【待修】不支持的引擎只给 `unknown`，不给证据

`inspect_game` 对 Godot / GameMaker / Electron 三款真实游戏都只回
`engine: "unknown"`，没有任何提示。而**报告侧**用几行代码就区分了出来：

| 特征 | 判定 |
|---|---|
| `*.pck` + `data_<名字>_windows_*` 导出目录 | Godot |
| `data.win` | GameMaker Studio |
| `chrome_*.pak` / `app.asar` / `resources` | Electron / Chromium |

这些判定成本极低、误报率也低，直接放进 `inspect_game` 的返回
（例如 `engine: "unsupported"` + `hint: "Godot（发现 1.46 GB 的 .pck）"`），
能让 Agent 立刻知道「不是本工具坏了，是这游戏不归它管」，而不是反复重试。

### 3.5 【待修】`search_classes` 的 `full_name` 对嵌套类型是**短名**

对 IL2CPP 样本实测：`search_classes` 返回的
`full_name` 是裸短名（如 `$BurstDirectCallInitializer`、`<>c__DisplayClass41_0`），
与 `nested_name` 不同；而 `decompile` / `class_detail` 需要的**是** `nested_name`。

后果：Agent 照着「用 `full_name`」去调，会遇到一个**很响的失败**
（`命中 6 个类` 或 `找不到类型`）。工具本身没错
（`class_detail` 会明确拒绝并给出 `candidates`，这是对的），
但**返回字段的语义不一致**会稳定地把 Agent 带偏。

建议：`search_classes` 同时返回 `class_detail` 能直接吃的那个名字
（或把 `full_name` 改成限定名），并在 `search_classes` 的说明里挑明。

### 3.6 【已修复】文档里的 `python <ABS>/src/gamemod_mcp/server.py` 其实是坏的

README 与 `mcp-config/` 一直推荐这种启动方式，但 `server.py` 用的是相对导入
（`from . import cap`），以脚本方式运行时没有父包，于是**在任何工具注册之前**就抛

```
ImportError: attempted relative import with no known parent package
```

客户端看到的只有 `McpError: Connection closed` —— 完全看不出是入口写法的问题。

修复过程中还发现它**不止一处**：`warn` / `progress` / `ue` / `decompile`
都是写在函数体里的**惰性相对导入**，于是「`initialize` + `tools/list` 全过」
与「一调用 `ue_*` / `decompile` 就 ImportError」可以同时成立。
现已全部收敛到入口的一处双分支导入。
**已加验收**：`devtools/verify_stdio_entry.py`（两种启动形式 + 脚本形式下
真调 5 个 UE 工具与 `decompile` + stdout 纯度 + 坏入口反证），19 项全过。
